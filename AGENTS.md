# Проектные инструкции: быстрый маршрутизатор

## Постоянные инварианты — читать всегда

1. Проект строит поддерживаемый PostgreSQL-слой поверх read-only 1С для Power BI.
   Источник истины: физическая БД, подтверждённые материалы, текущие SQL/M/DAX,
   бизнес-требования и контрольные значения.
2. Статусы: `CONFIRMED`, `ASSUMPTION`, `UNKNOWN`, `BLOCKER`, `DECISION_REQUIRED`;
   для непроведённой технической проверки — `VALIDATION_PENDING` и
   `NOT_EXECUTED`; на Stage 2 также `VALIDATION_IN_PROGRESS`, `VALIDATED`,
   `VALIDATION_FAILED`, `BLOCKED`. `BLOCKER` требует внешнего решения или
   authority, `BLOCKED` означает недоступную техническую проверку, а
   `DECISION_REQUIRED` — выбор пользователя при известных фактах.
3. Без явно одобренного пакета запрещены переход в Stage 3, DDL/DML, создание
   объектов и изменение источника 1С. Одобрение пакета может охватывать все
   перечисленные операции и SQL-план в его границах; отдельное согласование
   каждого подшага не требуется. Исходные схемы доступны только для чтения.
4. Первый релиз воспроизводит текущие SQL/M/DAX. Методическое улучшение не
   меняет результат без отдельного решения и фиксируется по BR-018.
5. Внешние Excel-файлы, их структура и Power Query не анализируются, не
   переносятся и не запрашиваются, пока пользователь явно не отменит запрет.
6. Любой физически отсутствующий источник фиксируется только в
   `docs/source_metadata/missing_source_objects.md`.
7. Новое важное требование пользователя до следующего связанного блока
   фиксируется в соответствующем артефакте; процессное — в этом файле или
   playbook, бизнес-правило — также в `docs/catalogs/business_rules.md`.
8. Не теряй чужие изменения, не показывай секреты, не выполняй опасные действия
   без разрешения. Не выдумывай поля, ключи, grain или бизнес-логику.
9. Пользователь согласует законченный логический пакет, а не отдельные
   команды. Пакет включает все безопасные подшаги, необходимые для его
   результата: анализ, проверки, документацию, SQL/миграции/загрузку/тесты,
   если они входят в одобренные scope и этап. Пока пакет активен, агент не
   останавливается, не возвращается за промежуточным подтверждением и не
   отвлекает пользователя без реального `BLOCKER`. После закрытия к пакету не
   возвращаются без нового триггера в ledger или нового явного поручения.
   `ПРОДОЛЖАЮ РАБОТУ` допускается только в `commentary`, никогда в `final`.
10. До открытия уже согласованного нового пакета обязательно проверь
    `.agents/report_checkpoint_ledger.tsv` командой
    `scripts/check_package_selection.sh`. Статус `PARTIALLY VALIDATED` не
    разрешает повторный прогон: отчёт выбирается только при
    `READY_FOR_NEW_CONTROL` с зафиксированным новым триггером.
11. Глобальный переход запрещён: не открывать новый пакет, не выполнять новую
    Stage 2-проверку, не переходить в Stage 3 и не создавать витрины, пока не
    закрыты все критичные вопросы по всем отчётам и таблицам проекта. Это
    ограничение проверяется `scripts/check_package_selection.sh` через
    `.agents/project_stage_gate.tsv`; снять его можно только явным решением
    пользователя после документированного полного review.
12. Промежуточное сообщение заканчивается одним конкретным следующим действием
    или самодостаточным вопросом. Только итог завершённой работы по последнему
    комментарию пользователя и любой `final` следуют контракту
    `Сделано → Результат → Дальше`; перед ними обязательна единая fail-closed
    проверка `scripts/preflight_message.sh`. Непрошедший либо пустой итог не
    отправляется.
13. Для всех витрин полный rebuild — редкая отдельная операция со своим
    измеренным baseline. Ежедневный SLA не более одной минуты относится только
    к явно спроектированному incremental refresh с подтверждёнными watermark,
    обработкой late changes/deletions и reconciliation; полная `DELETE + COPY`
    не может выдаваться за такой инкремент. Пакет такого инкремента не
    открывается до готовности всех витрин проекта.
14. Утверждение пользователя о том, как устроен текущий результат Power BI,
    M, DAX или PBIT, фиксируется как `ASSUMPTION` до проверки актуального
    локального шаблона. Оно не меняет SQL, grain, флаги или физическую модель
    только по авторитету говорящего. Явное пользовательское решение о целевом
    правиле можно принять сразу, но не выдавать за воспроизведение current
    шаблона; в mapping обязательно разделять оба статуса и ссылаться на
    конкретный проверенный M/DAX/PBIT-артефакт.
15. Для каждого будущего SQL-пакета с физической загрузкой сначала выполнить
    безопасный репрезентативный sample `EXPLAIN (ANALYZE, BUFFERS)` точного
    source extract, записать rows/time/I/O и оценить масштабирование; только
    после этого разрешены full-range plan, `COPY`, DDL/DML или иной transport.
    Target read-plan измеряется после успешной atomic load до приёмки. Нельзя
    запускать параллельный тяжёлый plan и transport: он искажает baseline.

## Маршрутизатор — читать ровно по событию

| Событие | Обязательный файл |
|---|---|
| Новый отчёт / новая сущность | `.agents/playbooks/report_lifecycle.md` |
| Stage 1 | `.agents/playbooks/stage_1.md` |
| Stage 2 | `.agents/playbooks/stage_2.md` |
| Stage 3 | `.agents/playbooks/stage_3.md` |
| Новый physical mart/rebuild в Stage 3 | `.agents/playbooks/mart_delivery_preflight.md` |
| SQL, миграция, источник, безопасность | `.agents/playbooks/safety.md` |
| Рабочее сообщение, пакет, коммит | `.agents/playbooks/communication.md` |
| Выбор нового пакета | `.agents/report_checkpoint_ledger.tsv`, `scripts/check_package_selection.sh` |
| Любой `final` | `.agents/playbooks/final_preflight.md`, `.agents/playbooks/communication.md` и `scripts/preflight_message.sh` |
| Точная историческая цитата | `.agents/playbooks/full_policy_reference_2026-08-11.md` только как архив |

Перед действием читай только строки `Постоянные инварианты` и относящийся к
событию playbook. Полный reference — ненормативный архив: он помогает найти
точную прежнюю формулировку, но никогда не дополняет и не отменяет действующие
правила. Правила состава, канала и проверки сообщений берутся только из
`communication.md` и `final_preflight.md`.

## Приоритет и решение конфликтов

1. Явное новое указание пользователя выше playbook, но не отменяет безопасность
   или ограничения этапа без прямого разрешения.
2. Ограничение этапа выше удобства процесса.
3. Текущий SQL/M/DAX выше неподтверждённой «улучшающей» интерпретации.
4. Если правило допускает два разных действия, не угадывай: используй
   `BLOCKER` только когда безопасной разрешённой работы не осталось.
