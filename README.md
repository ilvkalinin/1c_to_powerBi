# Аналитический слой PostgreSQL для Power BI

Проект предназначен для разработки витрин PostgreSQL поверх read-only данных 1С. Power BI должен получать очищенные факты и справочники со стабильными типами и известной гранулярностью, а тяжёлые повторяемые преобразования выполняются в PostgreSQL.

Для продолжения работы в новом чате сначала используйте
[`docs/new_chat_handoff.md`](docs/new_chat_handoff.md): он содержит готовый
порядок чтения материалов, анализа, проектирования, проверки данных и
финального handoff.

Сырые регистры находятся на VM-1, компактная база витрин — на VM-2. Полная реплика источника не создаётся: извлечение ограничивается необходимыми колонками и рабочим периодом, ориентировочно последними 2–3 годами после уточнения требований каждого отчёта.

Bootstrap завершён. Это README не хранит оперативный статус, разрешения или
состав текущего пакета: их единственный источник — `AGENTS.md`,
`.agents/project_stage_gate.tsv`, `.agents/report_checkpoint_ledger.tsv` и
`.agents/active_package.tsv`.

## Принципы

- Источник 1С не изменяется.
- Сначала требования и source-to-target mapping, затем ADR, data contract и SQL.
- Архитектура выбирается минимально достаточная: прямой `mart`, `stg + mart` или `stg + core + mart`.
- Все утверждения отмечаются как `CONFIRMED`, `ASSUMPTION`, `UNKNOWN`, `BLOCKER` или `DECISION_REQUIRED`.
- Пользователь одобряет полный логический пакет; внутри его scope все нужные
  проверки, документация, SQL, миграции, загрузки и тесты выполняются
  автономно без повторных согласований. Production DDL/DML входят только в
  явно одобренный пакет с reviewed SQL-планом.

## Настройка окружения

1. Скопируйте `.env.example` в локальный `.env`.
2. Заполните два подключения: read-only источник VM-1 и база витрин VM-2.
3. Не коммитьте `.env` и любые выгрузки с чувствительными данными.
4. До исследования БД согласуйте безопасные запросы к metadata/catalog и допустимые схемы.

Примеры конфигурации в `config/` не являются активной production-конфигурацией.

## Процесс первой витрины

1. Заполнить `docs/reports/_template.md`.
2. Предоставить DDL/метаданные источников и примеры обезличенных строк.
3. Создать `docs/mappings/<mart_name>.md`.
4. Зафиксировать архитектуру в `docs/adr/`.
5. Создать `docs/data_contracts/<mart_name>.md`.
6. Только затем добавить раздельные миграции, объект, загрузку, индексы, права, тесты и rollback.

Команды миграций и проверок появятся после подтверждения используемых инструментов и подключения. Порядок production-развёртывания описывается в `docs/08_runbook.md`; сейчас он намеренно содержит блокирующие условия, а не неисполняемые команды.
