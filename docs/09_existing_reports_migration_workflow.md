# Перенос существующих отчётов в компактные витрины

## Цель

Перенести максимально возможную стабильную обработку из исходного SQL и Power Query в PostgreSQL на VM-2, не копируя полные регистры и не создавая отдельную таблицу автоматически для каждого отчёта.

## Однократный вход по проекту

1. Краткий каталог всех отчётов:
   - название и назначение;
   - владельцы/пользователи;
   - исходные таблицы или регистры, если известны;
   - текущий период истории;
   - частота и длительность обновления;
   - примерный объём результата;
   - возможные пересечения с другими отчётами.
2. Инфраструктура:
   - версии PostgreSQL на VM-1 и VM-2;
   - разрешена ли сеть VM-2 → VM-1;
   - доступен ли `postgres_fdw` и разрешено ли его использование;
   - доступные роли и схемы;
   - допустимое окно и механизм запуска refresh;
   - CPU/RAM/disk обеих VM.
3. Политика истории:
   - с апреля по декабрь — с начала предыдущего года;
   - с января по март — с начала года, предшествующего предыдущему;
   - нужны ли отдельным отчётам исключения;
   - правила закрытых периодов и изменений задним числом.

## Пакет одного отчёта

Этот список задаёт полный scope логического пакета, а не последовательность
пользовательских согласований. До старта согласуются все применимые пункты,
ожидаемый результат, опасные операции и критерий закрытия; затем агент
самостоятельно выполняет включённые подшаги без возврата за разрешением на
каждый запрос, файл, миграцию или тест.

- исходный SQL без секретов;
- полный M-код всех Power Query, включая параметры и порядок шагов;
- DAX-меры и вычисляемые столбцы;
- список таблиц модели, связей, кардинальностей и направлений фильтрации;
- визуалы/поля, которым нужна детализация;
- текущие строки результата, размер и время refresh;
- контрольные значения с периодом, фильтрами и единицами;
- известные правила исключения, удалённых и непроведённых документов;
- при возможности `.pbit`, обезличенный `.pbix` или скриншоты модели.

Пароли, connection strings с секретами и полные выгрузки сырых данных не передавать.

## Итерация по отчёту

1. Восстановить lineage `источник → SQL → Power Query → модель/DAX → визуал`.
2. Зафиксировать гранулярность и минимальную детализацию, нужную всем визуалам отчёта.
3. Разделить преобразования:
   - PostgreSQL: фильтры, очистка, типы, крупные `JOIN`, стабильные вычисления и агрегации;
   - DAX: интерактивные расчёты, зависящие от filter context;
   - Power Query: только лёгкое подключение и технические параметры.
4. Создать source-to-target mapping.
5. Выбрать минимальный объект и механизм межсерверного обновления.
6. Реализовать и сверить с контрольными значениями существующего отчёта.
7. Зафиксировать фактические общие сущности и расчёты.
8. При завершении бизнес-разбора показать пользователю актуальный список всех оставшихся договорных отчётов.

## Повторное использование

При следующем отчёте сначала сравнить:

- гранулярность;
- смысл и формулы показателей;
- ключи и измерения;
- временные правила;
- фильтры проведения/удаления;
- требуемую детализацию.

При полном совпадении использовать существующую витрину. При частичном совпадении выделять общий объект только если это уменьшает реальное дублирование. При различной гранулярности сохранять отдельные факты.
