# Инвентаризация источников

Инвентарь существующих отчётов создан в `docs/reports/report_inventory.md`. Он подтверждает бизнес-области и назначение отчётов, но не подтверждает исходные таблицы, ключи или связи.

Для первого отчёта получены текущие запросы. Их source inventory и риски находятся в `docs/reports/client_base_query_review.md`, предварительный mapping — в `docs/mappings/client_base.md`.

Для «Отчета по ИП» сохранены бизнес-описание, две ветви SQL/M, DAX и изображения. Разбор находится в `docs/reports/ip_report_query_review.md`, mapping — в `docs/mappings/ip_training.md`. Источник `InfoRg7006` и обе документные ветви совпадают с показателем ИП в отчёте «Посещения Физкульт».

Для «Загрузки ОП» сохранены бизнес-описание, SQL/M, DAX, пять изображений и metadata-поля CRM. Разбор находится в `docs/reports/sales_team_workload_query_review.md`, mapping — в `docs/mappings/sales_interactions.md`. Два внешних Excel-файла нормативов времени пока не получены.

Для «Продажи детских пакетов» сохранены два DOCX, текстовые копии и пять визуалов. Бизнес-разбор завершён. Разбор находится в `docs/reports/children_packages_sales_query_review.md`, mapping — в `docs/mappings/children_package_sales.md`. Metadata подтверждает строку дополнительных пакетов чека, регистр расчётов и ключи строк, но текущий SQL их не использует полностью; точная связь суммы, номенклатуры и возврата остаётся технической проверкой.

Для «Выручки ДПФУ» сохранены два DOCX, текстовые копии и десять визуалов; бизнес-разбор завершён. Разбор находится в `docs/reports/dpfu_revenue_query_review.md`, mapping — в `docs/mappings/dpfu_revenue.md`. Основные источники факта — `AccumRg7575`, `AccumRg7646`, `AccumRg7370`; количество ИП повторно использует общий факт на `InfoRg7006`, а текущий план использует только сумму `InfoRg6612.Fld6620`. Бюджеты и классификатор остаются внешними.

Для «Карты администратора» сохранены два DOCX, текстовые копии и два визуала;
бизнес-разбор завершён. Gymmy использует `InfoRg5836` (`ЖР_СКУД`), из
которого исключаются строки с `Успех = 0`; второй источник — внешние
Excel-файлы администраторов. Текущий полный список содержит 12 карт и
расширяется вручную при открытии клуба. Разбор находится в
`docs/reports/administrator_card_query_review.md`, mapping — в
`docs/mappings/administrator_card.md`.

Для «Записей администраторов» сохранены бизнес-описание, текущие SQL/M/DAX и
два визуала; бизнес-разбор завершён. Две ветви используют
`Document283/Document279/Document312` и
`Document329/Document313/AccumRg7575`, а автор записи проверяется через
`InfoRg6291`. `AccumRg7575` пересекается с общим фактом «Выручки ДПФУ», поэтому
его отдельная копия отклонена; обе ветки используют `Fld7586`. Разбор находится в
`docs/reports/administrator_bookings_query_review.md`, mapping — в
`docs/mappings/administrator_bookings.md`, решение — в
`docs/adr/0004-administrator-bookings-from-shared-dpfu.md`.

Для «Выручки рецепции» сохранены бизнес-описание пяти страниц, текущий SQL/M и
десять визуалов. Факт использует `AccumRg7575` и `AccumRg7646`, уже известные
по «Выручке ДПФУ», но с рецепционным scope и продавцом. План остаётся внешним
Excel; переданы DAX накопительных показателей, KPI и прогноза. Разбор находится в
`docs/reports/reception_revenue_query_review.md`, mapping — в
`docs/mappings/reception_revenue.md`, решение — в
`docs/adr/0005-shared-ancillary-revenue.md`, контракт — в
`docs/data_contracts/reception_revenue.md`. Бизнес-разбор завершён; SQL и
проверки на БД отложены до технической валидации.

Для «Отчета по %Renew» сохранены исходный DOCX, текст, десять изображений и
переданный M/SQL подсчёта посещений. PostgreSQL сейчас предоставляет только
`COUNT(*)` движений `AccumRg7575` по коду контракта; факты Renew, рекарринга и
планы остаются существующими выгрузками 1С. Metadata подтверждает даты и срок
действия `Reference59`. Разбор находится в
`docs/reports/renew_rate_query_review.md`, требования — в
`docs/reports/renew_rate.md`, mapping контрактных метрик — в
`docs/mappings/renew_contract_usage.md`, архитектурное решение — в
`docs/adr/0006-renew-contract-usage.md`, контракт Power BI — в
`docs/data_contracts/renew_contract_usage.md`. Бизнес-разбор завершён;
реализация отложена до технической валидации.

Для «Управления продлением» сохранены два DOCX, текстовые копии и три
изображения. Основной набор имеет grain одного заканчивающегося контракта;
текущая модель отдельно загружает контракты, посещения, цену, рейтинг, стаж и
последнее взаимодействие и связывает их цепочкой `1:1`. Разбор находится в
`docs/reports/renewal_management_query_review.md`, требования — в
`docs/reports/renewal_management.md`, mapping — в
`docs/mappings/renewal_management.md`. Excel-выгрузки `%Renew` не являются
источником этого отчёта: оба показателя рассчитываются по текущему справочнику
абонементов, без снимков и дублирования строк по месяцам. Архитектурное решение
— `docs/adr/0007-renewal-management-current-state.md`, контракт Power BI —
`docs/data_contracts/renewal_management.md`. Бизнес-разбор завершён.

Получена и сохранена в проекте metadata-структура 1С [`docs/source_metadata/Структура хранения базы данных.txt`](source_metadata/Структура%20хранения%20базы%20данных.txt). Контрольная сумма SHA-256: `9e82c7067596cf9cf1ef8dd890c51914f9af2d9399edd9b994d35c4a48999058`. Правила хранения и происхождение: [`docs/source_metadata/README.md`](source_metadata/README.md).

Для объектов первого отчёта metadata подтверждает логические назначения, поля и заявленные индексы; фактические PostgreSQL-типы, размеры и физические имена с `_`/`X1` ещё требуют проверки через `pg_catalog`.

Для каждой таблицы фиксировать: база/схема/таблица, назначение и доказательство, колонки и типы, примерный объём, диапазон дат, первичный/естественный ключ, уникальность, возможные связи и их кардинальность, технические поля 1С, удаление/проведение, дата создания/изменения и признак актуальности.
