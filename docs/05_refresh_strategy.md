# Стратегия обновления

Для каждой витрины выбрать ровно один подтверждённый режим: полная перестройка, инкремент по изменению, инкремент по ID, скользящее окно, пересчёт изменяемого периода или гибрид.

Перед выбором установить:

- надёжность watermark;
- изменения задним числом и старых записей;
- удаления, исправления и непроведённые документы;
- изменения справочников и закрытых периодов;
- согласованность изменений нескольких регистров;
- SLA и допустимую задержку.

Текущий режим: `DECISION_REQUIRED`; фиктивный инкремент запрещён.

## Ограничения двух ВМ

- Первичная загрузка не должна извлекать 15-летнюю историю.
- Дата начала извлечения должна попадать в удалённый SQL-предикат, а не применяться после передачи данных.
- Если надёжного поля изменения нет, предпочтителен пересчёт ограниченного окна, а не фиктивный инкремент.
- При `postgres_fdw` необходимо доказать pushdown фильтров и агрегации фактическим `EXPLAIN`.
- При отдельной задаче загрузки исходный `SELECT` должен возвращать только необходимые поля и период.
- Удаления и поздние исправления требуют отдельного подтверждённого механизма.

## Подтверждённая политика истории

Граница зависит от даты запуска:

- с 1 апреля по 31 декабря: хранить данные с 1 января предыдущего года по конец текущего года;
- с 1 января по 31 марта: дополнительно сохранять весь год, предшествующий предыдущему, то есть статистику за оба предыдущих года и текущий период.

Пример: 15 февраля 2027 года нижняя граница — 1 января 2025 года; 1 апреля 2027 года — 1 января 2026 года. Верхняя граница для SQL задаётся исключающим `1 января следующего года`, чтобы корректно включать timestamp 31 декабря. Наличие будущих строк/планов внутри текущего года определяется конкретным отчётом.

## Предлагаемое окно повторного расчёта

Изменения задним числом обычно происходят в пределах двух месяцев. До измерения фактического максимума использовать `PROPOSED` безопасную нижнюю границу пересчёта: начало месяца, наступившего за два месяца до текущего. Это текущий месяц плюс два полных предыдущих календарных месяца.

Для каждого refresh:

1. перечитать это окно с VM-1;
2. атомарно заменить или выполнить идемпотентный upsert соответствующего окна на VM-2;
3. обработать исчезнувшие/удалённые строки;
4. не пересчитывать остальную историю без причины;
5. несколько запусков в день выполнять последовательно.

Точная достаточность окна остаётся `ASSUMPTION` до проверки реальных максимальных дат исправлений.

## Подтверждённые частоты отдельных отчётов

- «Посещения Физкульт» — один раз в день.
- «Посещения Пушкинский» — один раз в день.
- «Отчет по ИП» — один раз в день.
- «Загрузка ОП» — каждые два часа с 08:00 до 22:00.
- «Продажа детских пакетов» — один раз в день.
- «Выручка ДПФУ» — один раз в день.
