# ADR-0006: компактные метрики использования контрактов для %Renew

- Статус: `TECHNICAL REVIEWED — CU-TR-001 / PHYSICAL ADMISSION BLOCKED BY FINALIZATION AUTHORITY`
- Дата: 2026-07-28
- Отчёт: № 17 «Отчет по %Renew»

## Контекст

Факты Renew, рекарринга и планы уже поступают в Power BI из выгрузок 1С.
PostgreSQL нужен только для количества посещений по контракту и двух
коэффициентов использования.

Закрытый месяц сохраняется отдельным Excel-снимком и больше не изменяется.
Отчёт должен обновляться ежедневно для текущих и будущих окончаний. При этом
исторические Excel-строки должны продолжать находить контрактные метрики.

Полная копия `AccumRg7575` на VM витрин запрещена. Общий
`mart.visit_client_day` не подходит: он намеренно не хранит контракт и
схлопывает события до клиента-дня.

## Рассмотренные варианты

1. Читать сырой регистр из Power BI — отклонено из-за объёма и тяжёлых joins.
2. Расширить `mart.visit_client_day` контрактом — отклонено: изменит grain и
   увеличит общий факт ради одного потребителя.
3. Хранить отдельный снимок на каждый день — отклонено как лишний объём.
4. Одна компактная строка на контракт с immutable/mutable-секциями — выбрано.

## Решение

Предлагаемый объект:

> `mart.contract_usage`.

Тип — физическая таблица на VM-2. Power BI читает её в режиме `Import`.

Гранулярность:

> один контракт.

Технический ключ в target:

> `contract_id = encode(Reference59.ID, 'hex')::text`.

Существующая интеграция Power BI продолжает использовать `contract_code`, пока
его уникальность не проверена либо выгрузка 1С не начнёт передавать
`contract_id`.

Таблица хранит только:

- ID и код контракта;
- даты начала и окончания;
- месяц окончания;
- срок действия в днях;
- число активных календарных месяцев;
- количество посещений;
- коэффициент использования;
- среднемесячные посещения;
- технические признаки финализации.

Клиентские персональные данные, сырые посещения, Renew, рекарринг и планы не
переносятся.

## Обновление

Поток:

> source-side агрегация на VM-1 → временный объект загрузки на VM-2 →
> атомарное обновление `mart.contract_usage` → Power BI Import.

Каждый день:

1. строки уже закрытых месяцев не изменяются;
2. текущие и будущие контракты полностью пересчитываются из источника;
3. mutable-секция `mart.contract_usage` заменяется атомарно;
4. Power BI обновляется после успешной замены.

При закрытии месяца (после отдельного operational decision, задающего
`mutable_from_month`):

1. выполняется последнее обновление посещений и сроков контрактов этого месяца;
2. строки получают `is_finalized = true` и `finalized_month`;
3. после этого соответствующий Excel-снимок используется как неизменяемый;
4. финализированные строки больше не обновляются.

Это не watermark-инкремент. Граница изменяемости определяется подтверждённым
бизнес-процессом закрытия месяца.

Хранится только история, которая требуется подключённым Excel-снимкам и общей
проектной политике периода; 15-летняя история не переносится.

## Подсчёт

- посещения отбираются внутри полного интервала контракта;
- текущая формула совместимости — `COUNT(*)`;
- перед реализацией она сравнивается с уникальными документами и ресурсом
  количества;
- срок действия берётся из `Reference59.Fld693`;
- календарные месяцы считаются inclusive;
- деление на ноль возвращает `NULL`.

## Слои

Постоянные `staging` и `core` не создаются. Используется только временный
загрузочный объект и одна физическая таблица `mart`.

Отдельный report-specific view не нужен: контрактный набор уже соответствует
требуемой гранулярности Power BI.

## Граница PostgreSQL и Power BI

PostgreSQL выполняет:

- отбор валидных посещений;
- связь с контрактом;
- ограничение интервалом контракта;
- подсчёт посещений, дней и календарных месяцев;
- расчёт строковых коэффициентов для сегментации;
- финализацию закрытого месяца.

Power BI:

- сохраняет существующую модель Renew и Excel-источники;
- использует русскую таблицу `Использование контрактов`;
- связывает её с контрактными снимками по коду контракта;
- не суммирует коэффициенты;
- рассчитывает Renew, планы, дефициты и сравнения в DAX.

## Повторное использование

«Управление продлением» является вероятным потребителем, но его grain и
правила ещё не разобраны. Нейтральное доменное имя объекта позволяет
переиспользование без создания второй таблицы. Расширение колонок допускается
только после подтверждённого mapping второго отчёта.

## Последствия

- переносится одна строка на контракт вместо движений посещений;
- исторические Excel-снимки не теряют показатели использования;
- ежедневно пересчитывается только небольшая mutable-секция;
- архитектура существующего отчёта и внешние выгрузки не меняются;
- общий client-day факт не раздувается контрактным измерением.

## Блокеры перед реализацией

1. Уникальность `Reference59.Code` и существующей связи Power BI.
2. Полиморфный тип `AccumRg7575.Fld7578`.
3. `COUNT(*)` против unique document и `SUM(Fld7585)`.
4. `Active`, `Posted`, `Marked`, сторно и отмены.
5. Физический тип и единица `Reference59.Fld693`.
6. Один контракт фиксируется только в одном закрытом месяце.
7. Порядок последнего refresh и сохранения Excel на границе месяца.
8. Контрольный контракт через границу года и контракт с заморозкой.
9. Фактический объём и время ежедневного source-side запроса.
10. Named operational authority, которая передаёт runner'у
    `mutable_from_month`; SQL не выводит его из Excel или времени сервера.

## Условия пересмотра

- код контракта не уникален — добавить стабильный ID в выгрузку 1С либо
  согласованный составной ключ;
- контракт может повторно фиксироваться в другом месяце — перейти к grain
  `месяц снимка × контракт` и изменить связь Power BI;
- «Управление продлением» требует другой grain — общий объект не расширять
  скрыто, а пересмотреть архитектуру после mapping;
- ежедневный полный пересчёт mutable-секции не укладывается в SLA — выбирать
  инкремент только после доказанного watermark.

## Stage 2 evidence — SV-082

На bounded current-PBI path 133 legacy count-строки совпали с 133 physical
keys и 133 документами; `SUM(Fld7585)=133.00`. Для 100 контрактов через
границу 2025–2026 15 034 из 16 089 in-interval событий лежат вне legacy
2026-окна. Это подтверждает риск методического улучшения, но BR-018 сохраняет
current `COUNT(*)` и годовой фильтр первого релиза. `Fld693` физически numeric,
но не может быть заменён календарной разницей дат без отдельного решения.

## CU-TR-001 — Stage 3 technical review

Точный parameterized extract, независимые CU-S01--CU-S03, DDL, source-first
atomic runner и target reconciliation подготовлены локально. Short actual plan
на `[2026-08-17, 2026-08-24)` вернул 31,788 target-grain rows за 1,505.871 ms,
shared hit 1,060,722, без read/temp I/O. CU-S01 нашёл один observed
polymorphic pair `08/0000003b`, ноль duplicate technical keys и нулевые
inactive/unposted/marked rows; CU-S02 нашёл ноль duplicate contract-code
groups. Это evidence sample, не замена full fixed-window pre-COPY controls.

Runner требует явные `legacy_start`, `legacy_end`, `mutable_from_month` и
`max_transfer_bytes`; target connection, DDL/DML/COPY в этом review не
выполнялись. `mutable_from_month` не имеет physical source marker и остаётся
admission blocker до named operational authority.
