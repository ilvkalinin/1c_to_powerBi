# ADR-0003: Общий компактный слой посещений

- Статус: `DESIGNED / STAGE_2 SOURCE VALIDATION PARTIALLY VALIDATED — SV-070, SV-071 / IMPLEMENTATION DEFERRED`
- Дата: 2026-07-24
- Отчёты-основания: «Посещения Физкульт», «Посещения Пушкинский»

Ревизия 2026-08-03: данные ИП окончательно вынесены в отдельный общий
`mart.ip_training_daily` по ADR-0025. `mart.visit_client_day` не содержит
количество ИП. Это устраняет смешение grain и завершает требуемую ревизию;
техническая валидация обоих продуктов остаётся обязательной.

## Контекст

Оба отчёта используют одни и те же основные источники посещений, предварительной записи, групповых занятий, абонементов, клубов и услуг. Создание отдельных копий под каждый отчёт дублировало бы события, client key и правила классификации.

При этом полностью дневной агрегат `дата × клуб` недостаточен: показатели общего посещения, купонов, ДПФУ и категорий Пушкинского используют `DISTINCTCOUNT` клиента за произвольный фильтр-период. Сырые события избыточны: повторные строки одного клиента в один день не нужны для этих distinct-показателей.

## Рассмотренные варианты

1. Отдельная таблица на каждый отчёт — отклонено из-за дублирования источников и логики.
2. Полная копия движений посещений и продаж — отклонено из-за объёма и лишних колонок.
3. Только дневные количества — отклонено: не воспроизводит distinct клиента в итогах произвольного периода.
4. Общий обезличенный client-day факт плюс один общий дневной агрегат клуба — выбранное направление.

## Решение

### Общий client-day факт

Предлагаемый физический объект: `mart.visit_client_day`.

Гранулярность:

> дата события × фактический клуб × стабильный обезличенный клиент.

Логический ключ:

> `(visit_date, visit_club_id, client_key)`.

Хранить только необходимые признаки:

- наличие обычного посещения;
- посещение действующим членом Пушкинского;
- купон;
- ДПФУ;
- гостевой визит;
- VIP;
- ДРЦ без Продлёнки и Умняшек;
- Продлёнка;
- Умняшки.

Несколько сырых событий одного клиента внутри ключа схлопываются. Межкатегорийные пересечения сохраняются намеренно. Сырые услуги, документы, ФИО, исходный client ID и абонементы на VM-2 не переносятся.

### Общий дневной агрегат клуба

Предлагаемый объект: `mart.club_day_metrics`.

Гранулярность:

> дата × клуб.

В одной строке хранить только необходимые дневные показатели:

- сумму `КоличествоПосетивших` ГП для используемых клубов;
- всего членов;
- посетили клуб сегодня;
- активные за `[D-30,D)`, не посетившие D;
- неактивные.

Показатели клиентской базы рассчитываются сначала только для Пушкинского; для остальных клубов соответствующие колонки остаются `NULL`, а не фиктивным нулём. ГП и состояние КБ допустимо объединить, поскольку у них одинаковые grain, календарь и refresh. Смешивание этих значений с client-day строками запрещено.

Набор можно расширять показателями только при подтверждённом потребителе. Он не заменяет демографический снимок `mart.client_base_snapshot`, потому что имеет другую частоту и другую гранулярность.

### Справочники

Переиспользовать один малый справочник клубов и один календарь. Не создавать отдельные справочники для каждого отчёта.

## Слои

Выбран минимальный поток:

> read-only source query на VM-1 → временный загрузочный объект на VM-2 → физические таблицы `mart`.

Постоянные `staging` и `core` пока не создавать. Общая бизнес-логика реализуется один раз в source-side запросе каждого общего объекта.

## Почему физические таблицы

- VM источника и VM витрин разделены;
- Power BI должен читать локальный компактный набор;
- вычисления distinct и классификация не должны повторяться при каждом чтении;
- ежедневное обновление допускает атомарную замену ограниченного периода.

Окончательное решение о транспортном механизме и DDL откладывается до подключения и измерений.

## Обновление

- частота посещенческих отчётов — один раз в день;
- первичная загрузка — только период по общей календарной политике;
- регулярный кандидат — пересчёт изменяемого окна около двух месяцев;
- старые даты не перестраивать без основания;
- точный watermark не назначать до проверки source metadata и поздних исправлений;
- задания разных тяжёлых объектов не запускать параллельно на VM-2.

## Power BI

Пользовательские таблицы называются по-русски:

- `Посещения клиентов`;
- `Показатели клуба по дням`;
- `Календарь`;
- `Клубы`;
- отчётные таблицы мер.

PostgreSQL выполняет joins, классификацию, схлопывание до client-day и дневные группировки. DAX выполняет filter-dependent `DISTINCTCOUNT`, суммы готовых значений, проценты и композиционные меры.

## Последствия

- два отчёта не создают две копии посещений;
- показатели ГП и состояния КБ с одинаковой гранулярностью не создают две отдельные таблицы;
- сохраняется точный distinct по произвольному периоду;
- объём существенно меньше сырых движений;
- добавление нового флага допускается только при подтверждённом потребителе;
- client key должен быть стабильным между датами, клубами и refresh, но не раскрывать исходный идентификатор.

## Выполненная ревизия после «Отчета по ИП»

`Посещения ИП` нельзя окончательно хранить как агрегированное поле client-day:

- отчёт ИП должен раскрывать сотрудника, услугу и код клиента;
- один клиент может иметь несколько тренировок в один день;
- один client-day не сохраняет эту детализацию;
- отдельный подсчёт в client-day дублировал бы те же строки и правила отбора.

Решение — единый компактный `mart.ip_training_daily` с grain
`дата × клуб × сотрудник × клиент × услуга` и количеством тренировок, из
которого также суммируется показатель «Посещения ИП». Подробности и блокеры
реализации зафиксированы в ADR-0025.

## Открыто перед SQL

- способ создания стабильного обезличенного client key;
- статусы `Active`, `Posted`, `Marked` и enum;
- фактические кардинальности join;
- контрольные значения;
- планы и размеры источника;
- транспорт между VM;
- временный ключ и кардинальности источника общего факта тренировок ИП.

Единое бизнес-правило границ подтверждено: снимок на 00:00 D использует `active_from < D` и `active_to >= D−1`.
