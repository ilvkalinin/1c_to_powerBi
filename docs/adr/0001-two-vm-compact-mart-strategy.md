# ADR-0001: Компактные витрины на отдельной ВМ без полной копии источника

- Статус: `PROPOSED`
- Дата: 2026-07-23
- Владельцы: пользователь / основной агент

## Контекст и подтверждённые факты

- `CONFIRMED`: сырые регистры 1С находятся в PostgreSQL на VM-1.
- `CONFIRMED`: база витрин создаётся на VM-2.
- `CONFIRMED`: полная копия сырых таблиц нежелательна из-за объёма и сетевого обмена.
- `CONFIRMED`: рабочий горизонт ориентировочно 2–3 года вместо 15 лет.
- `CONFIRMED`: существующие SQL и Power Query являются входом для восстановления текущей логики отчётов.
- `CONFIRMED`: источник PostgreSQL 19 мощнее целевой Windows VM с PostgreSQL 18.3, 8 vCPU и 8 ГБ RAM.
- `CONFIRMED`: на VM-2 сейчас свободно 172 ГБ; часть пространства занята прежними тестовыми выгрузками.
- `CONFIRMED`: refresh ежедневный, для части отчётов — несколько раз в день, запуск через Windows Task Scheduler.
- `CONFIRMED`: изменения задним числом обычно укладываются примерно в два месяца.

## Рассмотренные варианты

1. Полная реплика сырых таблиц на VM-2 — отклонена: лишнее хранение и передача истории.
2. Удалённое чтение всех сырых данных при каждом refresh Power BI — отклонено как целевой вариант: нагрузка на сеть/источник и нестабильное время.
3. Фильтрация и доступная агрегация на VM-1 с хранением компактных витрин на VM-2 — предлагаемый вариант.
4. Частичный технический buffer на VM-2 — допустим только для конкретных колонок/периода, если он доказан повторным использованием, инкрементом или восстановлением после сбоя.

## Предлагаемое решение

Строить витрины итеративно от существующих отчётов. Из VM-1 извлекать только необходимые колонки и строки согласованного горизонта, по возможности уже отфильтрованные и агрегированные. На VM-2 хранить конечные факты/измерения и только доказанно полезные промежуточные объекты.

Предпочтительное направление для проверки: выполнять итоговый read-only SQL на мощной VM-1 и потоково загружать его компактный результат на VM-2 по расписанию. `postgres_fdw` рассматривать только после доказательства pushdown и совместимости версий.

Не закреплять соответствие «один отчёт = одна физическая таблица». Повторно использовать витрину при совпадающих grain и семантике; выделять общий объект после появления подтверждённого второго потребителя.

## Последствия

- Сокращаются сетевой трафик и хранение на VM-2.
- Power BI получает локальные компактные объекты.
- Изменение существующей логики отслеживается через mapping SQL/M/DAX → PostgreSQL.
- Требуется корректный механизм поздних исправлений и удалений.

## Риски

- Не все операции могут быть протолкнуты на VM-1 выбранным транспортом.
- Слишком ранняя агрегация может убрать детализацию, нужную визуалам или DAX.
- Окно 2–3 лет может быть недостаточно отдельным отчётам.
- Исторические изменения вне окна могут остаться незамеченными без подтверждённого watermark.
- При восьми vCPU и восьми ГБ RAM параллельные загрузки и большие временные таблицы могут создать давление на память.
- Доступный диск нельзя считать полностью доступным проекту до инвентаризации старых выгрузок.

## Условия принятия решения

- Выбран и проверен безопасный транспорт между ВМ.
- Реализована календарная политика истории из `docs/05_refresh_strategy.md`.
- Измерены объёмы и фактический pushdown/время выполнения.
- Определены правила поздних изменений и удалений.

## Условия пересмотра

- Появление отчёта с большей историей.
- Недостаточная производительность source-side запросов.
- Повторное использование одинаковых сырых срезов несколькими витринами.
- Изменение сетевой или security-политики.
