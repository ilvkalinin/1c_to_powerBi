# ADR-0004: Записи администраторов из общего факта ДПФУ

- Статус: `PROPOSED / STAGE 2 PARTIALLY VALIDATED — SV-086 / STAGE 3 APPROVAL REQUIRED`
- Дата: 2026-07-27
- Отчёт: № 19 «Записи администраторов»

## Контекст

Отчёт показывает фактическую выручку оказанных услуг, на которые клиентов
записали администраторы. Обе документные ветки должны использовать
`AccumRg7575.Fld7586`. Регистр велик, находится на мощной исходной VM и уже
используется общим логическим фактом ДПФУ.

Полная копия `AccumRg7575` на VM витрин противоречит требованиям проекта.
Отдельная выгрузка тех же движений для одного отчёта продублирует выручку и
правила состояний.

## Рассмотренные варианты

1. Копия сырых строк `AccumRg7575` под отчёт — отклонена из-за объёма и
   дублирования.
2. Отдельная физическая таблица отчёта напрямую из источника — не выбрана до
   измерений; она повторит часть общего факта.
3. Удалённый view, который Power BI каждый раз читает с VM-1, — отклонён из-за
   повторного сканирования большого регистра.
4. Минимальная атрибуция записи в общем факте ДПФУ и локальный агрегирующий
   view — выбранное направление.

## Решение

Полный регистр не переносится. Поток:

> source-side отбор на VM-1 → временный объект атомарной загрузки → общий
> физический факт оказанных услуг ДПФУ на VM-2 → локальный агрегирующий view
> записей администраторов → Power BI Import.

На VM-1 отбираются только:

- подтверждённый календарный горизонт;
- движения ДПФУ, связанные с одной из двух веток записей;
- необходимые ключи и сумма `Fld7586`.

Общий факт ДПФУ получает минимальную nullable-атрибуцию:

- тип документа записи;
- ID документа записи;
- сотрудник — автор записи;
- должность автора на дату создания записи.

Отображаемые ФИО, клиент, тренер и средняя цена в общий факт не добавляются.
Физическое имя общего факта будет утверждено в отдельном ADR домена ДПФУ.

Предлагаемый объект отчёта:

> `mart.v_administrator_bookings_daily`.

Тип объекта первой версии — обычный локальный view. Отдельная таблица или
materialized view не создаётся без измерений.

## Гранулярность view

> дата занятия × клуб × администратор × должность на дату записи × услуга ×
> нормализованный формат × тип источника.

Логический ключ:

> `(lesson_date, club_id, booking_author_id, author_position_id, service_id,
> training_format_id, booking_source)`.

Показатели:

- количество уникальных документов записи;
- сумма знаковых движений `AccumRg7575.Fld7586`.

Если одному документу соответствует несколько движений, сумма сначала
схлопывается по документу, а документ учитывается в количестве один раз.

## Слои

Постоянные report-specific `staging` и `core` не создаются. Временный объект
нужен только для безопасной загрузки. Роль общего слоя выполняет единый факт
ДПФУ.

Общие измерения: календарь, клубы, сотрудники, должности, услуги и форматы.
Отдельные копии справочников под отчёт запрещены.

## Обновление

- Power BI: `Import`, один раз в день;
- история следует общей сезонной календарной политике проекта;
- надёжный watermark не подтверждён;
- точное окно повторного пересчёта исправлений и отмен определяется после
  проверки источника;
- замена пересчитанного периода должна быть атомарной;
- до доказанного watermark нельзя объявлять Power BI incremental refresh.

## Граница PostgreSQL и Power BI

PostgreSQL выполняет:

- связь двух типов записи с движениями;
- фильтры состояний, отмен и форматов;
- определение должности на дату записи;
- нормализацию формата;
- защиту от размножения суммы;
- агрегацию до целевой гранулярности.

DAX выполняет только суммы готовых показателей и среднюю цену через `DIVIDE`.
Power Query подключается, переименовывает поля на русский и назначает типы.

## Последствия

- единая формула выручки ДПФУ не дублируется;
- большая таблица не копируется целиком;
- отчёт не создаёт вторую физическую копию движений;
- новый атрибут увеличивает общий факт только ключами записи и автора;
- технический тип источника сохраняется скрытым для сверки веток;
- производительность локального view должна быть измерена до материализации.

## Блокеры перед реализацией

1. Доказать ключ связи каждой документной ветки с `AccumRg7575`.
2. Проверить кардинальность и отсутствие размножения суммы.
3. Проверить пересечение `Document283` и `Document329`.
4. Определить приоритет клуба и услуги при расхождении документа и движения.
5. Подтвердить `Active`, `Posted`, `Marked`, отмены, возвраты и сторно.
6. Проверить интервальную уникальность должности на дату записи.
7. Получить контрольные значения и фактические планы выполнения.

AB-V01—AB-V04 выполнены в read-only snapshot: 13 source relations существуют;
обе bounded current-M ветки сохранили уникальный ID документа. 26 из 72
предварительных документов имеют несколько движений, а historical
admin-position отсутствует у 199 из 200 документов и имеет 4 match у одного.
Это не разрешает переход к Stage 3 и не допускает смены кадрового правила или
схлопывания движений без отдельного решения.

## Условия пересмотра

- локальный view не укладывается в измеренный SLA — материализовать только
  итоговый агрегат;
- стабильную ссылку на запись нельзя хранить в общем факте — создать компактный
  booking bridge;
- атрибуция заметно увеличивает общий факт — вынести её в bridge;
- появляется доказанный watermark — перейти к подтверждённому инкременту;
- обнаружены изменения старше рабочего окна — расширить пересчёт либо добавить
  периодическую полную сверку.
