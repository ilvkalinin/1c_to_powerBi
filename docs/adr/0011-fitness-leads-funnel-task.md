# ADR-0011: task-level факт «Воронка. Лиды. Фитнес»

- Статус: `ACCEPTED / STAGE_2 SOURCE VALIDATION PARTIALLY VALIDATED — SV-078 / IMPLEMENTATION DEFERRED`
- Дата: 2026-07-29
- Отчёт: №5 «Воронка лиды фитнес»

## Контекст и подтверждённые факты

Отчёт анализирует созданные CRM-задания четырёх воронок. Его единица расчёта
— одно задание `Reference106.ID`, а не взаимодействие CRM, запись или
тренировка. Outcome-поля имеют фиксированную текущую семантику:

- `has_booking` определяется этапом CRM;
- `training_count` равен единице для трёх этапов «Пришел…», нулю для двух
  ДСУ-воронок вне этих этапов, иначе сумме квалифицированных строк `ДПФУ факт`
  того же клиента за включающий 45-дневный интервал от даты создания задачи;
- `has_paid_training_45d = training_count > 0`;
- услуга берётся из текущего источника задачи либо, при её отсутствии, из
  ранней записи клиента до заданной границы.

Текущий DAX допускает, что одна тренировка относится к нескольким задачам
одного клиента с пересекающимися окнами. Это сохраняется как подтверждённая
семантика, а не устраняется как дубль.

`UNKNOWN — взаимодействия отдела продаж` имеет grain взаимодействия
`Reference67.ID`; факты ИП и ДПФУ имеют grain события/движения. Ни один из
них не заменяет task-level факт без смешения grain.

## Рассмотренные варианты

1. Удалённый `mart`/view напрямую над VM-1 — отклонён: Power BI повторно
   выполнит client/date lookups по CRM, записям и движениям; это увеличит
   нагрузку на источник и сеть.
2. Постоянный `staging + mart` — отклонён: постоянная копия CRM, регистров
   записей или движений для одного подтверждённого потребителя избыточна.
3. `staging + core + mart` с общим CRM task-core — отклонён на текущем
   горизонте: другие будущие потребители task-grain не разобраны.
4. Source-side фильтрация → временный загрузочный объект → компактный
   физический task-level факт на VM-2 — выбран.

Обычный view, materialized view и дополнительные индексы не выбираются без
измерений. Физическая таблица обоснована раздельными VM, повторным
client/date расчётом и необходимостью импортировать компактный результат.

## Решение

После технической валидации создать один физический объект:

> `mart.fitness_leads_funnel_task`

Гранулярность одной строки:

> одно CRM-задание `Reference106.ID`.

Логический ключ: `task_id`; его уникальность и конечное физическое
представление проверяются до реализации.

Поток:

> read-only source-side запрос VM-1 → временный объект одной загрузки VM-2 →
> `mart.fitness_leads_funnel_task` → Power BI Import.

В source-side наборе выполняются только fixed rules из mapping: отбор воронок,
исключение дублей, CRM-классификации, текущие правила этапов, client-code/date
lookups outcome-полей и итоговая услуга. На VM-2 не переносятся сырые
`InfoRg7006`, `AccumRg7575`, `AccumRg7646`, документы записей, клиенты или
сотрудники.

Физический общий CRM core и изменение `UNKNOWN — взаимодействия отдела
продаж` не создаются. Их повторное использование рассматривается только при
доказанном совпадении task-grain будущего отчёта.

## Обновление и история

- История следует BR-003: январь–март — текущий и два предыдущих года;
  апрель–декабрь — текущий и предыдущий год, верхняя граница исключает
  1 января следующего года.
- Обновление выполняется ежедневно; данные доступны не позднее 08:30 по Москве
  (решение пользователя 2026-07-30, BR-014).
- `task_date`, `Period` и даты документов не считаются подтверждённым
  watermark. До проверки изменений/удалений — атомарный полный пересчёт
  согласованного исторического горизонта, а не неподтверждённый инкремент.
- Временный объект существует только в рамках refresh; постоянный staging не
  создаётся.

## Граница PostgreSQL и Power BI

PostgreSQL: source-state filters после их технического подтверждения,
классификация CRM, fixed client-code/date attribution, подсчёт
`training_count`, `has_booking`, итоговая услуга и task-level результат.

Power Query: Import готового факта, типизация и подключение к общим
справочникам; без raw ODBC-запросов, группировок или client/date merge.

DAX: `DISTINCTCOUNT(task_id)`, фильтр-зависимые проценты, ПГ через
`SAMEPERIODLASTYEAR`, MTD/накопительный итог и отображение нулей. Плана нет:
источник, поля, расчёт выполнения и плановые визуалы не входят в отчёт
(решение пользователя 2026-07-30).

## Последствия

- отчёт получает одну строку на задание и не смешивает уровни детализации;
- сохранена текущая многократная атрибуция тренировки пересекающимся окнам;
- расчёт по услуге требует валидации current `1:1` join, иначе контракт
  пересматривается до реализации;
- PII и client code используются source-side, но не обязательны в Power BI
  контракте.

## Риски и условия пересмотра

SV-078 (live read-only, 2026-08-11) подтвердил на bounded cohort 100 задач
без размножения current task-to-service join; 82 задачи не имели raw
client-day match. SV-072 подтверждает технический ключ `InfoRg7006`, но
фиксирует legacy one-to-many `Document329.VT4352`. Это evidence не меняет
current client-code/date attribution или task-grain по BR-018.

1. `Reference141X1.Code` может быть неуникален, изменяем или null; тогда
   client-code attribution нельзя переносить без отдельного решения.
2. Current join услуги по клиенту и дате закрытия может размножить задачу.
3. Не подтверждены source states, удаления, ключи, типы, объёмы и время
   полного пересчёта.
4. При появлении второго отчёта с тем же task-grain и теми же CRM-правилами
   пересмотреть решение на общий core; иной grain не является основанием.
5. При надёжном watermark и измеренном SLA пересмотреть стратегию refresh;
   при невыполнении SLA — только после измерений сравнить компактные агрегаты
   или materialization.
