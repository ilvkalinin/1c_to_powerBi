# ADR-0007: текущая контрактная витрина «Управление продлением»

- Статус: `IMPLEMENTED / Stage 3 VALIDATED — RM-LOAD-001—006`
- Дата: 2026-07-28
- Отчёт: № 16 «Управление продлением»

## Контекст

Отчёт строится только по текущим данным базы. Excel и исторические снимки не
используются. Один исходный абонемент должен присутствовать ровно в одной
строке и относиться к месяцу своей текущей даты окончания.

Текущая Power BI-модель отдельно загружает абонементы, посещения, цены,
рейтинг, стаж и последнее взаимодействие и связывает их цепочкой
двунаправленных `1:1`. Все эти наборы в отчёте используются как атрибуты одной
контрактной строки.

## Решение

Создать один физический объект:

> `mart.renewal_management_contract`.

Гранулярность:

> одна текущая строка на один исходный абонемент `Reference59.ID`.

Логический и технический ключ:

> `expiring_contract_id`.

`contract_end_month` вычисляется из текущей `membership_end_date`. Месяц не
входит в ключ. Если дата окончания изменяется, та же строка переходит в другую
когорту при следующем обновлении. Версии и дубликаты по месяцам не создаются.

## Состав строки

- исходный абонемент, клиент и клуб;
- выбранный следующий абонемент;
- цена покупки;
- количество и показатели использования;
- два Renew-флага;
- даты и длительность возврата;
- текущие рейтинг, стаж, этап воронки и последнее взаимодействие;
- необходимые PII для существующей детальной таблицы.

Отдельные физические таблицы `Посещения`, `Цены`, `Рейтинг`, `Стаж` и
`МаксВзаимодействие` не создаются.

## Два Renew-флага

- `renewed_by_month_close_flag` — дата активации следующего абонемента не
  позднее первого числа после месяца окончания исходного;
- `renewed_current_flag` — дата активации следующего абонемента не позднее
  текущей даты.

Оба флага ежедневно пересчитываются по текущему справочнику. Первый флаг не
является снимком и может измениться после исправления данных источника.

Проценты физически не хранятся. DAX делит сумму соответствующего флага на
distinct исходных абонементов текущей когорты.

## Скорость возврата

PostgreSQL рассчитывает:

> `renewal_lead_lag_days = renewal_activation_date - membership_end_date`.

Отрицательное значение означает досрочное продление, положительное — возврат
после окончания. Для возвратов также предоставляется `return_days`; для
непродлённых значение `NULL`. Основной агрегат Power BI — медиана.

## Повторное использование посещений

Архитектура предыдущего `%Renew` не переносится. Переиспользуются только
mapping и source-side правило агрегации посещений по контракту. Frozen-объект
предыдущего отчёта не подключается.

Сырые `AccumRg7575` на VM витрин не копируются. Контрактный агрегат
посещаемости включается в тот же source-side поток №16.

## Слои и тип объекта

Минимальный поток:

> read-only source-side запрос и схлопывание ветвей до уникального контракта →
> временный загрузочный объект VM-2 → атомарная замена физической таблицы
> `mart`.

Постоянные `staging` и `core` не создаются.

- обычный view отклонён из-за повторения удалённых тяжёлых joins;
- materialized view не даёт преимуществ без измерений;
- физическая таблица выбрана для локального Power BI Import и атомарной
  замены.

## Обновление

- автоматически один раз в день;
- полная атомарная замена всей подтверждённой ограниченной когорты;
- это пересборка компактной контрактной таблицы, не копия регистров;
- watermark не заявляется;
- исчезнувшие, изменённые и перенесённые между месяцами контракты корректно
  отражаются полной заменой;
- при ошибке остаётся предыдущая согласованная версия.

Точные границы истории и будущего окна следуют общей политике проекта и
утверждаются перед SQL.

## Power BI

Power BI использует:

- одну таблицу `Управление продлением`;
- общие справочники `Календарь` и `Клубы`;
- однонаправленные связи `1:*`;
- DAX для процентов, прошлого года, целей, дефицита и медианы.

Цепочка двунаправленных `1:1` удаляется. Визуалы и бизнес-логика отчёта
сохраняются.

## Блокеры перед реализацией

1. Связь исходного и следующего абонемента и детерминированный tie-break.
2. Состояния и удаление исходного/следующего абонемента.
3. Семантика исключений `Document287` и `Document332`.
4. Уникальность ID и кода абонемента.
5. Последние rating/tenure/interaction без размножения.
6. Цена покупки, `Active`, знак и возвраты.
7. Подсчёт посещений и тип полиморфного основания.
8. Единица `Reference59.Fld693`.
9. Границы когорты, типы, объём, время обновления и SLA.
10. Права доступа к ФИО и телефону.

## RM-FULL-DELIVERY-001 outcome (2026-08-29)

Full-population controls confirmed the cohort key, unique cohort codes, latest
rating/tenure cardinality, price and visit technical keys, and required types.
They also found 93 ties at the earliest eligible next-contract start and 96
ties at the latest eligible interaction timestamp (each up to five rows).
Current SQL has no secondary ordering. It would be a methodology change to
invent one, so physical delivery is prohibited pending an explicit BR-018
decision. Evidence: [RM Stage 2 execution](../reports/renewal_management_stage2_full_validation_execution_2026-08-29.md).

User decision BR-050 (2026-08-29) resolves both ties: paid next-contract wins
at the same earliest start, then minimum technical ID; latest interaction uses
minimum technical ID at the same timestamp.  The ID fallback is technical only.
