# Старт нового чата: контекст и обязательный порядок

Этот файл — краткая точка входа для нового чата. Он не заменяет `AGENTS.md`,
каталоги, ledger/gate и артефакты конкретного отчёта; при расхождении приоритет
имеют `AGENTS.md`, подтверждённое решение пользователя и доказательство в
исходном материале. Текущий разрешённый scope всегда определяется
`.agents/project_stage_gate.tsv` и `.agents/report_checkpoint_ledger.tsv`, а
не историческими статусами в этом документе.

## Что прочитать до действий

1. `AGENTS.md`.
2. Этот файл.
3. `docs/00_project_context.md`.
4. `docs/catalogs/source_objects.md`, `docs/catalogs/data_products.md`,
   `docs/catalogs/business_rules.md`.
5. `docs/reports/contract_scope.md`.
6. Для нового отчёта: `docs/mappings/_template.md`, связанные mapping, ADR и
   data contracts, найденные через каталоги.

Не читать исходники других отчётов без явной ссылки из каталога или артефакта
текущего отчёта.

## Правила анализа

- Полный SQL, Power Query M, DAX, модель Power BI и предоставленное
  бизнес-описание — первичные доказательства текущей логики.
- Правило, однозначно записанное в них, имеет статус `CONFIRMED`. Не задавать
  пользователю повторный вопрос и не предлагать альтернативы «на всякий
  случай».
- Вопрос допустим только при конкретном расхождении внутри отчёта, с уже
  подтверждённой логикой другого отчёта или при отсутствии доказательства.
  Вопрос должен назвать текущее правило, источник расхождения, возможную
  альтернативу и влияние выбора.
- Гранулярность факта определяет все меры. Нельзя менять единицу KPI из
  удобства DAX или автоматически агрегировать строки до другого grain.
- Если к контракту относятся взрослый и ребёнок, а grain отчёта —
  `клиент × контракт`, они являются разными единицами расчёта; посещения и
  категория `4+` не объединяются между ними.
- Для отчётов «Вовлечение новичков» и «Вовлечение новичков Второй месяц» это
  подтверждённая текущая норма. Их respective grains:
  `контракт × клиент × контрольная точка` и
  `контракт × клиент × месяц вовлечения`.
- Детские пакеты входят в обе модели через строку
  `Document346.VT4913`; клиентом факта служит ребёнок. Нельзя создавать для
  них отдельный отчётный факт, если они разделяют бизнес-семантику основного.

## Полный маршрут работы по новому отчёту

До начала подготовить и согласовать один полный логический пакет: цель,
отчёты/объекты, этап, все ожидаемые проверки и артефакты, опасные операции,
границы автономной работы и критерий закрытия. После согласования агент
выполняет все включённые подшаги самостоятельно и не возвращается за
подтверждением отдельных SQL, тестов, файлов, миграций или загрузок.

1. Извлечь и сохранить доказательства из предоставленных документов:
   бизнес-описание, полный SQL, M, DAX, связи Power BI, изображения/страницы
   и контрольные значения.
2. Создать или обновить `docs/reports/<report>.md` и
   `docs/reports/<report>_query_review.md`: бизнес-вопрос, показатели,
   фильтры, интервалы, grain каждого набора, связи модели, тяжёлые и
   дублирующиеся преобразования.
3. Создать mapping по актуальному шаблону. Каждая будущая колонка должна
   иметь источник, преобразование, тип, NULL-политику, grain, статус,
   доказательство и тест. Обязательно заполнить `Reuse review` в порядке
   `REUSE → EXTEND → intermediate → NEW`.
4. Сравнить продукт с каталогами и существующими фактами по источникам,
   ключам, grain и бизнес-семантике. Не создавать объект только из-за другого
   имени Power Query.
5. После подтверждения архитектурного решения оформить ADR и data contract:
   один точный grain, ключ, объект, слои, refresh, история, Power BI-связи,
   типы, аддитивность и граница PostgreSQL / Power Query / DAX.
6. До SQL выполнить или подготовить read-only проверку данных. Для каждого
   теста заранее зафиксировать ожидаемый результат. Проверить metadata и
   типы, объём, ключи, NULL, дубли, orphan, кардинальности joins, даты и
   границы интервалов, состояния, суммы/количества, повторный запуск,
   изменения/удаления, план и Power BI-контракт.
7. Обязательно провалиться в узкие контрольные случаи: границы периода,
   один контракт с несколькими клиентами, детский пакет, ties в ранжировании,
   as-of историю, несколько заморозок, сотрудника на граничной дате,
   посещение ровно на границе и строки с отсутствующими ссылками.
8. Если доступа к данным нет, не придумывать результат проверки. Оформить
   конкретную непроведённую проверку и её ожидаемый результат; не создавать
   production SQL, DDL или DML без явного разрешения.

## Текущий проектный статус

- Договорный список и его актуальные статусы: `docs/reports/contract_scope.md`.
- Отчёт №2 «Вовлечение новичков»: архитектура `mart.newcomer_engagement_milestone`,
  детские пакеты включены; ключ `(contract_id, client_id, checkpoint_day)`.
- Отчёт №3 «Вовлечение новичков Второй месяц»: отдельный
  `mart.newcomer_engagement_second_month`; ключ
  `(contract_id, client_id, month_of_engagement)`.
- Оба продукта имеют статус `DESIGNED / IMPLEMENTATION DEFERRED / TECHNICAL
  VALIDATION REQUIRED`; SQL не создавался.
- Из 31 договорного отчёта бизнес-анализ начат/завершён по 14; точное число
  оставшихся и перечень всегда брать из `contract_scope.md`, а не из этого
  текста.

## Формат финального handoff

Действующий формат и единственный preflight определены в
`AGENTS.md`, `communication.md` и `final_preflight.md`: `Сделано → Результат →
Дальше` через `scripts/preflight_message.sh`. Handoff разрешён только после
закрытия всего согласованного пакета; его `Дальше` предлагает один следующий
пакет с полным scope и критерием закрытия.

формате `Сделано → Результат → Дальше` через `scripts/preflight_message.sh`.
