# Дизайн-система портала знаний об отчётности и витринах

**Статус:** концепция для первой версии  
**Аудитория:** аналитики, руководители и сотрудники компании  
**Язык:** русский  
**Канал доступа:** браузер во внутренней корпоративной сети, десктоп

## 1. Назначение

Портал — единый справочник корпоративной отчётности. Он отвечает на четыре вопроса:

1. Какой отчёт нужен для конкретного направления?
2. Для какого решения создан отчёт и какие показатели в нём используются?
3. Как рассчитывается показатель, какие фильтры и группировки влияют на него?
4. Из какой витрины берутся данные и какие поля в ней доступны?

Портал не заменяет Power BI, не редактирует отчёты и не является системой заявок. Его задача — объяснять логику и быстро вести пользователя к нужному отчёту.

## 2. Цели и критерии успеха

### Цели

- Сделать поиск отчёта и расшифровки показателей быстрым и предсказуемым.
- Дать новым сотрудникам контекст: какие метрики важны и как на них влиять.
- Снизить число повторяющихся вопросов аналитикам о формулах, фильтрах и назначении отчётов.
- Зафиксировать связь отчёта с витриной данных без перегрузки пользователей техническими деталями.
- Создать основу для регулярного обновления документации и будущей автоматической подготовки черновиков.

### Критерии успеха через 2–3 месяца

- Пользователь находит нужный отчёт или термин за один поиск либо не более чем за два перехода.
- Все 37 отчётов из стартового реестра имеют опубликованную карточку.
- Вопросы аналитикам по уже задокументированным формулам и фильтрам заметно сокращаются.
- У каждой карточки видна дата последнего подтверждения актуальности.

## 3. Пользователи и ключевые сценарии

| Пользователь | Задача | Результат в портале |
|---|---|---|
| Новый сотрудник | Понять, какие показатели связаны с его работой | Находит направление, открывает отчёт, читает назначение и определения метрик |
| Руководитель | Быстро вспомнить смысл плана/факта, фильтров и похожих KPI | Открывает карточку отчёта или термин глоссария |
| Аналитик | Проверить состав метрик, ограничения расчётов и используемую витрину | Видит страницы отчёта, условия расчётов, витрины и список полей |
| Администратор/автор документации | Поддерживать справочник актуальным | Изменяет карточки в Git и публикует новую версию сайта |

## 4. Информационная архитектура

Главный экран содержит только два равноправных входа и одну строку поиска:

```text
Портал знаний
├── Поиск по названиям отчётов, метрик и терминов
├── Отчёты
│   └── Направление → карточка отчёта
└── Глоссарий
    └── Алфавитный список → карточка термина
```

### Раздел «Отчёты»

В каталоге показаны пять направлений: «Фитнес», «Продажи», «Гостеприимство», «Маркетинг» и «Для правления». После выбора направления пользователь видит простой список отчётов с названием и одной строкой назначения.

Отдельные фильтры по ролям или частоте обновления в первой версии не нужны. Основные способы входа — направление и поиск по названию.

### Раздел «Глоссарий»

Глоссарий — алфавитный список утверждённых бизнес-терминов. Он нужен, чтобы не повторять развёрнутые определения в каждом отчёте. Например, в карточке отчёта используется ссылка «Активная база», а в глоссарии хранится единое определение термина.

Термин глоссария не должен скрывать особенности отчёта. Если правило расчёта отличается, это фиксируется отдельной метрикой в карточке соответствующего отчёта.

## 5. Экранная модель

### 5.1. Главная страница

На одном экране:

- название портала и краткое пояснение;
- строка поиска;
- две крупные карточки: «Отчёты» и «Глоссарий»;
- список пяти направлений как быстрые переходы;
- блок «Недавно подтверждённые» или «Обновлено» — опционально, если окажется полезен.

Не следует повторять дизайн внешнего продающего сайта. Порталу подходит нейтральный, строгий внутренний интерфейс с высокой читаемостью и достаточным контрастом.

### 5.2. Карточка отчёта

Карточка строится по принципу «сначала суть, затем детали».

**Верхняя часть (всегда видима):**

- название и направление;
- для чего нужен отчёт;
- кнопка «Открыть отчёт в Power BI»;
- частота обновления;
- дата последнего подтверждения документации.

**Подробности (раскрывающиеся блоки):**

1. **Страницы отчёта.** Название страницы, для какого вопроса она нужна, ключевые визуалы, разрезы/группировки и применяемые фильтры.
2. **Метрики.** Список метрик конкретного отчёта. Каждая раскрывается в определение, понятную бизнес-формулу, единицу измерения и условия/исключения.
3. **Фильтры, группировки и особенности интерпретации.** Общие фильтры, правила план/факт, доступные разрезы, исключаемые группы, период и важные ограничения.
4. **Данные.** Используемые витрины; для каждой — описание и перечень полей. Если внешний источник остаётся в Excel или Google Sheets, выводится ссылка на него.

В первой версии не показываются технические SQL/DAX-формулы, цепочка до систем-источников, обратные связи «витрина → все отчёты» и скриншоты. Скриншоты можно добавить позднее в раздел страниц отчёта.

### 5.3. Карточка метрики внутри отчёта

Метрика существует в контексте одного отчёта. Если одинаково названный показатель рассчитывается по-разному, это разные метрики с уточняющими названиями и разными карточками.

Обязательные поля:

| Поле | Содержание |
|---|---|
| Название | Однозначное название метрики в отчёте |
| Бизнес-определение | Что измеряет показатель и для какого решения нужен |
| Формула | Понятная бизнес-пользователю формула |
| Единица измерения | Рубли, штуки, проценты, клиенты и т. п. |
| Условия расчёта | Фильтры, разрезы/группировки, исключения, статусы, особые правила план/факт |
| Термины | Ссылки на определения в глоссарии при необходимости |

## 6. Контентная модель

### Отчёт

Обязательные поля: идентификатор, название, направление, краткое назначение, ссылка Power BI, частота обновления, дата последнего подтверждения, список страниц, список метрик, список витрин.

### Витрина

Витрина не создаётся вручную как дубликат базы. Её название, комментарий и поля извлекаются из PostgreSQL. В карточке отчёта вручную хранится только ссылка на используемую витрину.

Для каждого поля выводятся русское название, физическое имя (если оно полезно для аналитика) и описание из комментария базы. Комментарии к витринам и полям — обязательная часть процесса их создания.

### Глоссарий

Обязательные поля: идентификатор, термин, краткое определение, развёрнутое определение при необходимости, дата подтверждения. Термины упорядочиваются по алфавиту.

## 7. Рекомендуемая техническая схема

### Принцип

**Git — источник истины для бизнес-документации; виртуальная машина — место публикации сайта.** Это не взаимоисключающие варианты.

- В Git хранятся карточки отчётов, метрик, глоссарий, ссылки Power BI и история изменений.
- На VM размещается статический веб-портал за корпоративным сетевым контуром.
- Метаданные витрин формируются из PostgreSQL при публикации либо по расписанию и попадают в сайт как генерируемый каталог.

Статический сайт достаточен: все пользователи имеют одинаковый доступ, персональные данные и операции записи в портале не нужны, а поиск по названиям можно выполнять прямо в браузере.

### Безопасность

- Доступ к сайту ограничивается корпоративной сетью на уровне сети/reverse proxy.
- Приложению не требуются учётные записи и роли пользователей.
- Техническая учётная запись для чтения метаданных БД имеет минимальные права: только на утверждённые витрины и их комментарии.
- Портал не должен предоставлять пользователям прямое подключение к БД.

### Предлагаемая структура репозитория

```text
knowledge-portal/
├── content/
│   ├── reports/       карточки 37 отчётов
│   ├── glossary/      термины
│   └── sources/       ссылки на Excel / Google Sheets при необходимости
├── generated/
│   └── marts/         автоматически собранный каталог витрин и полей
├── site/              интерфейс портала
└── scripts/           проверка контента и сборка
```

Карточки лучше хранить как Markdown с компактными структурированными полями в начале файла либо как YAML/JSON. Для авторов это читабельнее, чем ручное редактирование записей в базе, а для сайта — удобно для проверки и сборки.

## 8. Процесс наполнения и актуализации

### Начальное наполнение

1. Создать минимальные карточки всех 37 отчётов: направление, назначение, ссылка Power BI и частота обновления.
2. Перенести в карточки полезное содержание существующих инструкций: страницы, фильтры, метрики и условия расчётов.
3. Завести начальный глоссарий из повторяющихся терминов: например, клиентская база, активная база, УЧК, ДПФУ, %Renew, план, факт.
4. После появления витрин подключить автоматическую выгрузку их комментариев и полей.
5. Аналитик проверяет бизнес-смысл каждой карточки перед публикацией.

### Поддержание актуальности

При существенном изменении отчёта (новая страница, метрика, формула, фильтр, витрина или частота обновления) автор изменения одновременно обновляет карточку. Проверка документации входит в чек-лист публикации Power BI.

Обновление идёт через Git: аналитик или администратор меняет карточку, проверка убеждается, что обязательные поля и ссылки заполнены, затем сайт пересобирается и публикуется на VM. В карточке обновляется дата последнего подтверждения. Раз в квартал проводится короткая ревизия изменённых отчётов.

Редактор внутри публичного портала в первой версии не нужен. Если позднее появится потребность, его можно добавить как отдельный административный интерфейс поверх тех же Git-данных.

## 9. Будущая автоматизация инструкций из Power BI

Вторая очередь — отдельный внутренний процесс подготовки черновика, а не автоматическая публикация:

1. Аналитик загружает `.pbix` или `.pbit`.
2. Инструмент извлекает доступную структуру: страницы, меры, поля, фильтры и связи.
3. Агент сопоставляет её с шаблоном и формирует черновик карточки отчёта и метрик.
4. Агент добавляет скриншоты страниц, если для этого доступна разрешённая среда рендеринга Power BI.
5. Аналитик проверяет смысл формул, исключений и терминов, после чего материал публикуется.

Автоматизация не должна самостоятельно утверждать бизнес-формулы. Для надёжных скриншотов потребуется отдельно определить технический способ рендеринга: установленный Power BI Desktop или разрешённый доступ к Power BI Service.

## 10. Реестр неперенесённых материалов

В текущей папке проекта не найдены структурированные инструкции для следующих 12 отчётов. Они остаются в первом охвате и должны быть добавлены в исходные материалы перед полным наполнением:

- «Вовлечение новичков Второй месяц»;
- «Отчет по поступлениям»;
- «Отчет по промокодам»;
- «Карты будущего периода»;
- «Edna»;
- «Отчет по посещаемости клиентов с долгами»;
- «Несчастные случаи»;
- «Пульс клуба 2026»;
- «Группа VK Физкульт (Анализ постов)»;
- «Директ»;
- «Отчет членство для правления»;
- «Свод выручка ГК».

Для остальных отчётов в проекте уже есть достаточная отправная точка: структурированные требования, исходные инструкции или материалы Power BI. Материалы следует переносить в единый каталог исходников без редактирования; портал будет использовать подготовленные карточки, а не отображать исходные DOCX напрямую.

## 11. Границы первой версии

**Входит:** каталог 37 отчётов, поиск по названиям, алфавитный глоссарий, карточки отчётов с метриками/фильтрами/страницами, ссылки Power BI, частота обновления, витрины и их поля, дата подтверждения, публикация на VM.

**Не входит:** мобильная оптимизация как отдельная цель, разные пользовательские роли, заявки и комментарии, экспорт PDF/Word, технические SQL/DAX-формулы, полная lineage до исходных систем, автоматическая генерация инструкций и скриншоты.

## 12. Приёмка первой версии

- Все 37 отчётов доступны через направления и поиск.
- У каждой карточки есть назначение, ссылка Power BI, частота обновления и дата подтверждения.
- У метрик есть бизнес-определение, формула, единица измерения и условия расчёта.
- Термины из глоссария открываются из карточек отчётов.
- Карточка показывает страницы отчёта, их фильтры и разрезы/группировки.
- Для отчёта видны используемые витрины и их поля; для внешних источников есть ссылка.
- Сайт доступен из корпоративной сети в браузере на десктопе и не требует отдельной регистрации.
