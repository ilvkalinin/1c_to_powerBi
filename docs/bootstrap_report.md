## Custom agents и взаимодействие

Созданы `source_mapper`, `data_architect`, `postgres_engineer`, `powerbi_reviewer`, `data_quality_reviewer`, `performance_reviewer`. Модель не закреплена и наследуется. Исследователи/reviewers настроены read-only; архитектор и инженер имеют workspace-write. Data-quality reviewer возвращает тесты основному агенту для записи.

Порядок: параллельное исследование → последовательное архитектурное решение → один write-инженер → параллельные независимые reviews → интеграция и повторная проверка основным агентом. Одновременная запись в один SQL запрещена.

Формат standalone agents подтверждён актуальным Codex Manual: `name`, `description`, `developer_instructions` обязательны; `sandbox_mode` допустим; отсутствие `model` обеспечивает наследование. Дублирующая регистрация ролей в `.codex/config.toml` не требуется.

`sandbox_mode` ограничивает локальную файловую систему, но не заменяет read-only права PostgreSQL. Реальная защита источника должна обеспечиваться отдельной DB-ролью. Ограничение write-агентов отдельными путями является инструкцией поведения, а не файловой ACL. Новые project-scoped agents/skills следует проверить в новом чате после загрузки trusted project config.

## Технологические решения

- PostgreSQL + обычные SQL-миграции + Git.
- Python допускается позже только для повторяемой автоматизации.
- Конфигурация подключения — через переменные окружения.
- SQL-тесты — с заранее зафиксированными ожиданиями.
- `.env.example` содержит только пустые имена переменных двух подтверждённых PostgreSQL-подключений: read-only источник VM-1 и база витрин VM-2.
- YAML-файлы являются не активным runtime, а небольшими машиночитаемыми шаблонами будущей инвентаризации; их поля намеренно `null`/`UNKNOWN`.

## Что отложено и почему

- SQL конкретных витрин, схемы и индексы: нет фактических источников, прав, mapping и планов.
- Подкаталоги `staging/core/marts/...`: создавать только выбранные архитектурой.
- Python scripts и зависимости: нет подтверждённого подключения и повторяемого процесса.
- Tests/fixtures: нет объекта, ключа и ожидаемых значений.
- dbt, Airflow, Dagster, Prefect, Docker, Kubernetes, ETL и платные сервисы: не согласованы и не нужны bootstrap.
- Технический журнал refresh: ручной/автоматический процесс ещё неизвестен.
- View/materialized view/table и refresh strategy: требуют объёмов, SLA, watermark и правил изменений.
- Production deploy: нет разрешения и параметров окружения.

## Риски

- Технические имена 1С могут быть неверно интерпретированы без метаданных.
- Отсутствие локального PostgreSQL CLI пока исключает автоматическую проверку БД.
- Python 3.14 требует проверки совместимости будущих зависимостей.
- Штатный `quick_validate.py` из `skill-creator` не запустился из-за отсутствующего в окружении `PyYAML`; YAML frontmatter, обязательные поля, соответствие имён каталогам и UI metadata проверены локальным YAML-парсером Ruby.
- Ранний выбор слоёв, materialization или инкремента создаст неподтверждённую сложность.
- Без контрольных значений тесты могут выявлять аномалии, но не доказывать бизнес-корректность.

## Следующий конкретный шаг

Предоставьте пакет одного существующего отчёта: исходный SQL, полный Power Query M, используемый DAX, схему модели Power BI и контрольные значения. После этого будет создан source-to-target mapping и спроектирована первая компактная витрина.
