## Учёт class-C критичности — 2026-08-13

Новый вопрос пользователю не требуется: current SQL/M/DAX уже задаёт первый
релиз, а нерешённые пункты являются физическими controls, не выбором новой
бизнес-методики.

- гостевая воронка сохраняет отсутствие status-filter и финальный `Distinct`
  по `(client code, guest visit date)`. 111 578 повторяющихся candidate-групп
  регистра не разрешают вводить новый event key, `ROW_NUMBER()` или иной
  silent dedup;
- distinct-карточки по клиенту в выбранном периоде, ACCUNIQ только в дату
  гостевого визита и окно активации `[0, 44]` дней сохраняются точно как
  current M/DAX. Состояния гостя, единица ACCUNIQ и границы 0/44/45 требуют
  независимого source control до SQL, но не угадывания новой трактовки;
- для первого посещения и тура сохраняются current `ROW_NUMBER`/дата
  телефонии-or-interaction и `COUNT`, без автоматически добавленного tie-break
  или `DISTINCT`. Внешний план Google Sheets по-прежнему не переносится.

Это safeguards воспроизведения по BR-018, а не методическое изменение.

## Граница физической реализации — решение 2026-08-24

Пользователь выбрал «оставить как в Power BI». Поэтому `mart.new_first_visit`
и `mart.guest_visit_conversion` не создаются: нынешний `ROW_NUMBER` без
второго порядка и `Distinct(client code, guest visit date)` остаются в Power
BI. Их нельзя перенести как one-row PostgreSQL facts без выбора, которого
current rule не задаёт. Правило закреплено в BR-035; источник и текущий PBI
не меняются.

## Назначение

Отчёт даёт рецепции и продажам дневную картину трёх разных воронок:

1. первый визит клиента с абонементом стажа `New`;
2. гостевой визит → фитнес-тестирование ACCUNIQ → активация абонемента;
3. тур/встреча → запись на ACCUNIQ → активация абонемента, включая план-факт
   встреч.

Пользователи: `UNKNOWN`. История следует общей политике `BR-003`, обновление
выполняется ежедневно, данные доступны не позднее 08:30 по Москве (решение
пользователя 2026-07-30, BR-014).

## Страницы, показатели и фильтры

### «Первые посещения»

Показывает первые квалифицированные посещения по каждому абонементу стажа
`New` в дневной детализации. Текущий SQL выбирает раннее движение
`AccumRg7575` для контракта, только документное посещение и исключает ДРЦ,
УК, ИП, сотрудников и неклиентов. Фильтры: клуб, год, месяц, день, стаж,
возрастная группа и возраст. Для строк с абонементом категория «дети /
юниоры / взрослые» берётся из возрастной категории номенклатуры абонемента.
Без абонемента она определяется по полному возрасту клиента на дату события
(решение пользователя 2026-07-30).

### «Гостевые визиты»

Показывает distinct клиентов с гостевым визитом, число из них с ACCUNIQ в
дату гостевого визита и число с первым подходящим абонементом, активированным
в интервале от 0 до 44 календарных дней после визита. Карточки и DAX:

- всего гостевых — `DISTINCTCOUNT(КодКлиента)`;
- ACCUNIQ — те же клиенты с непустой датой ACCUNIQ;
- абонементы — те же клиенты с непустой датой активации;
- конверсии — отношение соответствующего distinct-числителя к числу гостевых.

В детализации показываются клиент, дата гостевого визита, дата ACCUNIQ, дата
активации и техническая колонка количества. Фильтры совпадают с первой
страницей. Текущая модель также присваивает стаж клиента на дату регистрации
события, а не на дату гостевого визита.

### «Туры»

Источник — CRM-взаимодействия в воронке «Продажа клубной карты» с текущим
GUID типа «встреча». В набор входят пары:

- состояние `Закрыто` и статус `Выполнено` — состоявшаяся встреча;
- состояние `Запланировано` и статус `Не выполнено` — запланированная встреча.

Для состоявшихся туров DAX считает число строк, конверсию в ACCUNIQ по
непустой записи и конверсию в абонемент по непустой дате активации. Покупка
атрибутируется к туру при активации от 0 до 44 дней после отчётной даты тура.
ACCUNIQ атрибутируется при записи клиента на услугу ACCUNIQ в ту же дату.

Страница содержит карточки, дневные графики и таблицу с клиентом, состоянием,
исполнителем и результатами. Фильтры: клуб, год, месяц, день, стаж,
возрастная группа, возраст и исполнитель.

План встреч приходит из отдельной Google Sheets. План на оставшиеся дни месяца
является интерактивной DAX-мерой: месячный план минус факт состоявшихся туров
до текущего дня, делённые на оставшиеся дни. В PostgreSQL он не переносится.

## Гранулярность, история и PII

Отчёт нельзя реализовывать одной таблицей:

| Набор | Предварительная строка | Причина отдельности |
|---|---|---|
| Первые посещения New | контракт × первое квалифицированное посещение | связан с контрактом и ранжируется по времени посещения |
| Гостевые визиты | гость × дата гостевого визита; технический ключ `UNKNOWN` | имеет собственный регистр статусов и конверсии |
| Туры | CRM interaction `Reference67.ID` | это CRM-событие с собственными состояниями и исполнителем |

Текущие детали содержат код и ФИО клиента, а у туров ещё и телефон. Они не
нужны для KPI, но сохраняются по решению пользователя 2026-07-30, чтобы не
менять текущие детальные таблицы. Права Power BI должны соответствовать
текущему доступу к отчёту.

Текущий нижний предел в M/SQL — 2025 год. Для будущей реализации применяется
единая календарная политика `BR-003`; обновление выполняется ежедневно,
данные доступны не позднее 08:30 по Москве (решение пользователя 2026-07-30,
BR-014).

## Зафиксированные риски

1. В M по гостевым визитам отсутствует фильтр `Статус`; неизвестно, какие
   состояния регистра означают проведённый визит.
2. Текущий DAX считает гостей distinct по клиенту, хотя визуал строится по
   дням. При нескольких гостевых визитах одного клиента за период итог
   отличается от числа событий — это текущая, подтверждённая реализация.
3. Текущее присвоение стажа берёт последнюю запись `InfoRg5654` до `_Period`,
   но заменяет отсутствие записи на `New`; семантика такого default не доказана.
4. Список 12 кодов ACCUNIQ и интервал конверсии 0–44 дней зафиксированы в M,
   но коды, смысл количества и состояния движений не подтверждены metadata.
5. В `ЗаписиНаАккуники` последняя запись выбирается по «групповому занятию»,
   а не по клиенту; последующий join идёт по клиенту и дате. Это может
   потерять либо неверно атрибутировать запись на ACCUNIQ.
6. В CRM один interaction может размножаться при join с `InfoRg7146`; дата
   тура использует телефонную дату, если она не `NULL`, иначе `_Fld820`.
   Кардинальность и бизнес-смысл такого выбора не подтверждены.
7. Нет проверки `Marked`, проведения, `Active`, сторно и удалений ни в одной
   ветви.

SV-106 подтвердил physical path `InfoRg7006`: latest выбирается по
предварительной записи и затем исключает состояния 2/3. В current scope
получено 8 строк с равным максимальным временем и 128 лишних строк
относительно пары `клиент × дата начала`. Эти строки сохраняются как результат
нынешнего PBIT; tie-break или дедупликация без нового правила запрещены.
