# Требования отчёта: «Записи администраторов»

Статус: `BUSINESS LOGIC COMPLETE / STAGE 2 PARTIALLY VALIDATED — SV-086 / IMPLEMENTATION DEFERRED`.
Договорный отчёт № 19. SQL и физические таблицы не создаются; допустимы только
read-only проверки источника.

## Stage 2: source-side evidence

Набор точных current-SQL проверок AB-V01—AB-V04 сохранён в
[`administrator_bookings_2026-08-11.sql`](../source_metadata/validation_sql/administrator_bookings_2026-08-11.sql).
11 августа 2026 года `BEGIN READ ONLY` подтвердил `transaction_read_only=on`.
AB-V01 нашёл все 13 relations. AB-V02: 100 current-M групповых документов =
100 ID, повторов нет. AB-V03: 72 подходящих предварительных документа = 72 ID;
26 из них связаны с несколькими движениями `AccumRg7575` (максимум 25), но
агрегация current M оставляет один документ. AB-V04: в выборке 100 групповых
документов нет historical admin-position match; в предварительной ветке нет
match у 99 из 100 документов, а один имеет четыре. Это `VALIDATION_FAILED` для
автоматической замены current-M кадрового CTE исторической связью.

Первичная запись о таймауте была вызвана ошибочным включением SSL в клиенте:
сервер не поддерживает SSL. После корректного подключения источник доступен;
новых записей в реестр отсутствующих объектов нет.

SV-035, SV-037, SV-072 и SV-073 остаются переиспользуемыми доказательствами
ключей движений, ветки предварительной записи и состояний занятий, но не
заменяют специфичную сверку двух веток данного отчёта.

## Учёт class-C критичности — 2026-08-13

Новый вопрос пользователю не требуется. Правила первого релиза уже
подтверждены: один документ — одна запись одного клиента, должность автора
определяется на дату создания записи, а выручка обеих веток берётся из
`AccumRg7575.Fld7586`.

- SV-086 подтверждает document grain обеих веток, но 26 из 72 документов
  предварительной записи связаны с несколькими движениями. Поэтому нельзя
  считать одно движение отдельной записью, применять `DISTINCT` к движениям
  или молча менять current aggregation документа;
- 199 из 200 документов в контрольной выборке не получили historical
  admin-position match, а один получил четыре. Историческое интервальное
  сопоставление нельзя автоматически подставлять вместо current-M кадрового
  правила или выбирать из нескольких match эвристикой;
- до отдельного доказательства связи запись × клиент × услуга × движение
  сохраняются current filters, отмены и ветки источников по BR-018. Это не
  разрешает реализацию SQL с недоказанной суммой: требуются независимые
  controls кардинальности и сохранения `AccumRg7575.Fld7586`.

Это safeguards воспроизведения, а не изменение методики.

## Назначение

Показать выручку оказанных групповых услуг ДПФУ, на которые клиентов записали
администраторы рецепции, количество таких записей и среднюю цену записи.

## Фильтры

- год и месяц занятия;
- день занятия;
- клуб занятия;
- администратор — автор записи;
- формат тренировки из карточки номенклатуры.

Активная отчётная дата — дата занятия, а не дата создания записи.

## Метрики

| Метрика | Текущее правило |
|---|---|
| `Всего выручки по записям администраторов` | `SUM(equity)` |
| `Всего записей администраторов` | `COUNT(Код_Клиента)` в объединённом наборе |
| `Средняя цена записи` | выручка / количество записей |

Скриншот даёт контроль формулы: `482 205 / 542 ≈ 890`.

## Визуализации

- три карточки;
- рейтинг клубов по выручке;
- динамика выручки по дням, месяцам и годам;
- таблица `Номенклатура × Администратор × Должность` с выручкой, количеством
  записей и средней ценой.

## Минимальная требуемая гранулярность

Предварительно достаточно агрегата:

> дата занятия × клуб × администратор × должность на дату записи × услуга ×
> формат тренировки × технический тип источника.

Показатели строки:

- `Количество записей`;
- `Выручка`.

Клиент, тренер и возрастная категория показанными визуалами не используются и
в Power BI передаваться не должны.

## Предварительное повторное использование

Выручка предварительных записей уже использует `AccumRg7575`, входящий в общий
логический факт `Оказанные услуги ДПФУ`. Не следует создавать вторую копию
этих движений. Предпочтительное направление после подтверждения связей —
дополнить общий факт атрибуцией записи:

- тип и ID записи;
- сотрудник — автор записи;
- должность автора на дату записи.

Затем Power BI получает только агрегат, нужный странице. Отдельный факт
посещений клиентов для этого отчёта не подходит.

## Обнаруженные противоречия

1. В ветке групповых записей выручка берётся из суммы документа записи
   `Document283.Fld3297`, а в ветке предварительных записей — из фактических
   движений `AccumRg7575.Fld7586`.
2. Состав администраторов определяется на текущую дату; после увольнения
   сотрудника его прошлые записи исчезают.
3. Две ветки применяют разные фильтры форматов тренировок.
4. Текущий DAX считает строку с клиентом, а не поля количества клиентов
   документов.
5. Запрос дневного плана `InfoRg6612` не используется описанными визуалами.

## Подтверждённые правила

- один документ записи создаётся на одного клиента; одна строка документа
  считается одной записью;
- должность автора определяется на дату создания записи, поэтому увольнение
  сотрудника не удаляет его историю;
- для `Document329` остаются только `Групповое занятие` и `Платный урок`,
  объединённые в категорию `Групповое занятие`;
- для `Document283` остаются все форматы, кроме `Персональная тренировка`;
- отсутствующий формат в обеих ветках заменяется на `Малая группа`;
- `Дневное планирование Power BI (2)` из модели отчёта исключается;
- обновление выполняется ежедневно.

## Выручка

Для обеих веток используется фактическая стоимость оказанной услуги
`AccumRg7575.Fld7586`. Большой регистр не копируется на VM витрин:

- на исходной базе отбираются движения подтверждённого периода, связанные с
  документами записей администраторов;
- сумма считается по конкретной записи клиента;
- после присоединения автора результат агрегируется до целевой дневной
  гранулярности;
- на VM витрин передаётся только компактный агрегат.

`Document283.Fld3297` остаётся контрольным значением для технической сверки,
но не является целевым источником выручки.

## Архитектурное решение

`AccumRg7575` не копируется полностью и не создаётся второй факт выручки.
Общий факт ДПФУ получает только техническую атрибуцию записи и автора. Для
Power BI создаётся обычный локальный агрегирующий view; отдельная таблица или
materialized view допускается только после измерений.
