## Power Query: подтверждённые правила

### События записи

В обеих ветках фильтр по дате ставится на дату начала занятия. Ветка ПЗ
соединяет `InfoRg7006.Fld7007` с `Document329`, исключает специальную услугу
ИП, купоны и тип взаиморасчётов «с сотрудником» из `Document329.VT4352`.
Ветка ГП соединяет с `Document279`, оставляет предварительно оплаченные
занятия. В обеих ветках `Enum448.EnumOrder = 1` — ожидаемая запись, `2/3` —
отмена, `4` — прибытие (только отдельный набор ГП).

Временные категории текущего M:

| Условие | Ярлык |
|---|---|
| `Period < Date(lesson_start)` | `До 9:00` |
| `Period < lesson_end` | `До конца урока` |
| иначе | `После конца урока` |
| предыдущая строка и `Period >= Date(lesson_end)+1` | `След день` |
| отмена и `Period < Date(lesson_start)` | `Отмена до 9:00` |
| иная отмена | `Отмена после 9:00` |

В M нет сравнения с 09:00. Подпись оставлена как legacy-label; текущий
результат соответствует концу предыдущего дня.

### План и групповые занятия

План использует `InfoRg6612.Fld6613` как дату тренировки, `Fld6614/15/16`
как подразделение/клуб/тренер, `Fld6619` как клиента и `Fld6620` как
стоимость. DAX считает план услуг через `COUNT([Клиент])`, а не через
колонку количества регистра.

Для таблицы групповых занятий M берёт `Document279.Fld3222` как вместимость.
Набор статусов 1/2/3 даёт `+1/-1` на запись; статус 4 даёт пришедших для
платной программы; `InfoRg8675.Fld8677` — пришедших бесплатной программы.

## DAX: формулы, которые нельзя неявно менять

- `ВсегоЗаписей = До9 + ДоКонца + Отмены + ПослеКонца + СледДень`.
- `До9` складывает ожидающие записи «До 9:00» и вычитает отмены до этой
  границы; `Отмены` возвращает количество отмен после границы со знаком
  минус.
- Доли всех категорий делятся на `ВсегоЗаписей`; `Записей на 1 сотрудника`
  делит его на distinct сотрудников текущего набора.
- «Сотрудников 80%+» считает сотрудника, если
  `До9 / (До9 + ДоКонца + ПослеКонца − Отмена) >= 0.8`.
- «Был в клубе» сопоставляет код клиента, календарную дату занятия и клуб с
  набором посещений; это не проверка физического присутствия во время
  занятия.

## Подготовленные read-only SQL-проверки

Статус каждого фрагмента: `VALIDATION_PENDING`; `NOT_EXECUTED — ожидается
подключение к корпоративной сети`. Выполнять только в STAGE_2 после
подтверждения фактической схемы и подстановки согласованного интервала
`:from_ts` / `:to_ts`. Имена ниже повторяют SQL из текущего M.

```sql
-- PC-V02: кандидат ключа состояния предварительной записи.
SELECT _Period, _RecorderRRef, _LineNo, count(*) AS duplicate_count
FROM _InfoRg7006
WHERE _Period >= :from_ts AND _Period < :to_ts
GROUP BY _Period, _RecorderRRef, _LineNo
HAVING count(*) > 1;
-- Expected: 0 строк либо документированное правило истории.

-- PC-V03: каждая строка состояния относится ровно к одной ветке документа.
SELECT
    CASE WHEN p._IDRRef IS NOT NULL THEN 'Document329' END AS personal_branch,
    CASE WHEN g._IDRRef IS NOT NULL THEN 'Document279' END AS group_branch,
    count(*) AS state_rows
FROM _InfoRg7006 s
LEFT JOIN _Document329 p ON p._IDRRef = s._Fld7007_RRRef
LEFT JOIN _Document279 g ON g._IDRRef = s._Fld7007_RRRef
WHERE s._Period >= :from_ts AND s._Period < :to_ts
GROUP BY 1, 2;
-- Expected: нет строки, где обе ветки заполнены или обе NULL.

-- PC-V04: измерить влияние состояний источника по каждой ветке.
SELECT 'Document329' AS branch, s._Active, p._Posted, p._Marked, count(*)
FROM _InfoRg7006 s JOIN _Document329 p ON p._IDRRef = s._Fld7007_RRRef
WHERE s._Period >= :from_ts AND s._Period < :to_ts
GROUP BY 1, 2, 3, 4
UNION ALL
SELECT 'Document279', s._Active, g._Posted, g._Marked, count(*)
FROM _InfoRg7006 s JOIN _Document279 g ON g._IDRRef = s._Fld7007_RRRef
WHERE s._Period >= :from_ts AND s._Period < :to_ts
GROUP BY 1, 2, 3, 4;
-- Expected: выбранное правило Active/Posted/Marked и его числовой эффект зафиксированы.

-- PC-V07: подтверждение фактических кодов состояния.
SELECT e._EnumOrder, count(*) AS state_rows
FROM _InfoRg7006 s
LEFT JOIN _Enum448 e ON e._IDRRef = s._Fld7013RRef
WHERE s._Period >= :from_ts AND s._Period < :to_ts
GROUP BY e._EnumOrder
ORDER BY e._EnumOrder;
-- Expected: все коды сопоставлены с бизнес-состоянием; orphan enum = 0.

-- PC-V09: риск размножения персональной записи табличной частью услуг.
SELECT p._IDRRef AS booking_id, count(v._LineNo) AS service_rows
FROM _Document329 p
LEFT JOIN _Document329_VT4352 v ON v._Document329_IDRRef = p._IDRRef
WHERE p._Fld4306 >= :from_ts AND p._Fld4306 < :to_ts
GROUP BY p._IDRRef
HAVING count(v._LineNo) > 1;
-- Expected: либо 0 строк, либо утверждён источник одной qualifying service-line.

-- PC-V10: дубли назначения в текущем плане.
SELECT _Fld6613, _Fld6614RRef, _Fld6615RRef, _Fld6616RRef, _Fld6619, count(*)
FROM _InfoRg6612
WHERE _Fld6613 >= :from_ts AND _Fld6613 < :to_ts
GROUP BY 1, 2, 3, 4, 5
HAVING count(*) > 1;
-- Expected: 0 строк либо документированная причина и правило схлопывания.

-- PC-V11/12: одна строка занятия и источник вместимости/статусов.
SELECT
    g._IDRRef AS group_lesson_id,
    g._Fld3222 AS capacity,
    count(s._LineNo) FILTER (WHERE e._EnumOrder = 1) AS expected_rows,
    count(s._LineNo) FILTER (WHERE e._EnumOrder IN (2, 3)) AS cancel_rows,
    count(s._LineNo) FILTER (WHERE e._EnumOrder = 4) AS arrived_rows,
    max(gs._Fld8677) AS free_program_arrived
FROM _Document279 g
LEFT JOIN _InfoRg7006 s ON s._Fld7007_RRRef = g._IDRRef
LEFT JOIN _Enum448 e ON e._IDRRef = s._Fld7013RRef
LEFT JOIN _InfoRg8675 gs ON gs._Fld8676RRef = g._IDRRef
WHERE g._Fld3218 >= :from_ts AND g._Fld3218 < :to_ts
GROUP BY g._IDRRef, g._Fld3222;
-- Expected: одна итоговая строка на занятие; правила платной/бесплатной ветви
-- и кардинальность InfoRg8675 зафиксированы до вычисления заполненности.
```
