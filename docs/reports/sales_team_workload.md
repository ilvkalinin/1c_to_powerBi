# Требования отчёта: «Загрузка ОП»

Статус: `BUSINESS LOGIC COMPLETE / STAGE_2 SOURCE VALIDATION PARTIALLY VALIDATED — SV-084 / IMPLEMENTATION DEFERRED`. Внешние нормативы остаются вне PostgreSQL. Физические таблицы и объекты БД не создаются.

## Stage 2: SV-084 (2026-08-11)

Live read-only запрос подтвердил существование пяти центральных отношений CRM.
Ранее выполненные SV-026—SV-034 уже подтверждают допустимую phone-grain,
кардинальности task/manager, historical-employment semijoin, ключи воронок и
кампаний, planned-state и текущую классификацию событий. Новый полный
legacy-filter bounded control не вернул результат в `statement_timeout`, а
следующее подключение к gymdb завершилось `ETIMEDOUT`; эти попытки не считаются
валидацией. Они не изменяют текущие SQL/M/DAX, включённые фильтры или работу с
внешними Excel-нормативами по BR-018.

## Назначение

Договорный отчёт № 12 показывает загрузку менеджеров отделов продаж взаимодействиями с клиентами.

Отчёт состоит из двух страниц:

1. `Загрузка ОП` — выполненные и иные взаимодействия, структура задач, звонки и расчёт нормативной загрузки.
2. `Запланированные взаимодействия` — текущие запланированные задачи, включая просроченные, с детальной таблицей клиентов.

## Общие фильтры

- год и месяц;
- день;
- клуб оператора;
- оператор;
- стаж клиента `New / Ex / Renew`;
- статус клиента `Действительный / Бывший / Потенциальный`.

## Страница «Загрузка ОП»

| Метрика | Бизнес-описание | Текущая реализация | Статус |
|---|---|---|---|
| `Количество задач` | число взаимодействий менеджеров с непустым кодом клиента | `COUNT(КодКлиента)` | CONFIRMED — сохранить текущую меру |
| `В среднем задач в день` | число задач за день, когда менеджер выполнил хотя бы одну задачу | задачи / distinct активных пар `менеджер × день` | CONFIRMED — user decision |
| `Взял трубку` | считать строго по текущим мерам | SQL-флаг `Answer`, затем DAX обнуляет входящие звонки | CONFIRMED — user decision |
| `Средняя длительность звонка` | считать строго по текущей мере | `AVERAGE(ВремяОкончания − ВремяНачала)` по непустым неотрицательным длительностям без дополнительного фильтра `Answer` | CONFIRMED — user decision |
| `Медиана длительности звонка` | считать строго по текущей мере | `MEDIAN(Длительность звонка)` по тем же непустым длительностям | CONFIRMED — user decision |
| `% загрузки` | нормативное время / рабочее время активных менеджер-дней | сумма норматива / distinct пар `менеджер × день` / 465 минут | CONFIRMED — user decision / corrects total formula |

Основные разрезы:

- клуб;
- вид события;
- состояние взаимодействия;
- статус взаимодействия;
- статус и стаж клиента;
- менеджер;
- тип воронки;
- взял трубку / всего звонков.

Нормативы зависят от сети и вида события. Для встречи в сервисной воронке текущий DAX задаёт 5 минут. При отсутствии норматива используются 1,5 минуты без ответа и 3 минуты при ответе. Рабочий день равен 465 минутам. Смен без задач по бизнес-правилу не бывает.

Два Excel-файла нормативов остаются без изменений и продолжают подключаться как внешние источники Power BI. Их перенос в PostgreSQL не входит в текущую работу.

## Страница «Запланированные взаимодействия»

| Метрика | Определение | Текущая реализация | Статус |
|---|---|---|---|
| `Всего запланировано` | текущие взаимодействия в состоянии `Запланировано` | количество строк выбранного набора | CONFIRMED current |
| `Всего просрочено` | плановая дата меньше текущей даты | `ДатаПлан < TODAY()` | CONFIRMED — dynamic current backlog |
| `Не просрочено` | плановая дата сегодня или позднее | `ДатаПлан >= TODAY()` | CONFIRMED current |

Разрезы:

- клуб;
- менеджер;
- вид события;
- плановая дата.

Детальная таблица показывает менеджера, код клиента, ФИО, телефон, плановую дату и количество. Следовательно, агрегат только `дата × клуб` не подходит, а выдача содержит персональные данные и требует ограниченного доступа.

## Текущий отбор данных

Текущие запросы:

- оставляют воронки `Продажа клубной карты`, `Сервисная воронка ОП`, `Корпоративная продажа`;
- исключают две Jivo-site кампании из сервисной воронки;
- оставляют сотрудников в должностях `Менеджер ОП` и `Старший менеджер ОП`;
- проверяют интервал приёма/увольнения по `ДатеСоздания` взаимодействия;
- определяют сеть как `Пушкинский` для клубов `Пушкинский` и `Пушкинский VIP`, иначе `Физкульт`;
- используют захардкоженные периоды 2026 для основной страницы и 2025–2026 для планов.

Целевые правила сохраняют текущие три воронки и исключение двух Jivo-site кампаний. Расширять охват относительно запроса не требуется.

`Клуб оператора` определяется клубом задания `Reference106.Fld1195`. Менеджер должен иметь действующую запись `InfoRg6291` в этом же клубе и одной из двух разрешённых должностей на `ДатуСоздания` взаимодействия. Один менеджер может работать в нескольких клубах.

## Минимальная детализация

Средняя и особенно медианная длительность, а также детальная таблица планов требуют сохранить уровень отдельного взаимодействия.

Бизнес-grain core:

> одно взаимодействие `Reference67`.

Report-compatible phone-grain не нормализуется: если `InfoRg7146` содержит
несколько строк звонков для одного взаимодействия, каждая остаётся отдельной
строкой report-view; без телефонной строки сохраняется одна строка
взаимодействия. Это подтверждённое текущее правило и evidence SV-026, а не
основание для дедупликации.

Один общий набор потенциально способен обслужить обе страницы через две даты:

- `Дата взаимодействия`;
- `Плановая дата`.

Отдельная физическая копия `ЗапланированныеВзаимодействия` не требуется:
обе роли даты сохраняются в общем CRM-core и report-view.

## Подтверждённые решения 2026-07-24

- рабочий менеджер-день существует, если менеджер выполнил хотя бы одну задачу; смен без задач нет;
- звонковые показатели рассчитываются строго по предоставленным мерам, даже там, где текстовое описание отличается;
- Excel-нормативы не переносить и не изменять;
- `Треды Edna`, `Первое исходящее` и предыдущие контакты исключить как неиспользуемые;
- обновлять каждые два часа с 08:00 до 22:00 включительно: `08, 10, 12, 14, 16, 18, 20, 22`.
- входящий звонок не увеличивает `Взял трубку`, поскольку инициатором является клиент;
- клуб — клуб задания, но трудоустройство менеджера проверяется в том же клубе;
- должность и интервал трудоустройства проверяются на `ДатуСоздания`;
- оставить текущие три воронки и две Jivo-site кампании исключёнными;
- просрочка определяется относительно текущей даты без исторических снимков;
- строки без кода клиента не входят в `Количество задач`.
