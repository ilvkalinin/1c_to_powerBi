# Требования отчёта: «Воронка»

Статус: `BUSINESS LOGIC COMPLETE / GLOBAL-GATE SOURCE CONTROLS CLOSED — SV-080, SV-101, SV-103, MF-V10A / IMPLEMENTATION DEFERRED`.

Договорный отчёт № 27, блок «Маркетинг». Он показывает созданные задания
CRM-воронки «Продажа клубной карты», конверсию в активацию подходящих
абонементов и выполнение плана. Источники истины: бизнес-описание, текущие
SQL/M/DAX и Stage 2 source-side evidence. `SV-080`, `SV-101`, `SV-103` и
`MF-V10A` выполнены в gymdb только на чтение. Текущий source-side scope global
gate закрыт; приёмка созданной модели остаётся следующим этапом и не начинается
автоматически.

## Бизнес-гранулярность и время

- Задание: одно CRM-задание; количество заданий — `DISTINCTCOUNT(КодЗадания)`.
- Абонемент: метрика считает каждую квалифицированную связь `задание ×
  абонемент` через `InfoRg6798`. Квалификация требует `activation_date >=
  task_created_at` и `activation_date >= 2024-01-01` (BR-020). Один и тот же
  абонемент у разных заданий учитывается для каждого задания; `SV-080`
  опроверг one-to-one кардинальность `задание → контракт`.
- Дата задания: дата создания задания. Ею управляются отбор периода, дневные
  графики и сравнение с прошлым годом.
- Дата абонемента: дата активации контракта. Она определяет факт покупки,
  включая накопленный трафик.
- «Накопленный трафик»: задания, созданные в двух календарных месяцах перед
  выбранным месяцем, разделяются на входящий/исходящий по типу первого
  взаимодействия. Текущая DAX исключает из остатка часть закрытых отказом или
  отменой и часть уже активировавших контракт; точные границы и дедупликация
  фиксированы как `VALIDATION_PENDING`.

## Общие фильтры

На страницах «Воронка», «Свод» и «Абонементы»: год/месяц, день, сеть/кластер,
клуб, тип взаимодействия, стаж клиента, возрастная группа купленного
контракта, тип оплаты купленного контракта и длительность купленного
контракта. На «Маркетинговых кампаниях» вместо года/месяца и дня применяется
произвольный период; остаются сеть/кластер, клуб, тип взаимодействия,
маркетинговая кампания, стаж и возрастная группа.

Возрастная группа, тип оплаты и длительность контракта влияют **только** на
метрики, связанные с абонементами; число заданий и его план должны игнорировать
эти срезы. На странице кампаний правило относится к возрастной группе.

## Подтверждённые правила текущего набора

1. Охват задач: воронка `Продажа клубной карты`, задание не помечено на
   удаление, клуб «Детский развивающий центр» исключён, дата создания попадает
   в выгружаемый год.
2. Два exact-значения причины неуспешного завершения «Найдено аналогичное
   задание» исключаются до модели.
3. Контракт выбирается из `InfoRg6798` только при `_Fld6802 = true`; исключены
   «клип-карта» и бесплатный тип оплаты. Raw current SQL ведёт историю
   активаций с 2024-01-01. По BR-020 дополнительно требуется, чтобы активация
   была не раньше даты создания соответствующего задания.
4. Возраст: детские секции выделяются по типу контракта; иначе возрастные
   категории номенклатуры переводятся в «Взрослые», «Дети», «Юниоры», а
   неизвестное — «Взрослые». Тип оплаты: «Рекарринг» или «Предоплата».
   Длительность: `001–007`, `008–030`, `031–180`, `181–364`, `365+` дней.
5. Тип первого взаимодействия маппится по фиксированным GUID, затем Power
   Query оставляет отдельными встречу, входящий/исходящий звонок, оформление,
   чат, регистрацию рекомендации и гостевого визита, обратную связь;
   кампанию с родителем, начинающимся на «Промо», относит к мероприятиям,
   остальное — к «Прочим».
6. Накопленный трафик использует текущий исторический набор
   `UNION(Задания 2024, Задания 2025)`: для первого дня выбранного месяца
   берёт разные коды заданий двух предыдущих календарных месяцев, вычитает
   разные закрытые до месяца «Отказ»/«Отмена» и сумму разных клиентов
   контрактов, активированных до месяца, по каждому заданию. На контрольном
   месяце 2025-07-01 source-side MF-V08 дал итог 23 864; фактические числа
   Power BI для независимой сверки не предоставлены.

## Результат reuse review

Базовый набор отчёта повторно использует `mart.fitness_leads_funnel_task`:
совпадают grain, ключ `task_id`, CRM-источники и task-to-contract enrichment.
Новый факт, копия регистра или отдельное извлечение CRM не нужны. Маркетинговая
классификация первого взаимодействия и меры накопленного трафика остаются
семантикой Power BI поверх этого набора. Решение `REUSE` является проектным до
технической валидации существующего факта.

## Результат Stage 2: SV-080

В контроле текущего bridge после фильтров модели выбраны 100 строк
`InfoRg6798`: они относятся к 36 CRM-заданиям, из которых 21 имеет более
одного контракта. В заданиях с несколькими контрактами — 85 связей
`task × contract`;
максимум — 16 контрактов на задание. Следовательно, гипотеза one-to-one
`task → contract` имеет статус `VALIDATION_FAILED`.

Task core остаётся `REUSE` из `mart.fitness_leads_funnel_task` (также
опирается на SV-078). BR-020 снимает бизнес-развилку: `contract_count = 1`
на каждой квалифицированной связи `task × contract`; глобальный `DISTINCT`
по абонементу и выбор «главного» задания запрещены. Никакие объекты PostgreSQL
и источника 1С не создавались и не изменялись.

По прямому запросу пользователя MF-V03E показал один реальный пример без ПДн:
задание `000144962` связано с четырьмя подходящими абонементами —
`СФ00118931`, `СФ00118985`, `СФ00118986`, `СФ00118987`.

Это не было примером обратного направления. Отдельный MF-V03F подтвердил
техническую связь абонемента `0000302905` с заданиями `008259075` и
`008854940`, но MF-V03G доказал, что обе связи не проходят BR-020: 2 известные
связи, 0 прошедших временную квалификацию. Этот пример не используется в
конверсии.

## Учёт class-C критичности — 2026-08-13

Новый вопрос не требуется: пользователь явно принял BR-020. В SQL нельзя
сначала схлопнуть bridge, а потом применять дату, либо считать старый
абонемент результатом позднего задания. Физические controls task code, states
и join preservation остаются следующими техническими условиями, но не меняют
подтверждённую единицу метрики.
