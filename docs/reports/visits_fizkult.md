## Требуемые логические гранулярности

Для показателей с `DISTINCTCOUNT`:

> дата посещения × фактический клуб × стабильный обезличенный клиент.

Повторные сырые входы одного клиента в этот день и клуб схлопываются. Такой набор является максимально агрегированным уровнем, который ещё сохраняет корректный distinct по произвольному диапазону дат и клубов.

Для ГП:

> дата события × клуб группового занятия.

ГП поступает готовым количеством посетивших без клиентских идентификаторов, поэтому его нельзя смешивать с client-day строками в одном факте.

На VM-2 не передаются исходные ID/коды клиентов, ФИО, абонементы и сырые услуги. Требуется только отдельный стабильный обезличенный ключ для `DISTINCTCOUNT`.

## Предварительная модель Power BI

Все пользовательские названия — на русском:

- `Посещения клиентов` — общий обезличенный client-day факт для Физкульт и Пушкинского;
- `Показатели клуба по дням` — общий дневной агрегат ГП и других подтверждённых показателей той же гранулярности;
- `Тренировки ИП` — кандидат на общий компактный факт `дата × клуб × сотрудник × клиент × услуга` для показателя ИП и отдельного «Отчета по ИП»; до технической проверки временного ключа источника не реализуется;
- `Календарь` — общий календарь;
- `Клубы` — общий справочник;
- `Меры посещений` — таблица DAX-мер.

Проценты, `С тренером`, `Без тренера` и `DISTINCTCOUNT` остаются DAX-мерами. Поиск исходных событий, классификация флагов, устранение технических дублей и схлопывание до client-day выполняются PostgreSQL. Пересечения между разными показателями намеренно сохраняются.

Физическая архитектура не создаёт отдельный объект для отчёта: см. `docs/adr/0003-shared-visits-domain.md`.

## Полученная мера ГП

Текущая мера пользователя:

```DAX
Посещения ГП =
CALCULATE (
    SUM ( 'Посещения ГП'[Посетило] ),
    'Посещения ГП'[Дата события] IN VALUES ( 'спрДата'[Date] )
)
```

Следовательно, целевой SQL должен агрегировать `InfoRg8675.Fld8677` (`КоличествоПосетивших`) по дате события `Document279.Fld3218` и фактическому клубу группового занятия `Document279.Fld3224`.

## Полученные меры ДПФУ и купонов

```DAX
Посещения ДПФУ =
CALCULATE (
    DISTINCTCOUNT ( 'Посещения проверка ДПФУ'[КодКлиента] ),
    'Посещения проверка ДПФУ'[Период] IN VALUES ( 'СпрДата'[Date] )
)
```

```DAX
Посещения по купону =
CALCULATE (
    DISTINCTCOUNT ( 'Посещения по купону'[client_code] ),
    'Посещения по купону'[visit_date] IN VALUES ( 'СпрДата'[Date] )
)
```

Обе меры целевым образом несуммируемы по датам и клубам: в итоговом контексте один клиент считается один раз, даже если встречается в нескольких дневных строках. Это влияет на целевую гранулярность:

- дневной агрегат `дата × клуб` воспроизведёт каждую строку визуала;
- дневной агрегат не воспроизведёт текущий `DISTINCTCOUNT` в итоговой строке произвольного диапазона;
- для точного сохранения текущего итога требуется набор `дата × клуб × обезличенный стабильный клиент × признаки категорий`.

## Полученная мера общего посещения

```DAX
Посещения всего =
CALCULATE (
    DISTINCTCOUNT ( 'Посещения всего'[КодКлиента] ),
    'Посещения всего'[_period] IN VALUES ( 'СпрДата'[Date] )
)
```

Мера и целевой отчёт считают уникальных клиентов, а не события входа:

- два входа одного клиента в один день дают `1`;
- посещения одного клиента в разные выбранные дни также дают `1` в итоговой строке периода;
- один клиент, посетивший несколько клубов, может дать `1` в сетевом итоге, если клуб не ограничен.

Окончательное решение пользователя — считать строго как в формуле. Оно заменяет предыдущий ответ «два посещения = 2».

Для сохранения результата по произвольному диапазону PostgreSQL должен предварительно объединить и очистить события до набора `дата × фактический клуб × стабильный обезличенный клиент`, а Power BI выполнить `DISTINCTCOUNT` этого клиента в текущем контексте.

## Полученная мера ИП

```DAX
Посещения ИП =
COUNT ( 'ОбщаяРС'[Контрагент] )
```

Мера считает непустые строки контрагента, а не уникальных клиентов. `ОбщаяРС` объединяет строки предварительной записи из документов ГП и ПЗ.

После разбора «Отчета по ИП» выявлено доказанное повторное использование этих же строк с детализацией сотрудника, услуги и клиента. Поэтому дублирующий `ip_training_count` внутри client-day факта не проектируется: показатель должен суммироваться из общего агрегированного факта тренировок ИП после проверки временного ключа исходной тренировки.
