# S3-RGS-LOAD-001: blocker первичной загрузки «Свода выручка ГК»

Дата: 2026-08-20. Статус: `RESOLVED — SHARED-FACT REMEDIATION COMPLETED`.

## Что проверено

Запускал только source-side extract на read-only снимке 1С за BR-003
`2025-01-01`–`2027-01-01` и временные таблицы одной откатанной target
транзакции. `mart.revenue_group_summary_daily` до и после запуска содержит
0 строк: `DELETE` и `INSERT` не были достигнуты, commit отсутствует.

Временный итог собирал статьи `02`, `05`, `06` непосредственно из exact
current-M source branches, а `03` и `04` — из выбранных в ADR-0010 reused
facts. Независимый current-M source extract сформировал все статьи `02`–`06`;
сравнение по ключу `дата × клуб × статья` обнаружило 7 608 различающихся
ключей.

## Материальное расхождение

| Статья | Exact current-M source | Approved reused fact | Отклонение reused − source |
|---|---:|---:|---:|
| `03.ДПФУ (ШТАТ)` | 645 039 335,27 | 639 598 901,43 | −5 440 433,84 |
| `04.ДПФУ (АРЕНДА ИП)` | 142 006 954,80 | 266 971 767,57 | +124 964 812,77 |

Для статьи `03` source extract вернул 8 306 дневных ветвей из `7575` и 248
из `7646`; reused fact содержит 504 691 detail-строку и 8 217 ключей
`дата × клуб`. Для статьи `04` source extract содержит 1 239 ключей, тогда
как reused `mart.ip_revenue_daily` — 32 830 detail-строк и 7 557 ключей
`дата × клуб`.

Это не допустимая разница снимка: в extract `03` reused-факта имеется
дополнительный обязательный join клиента, которого нет в current M; в extract
`04` reused-факта применён `ILIKE '%ИП%'`, тогда как current M применяет
`LIKE '%ИП%'`. Эти наблюдаемые расхождения реализации требуют отдельного
решения; причинность каждой суммы не предполагается без remediation-пакета.

## Почему первоначальный вывод отменён

Первое сравнение сопоставило живой source snapshot 1С с физическим содержимым
двух ранее загруженных reused facts. Это не одна точка во времени. Максимум
даты событий `2026-08-14` в reused facts не является временем их refresh и
не позволяет сделать вывод о различии методики. По явному уточнению
пользователя 20.08.2026 этот результат отменён; он не является `BLOCKER`.

## Корректная source-to-source сверка

После отмены первой сверки выполнили оба source extract в одной read-only
`REPEATABLE READ` транзакции 1С за BR-003 `2025-01-01`–`2027-01-01`:

| Статья | Current M | Exact source extract reused fact | Различающиеся ключи |
|---|---:|---:|---:|
| `03.ДПФУ (ШТАТ)` | 8 307 ключей / 645 039 885,27 | 8 307 / 645 039 885,27 | 0 |
| `04.ДПФУ (АРЕНДА ИП)` | 1 239 ключей / 142 006 954,80 | 7 634 / 267 937 422,21 | 7 578 |

Расхождение `04` объясняется наблюдаемым условием existing IP extract:
`ILIKE '%ИП%'` вместо current-M `LIKE '%ИП%'`. Регистронезависимый поиск
включает, например, «Клип карта ПТ (8*55 мин), Тренер фитнес, 30 дн»
(47 555 строк / 27 642 848,00), поскольку «Клип» содержит подстроку «ип».
Current M эти строки не включает. Это не эффект времени и не может быть
исправлено внутри S3-RGS-LOAD-001 без изменения reuse boundary.

## Нужное решение

1. Разрешить самостоятельный remediation-пакет `ip_revenue_daily`: заменить
   `ILIKE` на точный current-M `LIKE`, атомарно перезагрузить shared fact и
   его сверки; затем заново открыть initial load «Свода выручка ГК».
2. Разрешить самостоятельный пакет current-M-only для «Свода выручка ГК»:
   взять статью `04` напрямую из текущей source ветви, сохранив existing
   shared fact и все его потребители без изменений.

Внешние Excel-ветви, Power BI и источник 1С в обоих вариантах не меняются.

## Разрешение

Пользователь выбрал вариант 1 — единый remediation общего факта. Predicate
`ILIKE '%ИП%'` заменён на exact current-M `LIKE '%ИП%'`,
`mart.ip_revenue_daily` пересобран и сверён; затем обновлён ancillary shared
fact и выполнен initial load свода. Итоговый факт содержит 25 339 строк,
все branch/key/sum/rerun controls проходят. Этот blocker закрыт и остаётся
историческим evidence выбора BR-027.
