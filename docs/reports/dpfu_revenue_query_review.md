## Текущий отбор факта

Ветка `AccumRg7575`:

- тип номенклатуры `Услуга`;
- исключаются бизнес-направления `Членство` и `Прочие членство`;
- исключается `посещение клуба`;
- включаются семь фитнес-подразделений;
- сумма `Fld7586`, количество `Fld7585`.

Ветка `AccumRg7646`:

- исключаются типы `Услуга`, `Абонемент`, `ПодарочныйСертификат`;
- применяются те же ограничения направлений и подразделений;
- сумма `Fld7659`, количество `Fld7657`.

Обе ветки отбирают два полных предыдущих года и текущий год, объединяются через `UNION ALL` и оставляют только ненулевую стоимость.

## Критические наблюдения

1. Две ветки представляют разные регистры и разные виды бизнес-событий. До объединения нужно доказать отсутствие двойного учёта одной операции.
2. `Active` в регистрах, проведение/удаление регистраторов и пометка удаления справочников не проверяются.
3. Ключи `Recorder + LineNo` не выбираются. SQL сначала группирует по точному `_Period` и набору текстовых атрибутов, затем приводит период к дате; уникальность итоговой строки не определена.
4. Временная политика SQL всегда берёт два предыдущих года, а не подтверждённую сезонную политику проекта.
5. Связь основного клуба идёт по текстовому коду клиента. При нескольких действующих абонементах выбирается `MAX(название клуба)`, то есть лексикографически произвольный клуб.
6. Основной клуб доступа не требуется описанными страницами; факт должен использовать фактический клуб движения.
7. Возраст считается как дни / 365. Это приблизительно и некорректно на границах дня рождения.
8. Классификации услуги строятся частично по `ILIKE` на названии и частично внешним файлом. Переименование услуги может менять историю.
9. Внешний справочник услуг объединяется только по нормализованному названию. Уникальность соответствия не проверяется; дубли способны размножить сумму и количество.
10. `CASE` для `Вид занятий` возвращает одно и то же значение в обеих ветках и ничего не преобразует.
11. Кластер Кстово различается: SQL относит его к верхней части Физкульт, DAX и визуал показывают отдельный кластер `Кстово`.
12. `Клуб для учета <> 'Детский развивающий центр'` не соответствует значениям, создаваемым предыдущим CTE, и выглядит неработающим условием.
13. Девять колонок с `LAG` считаются по строкам с неоднозначным порядком при одинаковом времени. Описанные страницы не требуют истории по тренеру и предыдущему посещению.
14. Признак `Новый` жёстко присваивается только клиенту с кодом `И00050639`; это похоже на тестовый остаток и не описано бизнес-требованиями.
15. ФИО, дата рождения, контракт и основной клуб доступа увеличивают объём и объём персональных данных, хотя визуалы их не показывают.
16. Выручка ИП агрегируется до месяца через `date_trunc('month')`. Выбор части месяца может включить весь месяц либо не включить его вовсе.
17. Запрос количества ИП повторяет источники отчёта № 8, но использует `InfoRg7006.Period`, тогда как для отчёта № 8 пользователь подтвердил дату начала тренировки из документа.
18. Дневной план использует `COUNT(Fld6619)`, а не ресурс `SUM(Fld6621)`, и не фильтрует `Active`.
19. Два дополнительных набора дневного плана `(3)/(4)`, годовой бюджет, `Бюджет по клубам` и `Текущий план по выручке` отсутствуют в материалах.
20. DAX количества исключает аренду и по-разному обрабатывает ИП; DAX выручки суммирует весь факт. Средний чек использует ещё один контекст. Числитель и знаменатель требуют явного единого правила.
21. Полные меры `mФА ... direct`, сумма факторов и факт аренды ИП отсутствуют, поэтому факторный анализ нельзя воспроизвести доказательно.
22. `ORDER BY` в выгрузке не нужен Power BI и увеличивает работу источника.
23. Скриншоты дают контрольное доказательство разных баз: общая выручка `217,2 млн` включает `36,6 млн` ИП, структура показывает `180,6 млн`, а общее количество `133 379` исключает отдельную строку ИП `43 828`. Средний чек `1 352` рассчитан без ИП.
24. `SELECTEDVALUE` в количестве поддерживает одиночный выбор ИП, но при множественном выборе ИП вместе с частью штатных подразделений попадает в ветку без ИП. Множественный выбор может не складывать выбранные подразделения.
25. Визуал сворачивает возраст в три категории `Взрослые / Дети / Юниоры`, но в переданном SQL есть только десять числовых интервалов; правило свёртки не передано.

## Повторное использование

- `InfoRg7006` не выгружать второй раз: количество ИП должно приходить из общего факта `Тренировки ИП`.
- Клиентский уровень ДПФУ нужен и этому отчёту, и distinct-показателю ДПФУ в посещенческих отчётах. Общий источник возможен после унификации исключений.
- Справочник клуба должен один раз хранить сеть и кластер; эти тексты не нужно повторять в каждой строке факта.
- Планы имеют другую гранулярность и не должны присоединяться к факту услуг до Power BI с размножением строк.

## Проверки перед SQL

1. Уникальность `(Recorder, LineNo)` в обеих ветках и сохранение суммы после joins.
2. Пересечение операций `AccumRg7575` и `AccumRg7646`.
3. Суммы и количества с `Active`, сторно и возвратами.
4. Уникальность внешнего соответствия услуги.
5. Сверка одного клуба/месяца по факту, количеству, УЧК и среднему чеку.
6. Частичный месяц для выручки ИП.
7. Сверка плана из `COUNT(Fld6619)` и `SUM(Fld6621)`.
8. Факторное тождество: сумма факторов равна `Факт − План`.

## Решения пользователя от 2026-07-24

- общая выручка включает арендную выручку ИП, но услуги ИП не входят в общий объём и средний чек;
- поступления учитываются на дату движения;
- возвраты уменьшают сумму и количество, нулевые строки исключаются;
- выручка ИП — оплаты по рекуррентным договорам членства ИП;
- УЧК — среднее месячных distinct клиентов, регулярность — среднее месячных `Количество / УЧК`;
- набор исключений сохраняется по текущим мерам;
- факторный DAX разрешено пересобрать;
- бюджеты, планы и классификатор услуг остаются внешними;
- категории возраста: дети `<14`, юниоры `[14,18)`, взрослые `18+`;
- Кстово — отдельный новый кластер;
- refresh ежедневный.

Повторная проверка DAX закрыла вопрос `InfoRg6612`: количество этого регистра мерами не используется. План количества приходит из внешнего бюджета; из дневного планирования нужен только план выручки.
