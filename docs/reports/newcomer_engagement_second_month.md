Статус: `BUSINESS ANALYSIS COMPLETE / ARCHITECTURE DESIGNED / STAGE_2 SOURCE VALIDATION PARTIALLY VALIDATED — SV-076 / IMPLEMENTATION DEFERRED`.

`Вовлечение новичков2 месяц.docx`, извлечённые 2026-07-28, и PBIT

## Бизнес-вопрос

Показать вовлечение в посещения пар `клиент × контракт` с абонементом,
начавшимся в предыдущем относительно выбранного месяце, и сравнить долю пар с
четырьмя и более посещениями во втором календарном месяце с прошлым годом и
планом.

## Подтверждённая текущая логика

`CONFIRMED` по бизнес-описанию и текущему Power Query:

- когорта формируется по дате начала абонемента; Power Query создаёт
  `ДатаВовлечения = Date.StartOfMonth(Date.AddMonths(ДатаНачала, 1))`;
- при выборе месяца отчёт должен показывать абонементы, начавшиеся в
  предыдущем месяце; при выборе нескольких месяцев — соответствующие когорты
  для каждого месяца;
- посещения считаются в полуинтервале от первого дня месяца, следующего за
  началом абонемента, до первого дня ещё следующего месяца. Например, для
  начала 21.04.2026 это 01.05.2026–31.05.2026;
- группа посещений: `0`, `1`, `2`, `3`, `4+`; целевая регулярность — `4+`;
- KPI считает абонементы: всего, `4+`, долю `4+ / всего`, аналогичные KPI за
  прошлый год, прирост доли, план доли `доля ПГ + 2 п.п.` и план в штуках как
  `ROUNDUP(всего × плановая доля, 0)`;
- доступны фильтры месяца, клуба, возраста, стажа и группы посещений;
- список новичков содержит дату начала, текущее число посещений, последнюю
  дату посещения и признак прохождения бесплатной стартовой тренировки (СПТ).

Дополнительные решения пользователя от 2026-07-28:

- новичок — контракт со стажем `New`;
- все действующие фильтры текущих SQL-запросов являются полными для текущей
  бизнес-логики; не следует добавлять к ним гипотетические условия по
  `Active`, `Posted`, `Marked` или сторно без конкретного расхождения;
- связью визита с контрактом признана текущая пара
  `AccumRg7575.Fld7578 = контракт` и `AccumRg7575.Fld7576 = клиент`;
- посещения считаются именно способом, зафиксированным в текущем SQL:
  `COUNT` строк `AccumRg7575` в полном втором календарном месяце;
- возрастной фильтр сохраняет текущую реализацию: категория из `Reference87`
  для основной ветки и константа `Дети` для детских пакетов;
- СПТ определяется текущей логикой совпадения клиента и даты
  занятия/посещения с поиском действующего контракта;
- плановая доля равна доле прошлого года `+ 2 п.п.`; Excel-запрос не является
  источником этого планового правила.

В текущей модели присутствует отдельный Excel-запрос по плану клуба и года,
но подтверждённое правило плановой доли — `доля ПГ + 2 п.п.`. Следовательно,
Excel не является источником этого расчёта; его фактический потребитель в
предоставленном фрагменте модели не показан.

## Гранулярность и модель

| Набор текущей модели | Гранулярность | Статус |
|---|---|---|
| `Абонементы` | контракт × клиент × месяц вовлечения | PARTIALLY VALIDATED: 100-row source control без дублей; детская ветка имеет source duplicates |
| `ПосещенияНовичков_Агрегат` | контракт × клиент; число и последняя дата посещения за второй календарный месяц | CONFIRMED query |
| `СПТ_Уникальные` | контракт × клиент с признаком СПТ | VALIDATION_FAILED для one-to-one: raw match client × date one-to-many; legacy match сохраняется по BR-018 |
| `_Даты` | календарная дата | CONFIRMED query; активная связь с `Абонементы[ДатаВовлечения]` подтверждена PBIT |
| `_Клубы` | клуб | CONFIRMED query; активная связь с `Абонементы[КлубДоступа]` подтверждена PBIT; уникальность не проверена |
| `Выпускники план` | клуб × год | CONFIRMED current Power Query; PBIT подтверждает связь по клубу; уникальность не проверена |
| `Возраст` | возрастная категория | CONFIRMED disconnected table; PBIT показывает активную связь с `Абонементы[ВозрастнаяКатегория]` |

PBIT подтверждает десять активных однонаправленных связей, включая
`_Даты[Date] → Абонементы[ДатаВовлечения]`, клуб и возраст. В модели нет
ролей RLS. Кардинальности, уникальность ключей измерений и фактический
page/report filter остаются техническими проверками, а не предположениями.

## Сопоставление с существующей архитектурой

Пересечения с `mart.newcomer_engagement_milestone` и его mapping:

- общие физические источники: `Reference59`, `Reference141X1`,
  `Reference132`, `Reference163` и `AccumRg7575`;
- общая бизнес-сущность: New-контракт и посещения, связанные с контрактом;
- применимы подтверждённые проектные правила истории (BR-003), возрастных
  групп (BR-008), стабильного технического ключа клиента/контракта (BR-007),
  а также необходимость технически доказать связь посещения с контрактом
  (BR-012).

Повторное использование готового продукта невозможно: существующий факт имеет
grain `контракт × клиент × контрольная точка 7/14/21/28/30` и хранит накопления первых
30 календарных дней. Он не содержит число посещений за полный второй
календарный месяц и не позволяет вывести его без сырых событий. Общий
`mart.visit_client_day` также не подходит: у него нет контрактного ключа.

Архитектурное решение: `NEW` `mart.newcomer_engagement_second_month` по
ADR-0009. Новый контрактный факт имеет несовместимую с checkpoint-фактом
временную семантику; source-side логика проходит техническую валидацию перед
реализацией.

## Предварительная граница вычислений

Подтверждённая проектная граница вычислений:

- PostgreSQL: отбор подходящих контрактов, квалификация посещений, агрегация
  строго во втором календарном месяце, последняя дата посещения, категория
  `0/1/2/3/4+` и технические ключи;
- Power Query: импорт компактных наборов и типизация; не выполнять повторные
  interval/aggregation joins по сырым движениям;
- DAX: интерактивные counts, доли, прошлый год, план и условное
  форматирование;
- внешний Excel: оставить плановую долю вне PostgreSQL, пока не принято
  отдельное решение о его владении и загрузке.

## Учёт class-C критичности — 2026-08-13

Новый вопрос пользователю не требуется: BR-018 уже определяет единственно
допустимое поведение первого релиза. Для детских пакетов реализация сохраняет
каждую source-строку, отобранную current `RANK() = 1`, включая ties. Поэтому
3 144 повторные пары `contract × child` (7 093 строки, максимум 11) не
дедуплицируются и не заменяются на `ROW_NUMBER()`.

Это критично для SQL: текущие DAX-меры считают строки `Абонементы` без
`DISTINCT`, а скрытая свёртка изменит число новичков и долю `4+`. Логический
ключ `contract × client × month_of_engagement` нельзя объявлять физически
уникальным, пока Stage-3 plan не сохранит техническую identity child-строки
для воспроизведения ties. Это safeguards текущего результата, а не
методическое изменение.
