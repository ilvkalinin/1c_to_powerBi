# Query review: «Воронка. Лиды. Фитнес»

Статус: `BUSINESS REVIEW COMPLETE / TECHNICAL VALIDATION PARTIALLY VALIDATED (SV-078)`. Review
основан на полном доступном SQL/M/DAX, трёх скриншотах, полученных
2026-07-29, и PBIT `ВоронкаЛидыФитнес.pbit`, полученном 2026-07-31. Никаких
запросов к БД не выполнялось.

## `Задания 2026`

Основной запрос читает `Reference106`, фильтрует четыре воронки по GUID,
ограничивает создание задач календарным 2026 годом и исключает `Marked`.
Он присоединяет клиент, клуб, воронку, кампанию и её родителя, этап и причину
неуспеха. GUID сопоставляются с `New`/`Ex`/`Renew` и видами первого
взаимодействия. Затем M отбрасывает два значения причины дубля и
переклассифицирует тип первого взаимодействия.

### Тяжёлые и рискованные места

1. CTE `Documents` объединяет `Document329` и `Document279`, а `z` группирует
   `InfoRg7006` по `Period × client_code × service_description` без фильтров
   статусов, активности, проведения или удаления. Join `z` к задаче только по
   `z.Period = task.closed_at` и `z.client_code = task.client_code`.
2. Один клиент может иметь несколько услуг в одну дату закрытия, поэтому
   `z` потенциально создаёт несколько строк одной задачи. Даже если DAX
   использует `DISTINCTCOUNT(task_code)`, срез `Услуга` будет неоднозначен.
3. SQL задач отбирает только 2026, а записи начинают историю с 2025, ИП — с
   2024, а ДПФУ использует скользящее окно. Этот доступный запрос задач сам
   по себе не может воспроизвести сравнение с предыдущим годом из
   `SAMEPERIODLASTYEAR`; возможный отдельный запрос за 2025 не передан.
4. В SQL не отобраны `Posted` документов, `Active` регистра и не проверена
   допустимость `Marked`; это не меняет зафиксированную логику, но требует
   технической валидации до переноса.

## `Записи`

Набор складывает две ветки `InfoRg7006` — `Document329` и `Document279` — до
`дата × клиент × услуга`. Оставлены только `Enum448.EnumOrder = 1`; исключены
спецуслуга ИП, тип взаиморасчёта с сотрудником (только ПЗ) и один родитель
услуг (только ПЗ). Возможная строковая часть `Document329.VT4352` присоединена
как `LEFT JOIN`: её кардинальность не доказана и способна размножить записи.

## `ДПФУ факт` и `ИП`

`ДПФУ факт` объединяет `AccumRg7575`, `AccumRg7646` и ИП, а затем агрегирует
до `дата × клиент`. `ИП` выводит детальные квалифицированные тренировки из
`InfoRg7006`. `Сумма ДПФУ за 45 дней` фильтрует этот агрегат по равенству
`КодКлиента` и включающему окну `[ДатаСоздания.Date; +45 дней]`; затем это
значение формирует `КоличествоТренировок` для двух не-ДСУ воронок. Одно
событие ДПФУ может войти в результаты нескольких задач клиента при пересечении
окон — это подтверждённая текущая семантика.

## DAX и модель

- таблицы `_Маркетинговые кампании` и `_ТипыВзаимодействий` строятся из
  `Задания`; `_СпрСтажи` — статическая таблица `New`/`Renew`/`Ex`;
- `Есть запись` — task-stage classification: шесть явно заданных значений
  этапа, включая этапы уже состоявшегося посещения; это не счётчик строк
  набора `Записи`;
- `КоличествоТренировок`: `1` для трёх этапов «Пришел…», `0` для двух
  ДСУ-воронок вне этих этапов, иначе сумма количества ДПФУ по клиенту за 45
  дней; `ПришелНаТренировку = КоличествоТренировок > 0`;
- `УслугаДляЗаписи` берёт раннюю дату записи в интервале от создания до ранней
  из закрытия, принудительного закрытия и `+45`; при нескольких услугах в этот
  день current DAX применяет `MIN` без явно заданного бизнес-priority;
- меры `ФактЗаданий`, `Записи` и `ПришелНаТренировкуФакт` считают distinct
  `КодЗадания`; `Количество тренировок` складывает подготовленную колонку;
- у `ФактЗаданий` объявлены, но не используются переменные `EndDate` и
  `StartDate`; у меры `Записи` также объявлены, но не используются даты.
  Это лишняя вычислительная/сопроводительная сложность, не действующее
  бизнес-правило;
- `SWITCH` в мерах повторяет одинаковый результат `cm` для всех категорий.
  Логика не меняет результат и может быть устранена только при последующем
  рефакторинге модели, не в рамках текущего анализа;
- relationship view подтверждает активные single-direction связи справочников
  стажа, даты, клубов, кампаний и типов взаимодействия к `Задания`. Полная
  модель, в том числе отношения `ДПФУ факт`, не показана.

## Непроведённый пакет read-only валидации

Статус каждого теста: `VALIDATION_PENDING`.

Все нижеуказанные SQL-шаблоны имеют статус
`NOT_EXECUTED — ожидается подключение к корпоративной сети`. Перед запуском
во втором этапе `<source_schema>` заменяется подтверждённой схемой из
`pg_catalog`; это отдельная проверка V-01. Проверки выполняются только
read-only.

| ID | Проверка и ожидаемый результат |
|---|---|
| V-01 | В `pg_catalog` существуют все используемые отношения и колонки; физические типы `ID`, дат и ссылок зафиксированы. Ожидается один однозначный объект на имя, либо mapping уточняется. |
| V-02 | `Reference106.ID` и отображаемый код задания уникальны. Ожидается ноль дубликатов ID; уникальность кода подтверждается отдельно, иначе меры используют ID. |
| V-03 | Фильтр четырёх воронок и исключение двух причин воспроизводят контрольное число задач за месяц со скриншота после согласования срезов. Ожидается точное совпадение. |
| V-04 | После каждого dimension join task сохраняет одну строку. Ожидается `COUNT(*) = COUNT(DISTINCT task_id)` до намеренных bridge. |
| V-05 | CTE `z` и join по `close_datetime + client_code` не создают более одной услуги на задачу, либо текущий срез `Услуга` переносится в отдельный bridge. Ожидается ноль многозначных задач для current rule либо явно зафиксированная bridge-кардинальность. |
| V-06 | У `InfoRg7006 → Document329/Document279` ровно одна допустимая документная ветка на запись; `Document329.VT4352` не размножает исходную запись. Ожидается ноль строк с двумя ветками и сохранение строк после join. |
| V-07 | Статусы `Enum448`, `Active`, `Posted`, `Marked`, удаления и отмены соответствуют текущим фильтрам. Ожидается зафиксированный перечень допустимых значений и отсутствие неучтённых состояний. |
| V-08 | `Reference141X1.Code` уникален и одинаково представлен в `Задания`, `Записи` и `ДПФУ факт`. Ожидается ноль неоднозначных/несопоставимых кодов; current attribution использует именно код, а не ID. |
| V-09 | Границы времени: ДПФУ — включающий `[ДатаСоздания.Date; +45]`; услуга записи — включающий `[ДатаСоздания.Date; MIN(Закрытие, ПринудительноеЗакрытие, +45)]`; проверить границы, 29 февраля и закрытие до создания. Ожидается точное совпадение с calculated columns. |
| V-10 | Узкие случаи: один контракт с несколькими клиентами, детский пакет, ties нескольких задач/тренировок в один день, as-of история стажа, несколько заморозок, сотрудник на граничную дату и отсутствующие ссылки. Ожидается, что ни один случай не создаёт скрытый join и не изменяет число заданий; неприменимые случаи документируются `NOT_APPLICABLE`. |
| V-11 | Сверка сумм/количеств: distinct задач, stage-based задач с записью, задач с `training_count > 0` и сумма тренировок по тем же фильтрам Power BI. Ожидается совпадение с контрольными значениями, предоставленными владельцем отчёта. |
| V-12 | Изменения, удаления, повторный запуск, объём и производительность. Ожидается идемпотентный результат на одном входном срезе, зафиксированное окно исправлений и измеренный план/время до выбора хранения. |
| V-13 | Power BI contract: типы, NULL, уникальность будущих ключей, связи календаря/клубов/кампаний/типов, отсутствие many-to-many и корректность ПГ. Ожидается однозначная звёздная модель и одинаковые результаты DAX. |

### Выполнимые во втором этапе SQL-шаблоны

```sql
-- V-02: ключ задания
SELECT _IDRRef, COUNT(*)
FROM <source_schema>._Reference106
GROUP BY _IDRRef
HAVING COUNT(*) > 1;

-- V-05: размножение задачи текущим join услуги из M.
WITH documents AS (
    SELECT _IDRRef, _Fld4316RRef AS service_ref
    FROM <source_schema>._Document329
    WHERE _Fld4306 >= DATE '2026-01-01'
    UNION ALL
    SELECT _IDRRef, _Fld3226RRef AS service_ref
    FROM <source_schema>._Document279
    WHERE _Fld3218 >= DATE '2026-01-01'
), z AS (
    SELECT r._Period, c._Code, s._Description AS service_name
    FROM <source_schema>._InfoRg7006 r
    INNER JOIN documents d ON d._IDRRef = r._Fld7007_RRRef
    INNER JOIN <source_schema>._Reference141X1 c ON r._Fld7008RRef = c._IDRRef
    LEFT JOIN <source_schema>._Reference163 s ON d.service_ref = s._IDRRef
    GROUP BY r._Period, c._Code, s._Description
), current_task_join AS (
    SELECT t._IDRRef AS task_id, z.service_name
    FROM <source_schema>._Reference106 t
    LEFT JOIN <source_schema>._Reference141X1 c ON t._Fld1196RRef = c._IDRRef
    LEFT JOIN z ON z._Period = t._Fld1192 AND z._Code = c._Code
    WHERE t._Fld1191RRef IN (
        decode('99ad9b75dc73f34911eee5eefdcdd3b4', 'hex'),
        decode('99f6efa9e59a276811f0fcebecd498be', 'hex'),
        decode('99b19ba3029d764511ef394a0464555f', 'hex'),
        decode('99ad9b75dc73f34911eee5ea6f34a13b', 'hex')
    )
      AND t._Fld1193 >= DATE '2026-01-01'
      AND t._Fld1193 < DATE '2027-01-01'
      AND t._Marked = false
)
SELECT task_id,
       COUNT(*) AS joined_rows,
       COUNT(DISTINCT service_name) AS service_count
FROM current_task_join
GROUP BY task_id
HAVING COUNT(*) > 1 OR COUNT(DISTINCT service_name) > 1;

-- V-06: взаимоисключаемость документных веток и размножение VT4352.
SELECT r._Period, r._Fld7007_RRRef,
       COUNT(DISTINCT d329._IDRRef) AS prebooking_docs,
       COUNT(DISTINCT d279._IDRRef) AS group_docs,
       COUNT(vt._Document329_IDRRef) AS prebooking_lines
FROM <source_schema>._InfoRg7006 r
LEFT JOIN <source_schema>._Document329 d329 ON d329._IDRRef = r._Fld7007_RRRef
LEFT JOIN <source_schema>._Document279 d279 ON d279._IDRRef = r._Fld7007_RRRef
LEFT JOIN <source_schema>._Document329_VT4352 vt ON vt._Document329_IDRRef = d329._IDRRef
GROUP BY r._Period, r._Fld7007_RRRef
HAVING COUNT(DISTINCT d329._IDRRef) > 0 AND COUNT(DISTINCT d279._IDRRef) > 0;
```

V-08/V-09 выполняются после проверки схемы и типов: правило атрибуции теперь
подтверждено DAX, но физическая уникальность кода, типы дат и набор строк
`ДПФУ факт` требуют read-only валидации.
