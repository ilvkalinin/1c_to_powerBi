# Требования отчёта: «Выручка рецепции»

Статус: `BUSINESS LOGIC COMPLETE / TECHNICAL VALIDATION DEFERRED`.
Договорный отчёт № 18. SQL, физические таблицы и проверки на БД не создаются.

## Назначение

Показать структуру фактической выручки рецепции, количество проданных услуг и
товаров, среднюю цену, выполнение среднесрочного плана, динамику и рейтинги
клубов и сотрудников.

## Страницы

1. `Общий` — факт/цель, количество, средняя цена, рейтинг клубов, подневная
   динамика факта и плана.
2. `Номенклатуры` — структура и динамика по категории и номенклатуре.
3. `Сотрудники` — иерархия сотрудник → категория → номенклатура.
4. `Рейтинги` — полотенца/халаты, шкафчики, солярий, товары рецепции.
5. `План/Факт` — накопительные факт и линейный план, прогноз и цвет выполнения.

## Фильтры и разрезы

- дата/диапазон дат;
- клуб либо сеть;
- вид деятельности;
- сотрудник;
- категория номенклатуры;
- номенклатура.

## Метрики

| Метрика | Правило / статус |
|---|---|
| `Выручка факт` | сумма знаковых движений стоимости |
| `Цель` | среднесрочный план; источник не передан |
| `Количество услуг` | сумма ресурса количества |
| `Средняя цена услуги` | скриншоты подтверждают `Выручка / Количество`, без умножения на 100 |
| `Доля выручки` | выручка строки / выручка в текущем выбранном контексте |
| `Прогноз` | факт / прошедшие дни × число дней месяца; границы выбора требуют решения |
| `Выполнение плана` | факт − план и процент к плану |

Контроль со скриншота: `71 414 / 745 ≈ 96`, поэтому формула бизнес-текста с
`× 100%` противоречит фактическому визуалу.

## Переданные меры

```DAX
_НакИтогДеньгиПлан =
CALCULATE(
    SUM('План'[План на день]),
    DATESMTD('Даты'[Date])
)
```

```DAX
_НакИтогДеньгиФакт =
CALCULATE(
    SUM('ВыручкаДУ'[Поступления]),
    DATESMTD('Даты'[Date])
)
```

```DAX
%Изм-еПланФакт =
DIVIDE(
    SUM('ВыручкаДУ'[Поступления]),
    SUM('План'[План на день])
)
```

Мера корректно передаёт KPI-карточке коэффициент выполнения плана. Карточка
Power BI сама отображает относительное отклонение от цели, поэтому при
`Факт / План = 141,96%` подпись показывает `+41,96%`.

```DAX
АбсИзм-еПланФакт =
SUM('ВыручкаДУ'[Поступления]) - SUM('План'[План на день])
```

```DAX
ПрогнозВыр =
SUM('ВыручкаДУ'[Поступления])
    / DAY(LASTDATE('ВыручкаДУ'[_Дата]))
    * DAY(EOMONTH(LASTDATE('ВыручкаДУ'[_Дата]), 0))
```

План остаётся внешней Excel-таблицей Power BI и не переносится в PostgreSQL.

Подтверждённая целевая версия прогноза:

```DAX
Прогноз выручки =
VAR MinSelectedDate =
    MINX(ALLSELECTED('Даты'[Date]), 'Даты'[Date])
VAR MaxSelectedDate =
    MAXX(ALLSELECTED('Даты'[Date]), 'Даты'[Date])
VAR OneMonthSelected =
    YEAR(MinSelectedDate) = YEAR(MaxSelectedDate)
        && MONTH(MinSelectedDate) = MONTH(MaxSelectedDate)
VAR MonthStart =
    DATE(YEAR(MaxSelectedDate), MONTH(MaxSelectedDate), 1)
VAR FactMTD =
    CALCULATE(
        SUM('ВыручкаДУ'[Поступления]),
        DATESBETWEEN('Даты'[Date], MonthStart, MaxSelectedDate)
    )
RETURN
    IF(
        OneMonthSelected,
        DIVIDE(FactMTD, DAY(MaxSelectedDate))
            * DAY(EOMONTH(MaxSelectedDate, 0)),
        BLANK()
    )
```

Прогноз использует выбранную календарную дату, не зависит от наличия продажи
в последний день и возвращает `BLANK()` для выбора нескольких месяцев.

## Предварительная гранулярность

Факт:

> дата движения × клуб × продавец × номенклатура × вид деятельности ×
> категория рецепции × тип исходного регистра.

Показатели строки:

- знаковое количество;
- знаковая выручка.

План хранится отдельно во внешнем Excel. PostgreSQL не изменяет и не
пересобирает его. Логическая структура Power BI зафиксирована в data contract;
точная схема связей плана проверяется при сборке модели.

## Повторное использование

`AccumRg7575` и `AccumRg7646` уже разобраны для «Выручки ДПФУ». Не создавать
копию этих регистров под рецепцию. Кандидат — общий квалифицированный факт
движений дополнительных услуг и товаров с общими измерениями даты, клуба,
продавца, услуги и вида деятельности. Каждый отчёт получает собственный
агрегированный view и собственные фильтры.

Архитектурное направление зафиксировано в
[`ADR-0005`](../adr/0005-shared-ancillary-revenue.md): общий отфильтрованный
факт движений и обычный локальный view рецепции. Решение остаётся
`PROPOSED / BLOCKED BY TECHNICAL VALIDATION`, пока не доказаны отсутствие
двойного учёта и семантика продавца.

## Принятые текущие правила

- дата факта — `_Period` соответствующего регистра;
- средняя цена — выручка / количество, без `× 100%`;
- отрицательные движения уменьшают количество и выручку;
- сохраняются текущая классификация и report-level исключения;
- Excel-план используется как есть;
- скриншот регистра подтвердил: `AccumRg7575.Fld7582` — исполнитель услуги, а
  не продавец;
- целевой кандидат продавца — `Document346.Fld4909 Сотрудник` из чека ККМ;
- `AccumRg7646.Fld7652` сверяется с сотрудником чека, при расхождении
  приоритет имеет подтверждённый реквизит документа.

## Реальные слабые места, требующие решения

1. Для рейтинга продавцов требуется технически проверить связь
   `AccumRg7575.Основание → Document346` и выбрать между полями документа
   `Сотрудник` и `Консультант`. Предварительный выбор — `Сотрудник`.
2. Возможное пересечение товаров двух регистров проверяется на БД.
