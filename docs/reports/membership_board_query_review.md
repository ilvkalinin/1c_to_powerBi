# Query review: «Отчёт членство для правления»

Статус:
`LOCAL QUERY/MODEL REVIEW COMPLETE / SHARED SOURCE TECHNICAL VALIDATION COMPLETE — SV-083, SV-105, SV-107, SV-112—SV-130 / SHARED SCHEMA IMPLEMENTED; BOARD RECONCILIATION AFTER INITIAL LOAD`.

Разобраны DOCX (16 отрендеренных страниц) и PBIT: 81 таблица, 88 связей,
22 M-expression, 263 меры, 310 calculated columns и 29 видимых страниц.
Для сравнения использован актуальный PBIT «Отчёта по поступлениям»: 108

## Вывод сравнения

Board-PBIT является производным и частично устаревшим вариантом модели
поступлений. Его пользовательская ценность — новые представления, базы
сравнения и факторный анализ. Его расхождения подготовки факта и пяти KPI
отклонены решением пользователя в пользу оперативного PBIT.

## Повторно используемые наборы

Полностью повторно используются запросы и логические источники, разобранные в
`membership_receipts_query_review`:

- `AccumRg7370` и документные ветви контрактных поступлений;
- `AccumRg7739` и утверждённые membership-услуги;
- `AccumRg7478/7646` и расчёт заморозки/цены;
- контракты, продукты, клубы, сотрудники и календарь;
- текущий и среднесрочный планы Power BI.

Новых источников 1С для board-отчёта не обнаружено.

SV-105 выполнил full-year source observation shared domain: в 2026 есть
46 416 неактивных движений контрактных авансов, а у membership-услуг
неактивных строк в этом срезе нет. Это не даёт права менять state/sign filter:
его допустимость по-прежнему определяется current M через документ-регистратор.

SV-112 подтвердил для board-reused contract-advance branch current-M знак на
98 127 включаемых распознанных движениях 2026: все они проведены и не
помечены на удаление; правило не расширено новым state/filter. Физическая
ветка `ПКО × RecordKind=1` не встретилась в 2025–2026 и остаётся preserved,
но не наблюдённой.

SV-113 подтвердил, что 14 document-recorder joins shared contract-advance
ветви не размножают строки и суммы. Другие joins и board-reconciliation
остаются отдельными проверками.

## Расхождения подготовки с эталонным PBIT

| Область | Board-PBIT | Актуальный «Отчёт по поступлениям» | Решение |
|---|---|---|---|
| страницы | отдельные 29 board-страниц | отдельные 30 оперативных страниц | сохраняются оба presentation layer |
| годовые факты | 2025–2026 | актуальный PBIT также содержит исторические служебные ветви, но target следует BR-003 | эталонная история BR-003 |
| номенклатура | нет актуальных `Наименование`, `ВозрастнаяКатегория` | поля присутствуют | эталон — актуальный справочник |
| авансы | 65 колонок и служебные `_123`, `СуммаФинал`, `вфычфыа` | 69 колонок, актуальные ключ, роли клуба, зона доступа и продуктовые признаки | эталон — оперативная подготовка |
| услуги | board хранит `ДокументПродажи` и старый возрастной helper | оперативная модель хранит актуальные `Оплата` и `Зона доступа` | эталон — оперативная подготовка |
| текущий план | нет четырёх колонок нового коэффициента дня | оперативная модель содержит их | эталон — оперативная подготовка |
| связи | board добавляет связи агрегата и годового плана, но не содержит актуальные role-playing связи продукта/клуба | оперативная модель содержит актуальные связи | общая целевая звезда из mapping поступлений |
| календарь | 27 автоматических `LocalDateTable_*` | 55 автоматических таблиц | обе реализации отклонены; нужен один явный календарь с ролями дат |

Имена `вфычфыа`, `_123` и аналогичные helpers не являются целевыми
бизнес-полями.

## Сравнение общих мер

Из 56 мер с одинаковыми именами 30 имеют одинаковые выражения, 26 различаются.

| KPI | Сравнение PBIT | Принятое правило |
|---|---|---|
| `Пост Факт` | выражение совпадает | BR-015/016 |
| `Кол Факт` | выражение различается | один контракт предоплаты / один ежемесячный платёж рекарринга |
| `ЦенаКонтр ФактИтог` и helpers | выражения различаются | эталонная формула `membership_receipts` |
| `Прод Факт` | выражение различается | эталонный квалифицированный KPI-набор и `30.42` |
| `ЦенаМес ФактИтог` и helpers | выражения различаются | цена контракта / продолжительность |

Board-only меры переключателей, светофоров, долей, презентаций и факторного
анализа допустимы как производные. Они не могут переопределять пять KPI.

## Модельные риски

1. Агрегат связан только с датой, клубом и суперстажем; часть его атрибутов
   хранится прямо в таблице. Это может давать другой filter propagation, чем
   детальный факт.
2. В агрегат уже записаны неаддитивные средние и плановые helpers. Повторное
   усреднение или суммирование способно изменить результат.
3. `Поступления` включают membership-услуги, а четыре контрактных KPI — нет;
   единый общий знаменатель запрещён.
4. Годовой, текущий и среднесрочный планы имеют собственные grain. Прямые
   joins к движениям создадут размножение.
5. Текущий board-PBIT опирается на устаревшие calculated columns и связи;
   переносить их в PostgreSQL без эталонного mapping запрещено.

## Непроведённый пакет проверок

Общий source-side домен частично проверен в SV-083: оба регистра и контрактные
справочники существуют, а в bounded срезах технические ключи уникальны и не
имеют orphan-contract. Это не подтверждает business sign, recurring-payment
key, состояния или полный полиморфный домен. Board-специфичные проверки ниже
не выполнялись: им требуется будущий физический домен Stage 3 либо внешние
планы, которые остаются вне границы проекта.

Сначала выполняется полный пакет MR-V01–MR-V12 из
`membership_receipts_query_review.md`. После него:

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| MB-V01 | пять KPI двух отчётов по одинаковым месяц×клуб×суперстаж×возраст×тип оплаты | точное равенство до принятого округления |
| MB-V02 | факт по resource/club/month из детального домена против `___Итого по сети` | одинаковые суммы; отсутствие строк, потерянных или размноженных агрегированием |
| MB-V03 | переключатель `план годовой / план текущий / пред. год` | меняется только база; факт остаётся неизменным |
| MB-V04 | уникальность внешних планов на их заявленном grain | не более одной строки на ключ плана; totals совпадают с контрольным файлом |
| MB-V05 | сумма компонентов факторного анализа против общего отклонения | расхождение только в пределах округления |
| MB-V06 | фильтрация по календарю, клубу, суперстажу, возрасту и типу оплаты | один и тот же фильтр меняет оба отчёта одинаково |
| MB-V07 | страницы месяц/YTD и прошлый год | корректные границы периода; нет смешения movement date и KPI date |
| MB-V08 | refresh и самые тяжёлые матрицы board-отчёта | укладываются в согласованный SLA; решение об агрегате принимается только по измерению |

Форма read-only reconciliation после появления физического объекта:

```sql
-- VALIDATION_PENDING / NOT_EXECUTED
-- Параметры: metric_date_from, metric_date_to, club_id, super_stage,
-- product_age_category, payment_type.
-- Один и тот же запрос выполняется для набора «Отчёта по поступлениям»
-- и потребителя board-отчёта.
SELECT
    metric_date,
    club_id,
    super_stage,
    product_age_category,
    payment_type,
    SUM(receipt_amount) AS receipts,
    COUNT(DISTINCT kpi_unit_key) AS units
FROM <validated_membership_domain>
WHERE metric_date >= :metric_date_from
  AND metric_date <  :metric_date_to
GROUP BY 1, 2, 3, 4, 5;
```

`<validated_membership_domain>` не заменяется физическим именем до
архитектурного решения и серверной валидации.

## Учёт class-C критичности — 2026-08-13

Новое решение не требуется. В будущей реализации board-страницы используют
эталонные пять KPI «Отчёта по поступлениям»: рекарринг считается по
ежемесячному платежу, роли receipt/metric date остаются разными, а средние,
доли и factor helpers не суммируются из `___Итого по сети`. Перед product
admission требуются уже названные physical key/state controls и MB-V01—MB-V08;
повторный Stage-2 прогон без нового независимого триггера запрещён.
