### Модельные дефекты, важные для целевой схемы

1. `Кол Факт`, средняя цена и продолжительность читают `Таблица Активных
   Контрактов`, но эта таблица не связана с `Сотрудники` и role клуба продажи.
   Поэтому менеджер и клуб продажи могут фильтровать поступления, но не четыре
   контрактных KPI.
2. В пяти основных фактах/планах 205 колонок, и ни одна не скрыта. Технические
   ключи и неаддитивные helper-колонки доступны пользователю.
3. Модель содержит 55 автоматических `LocalDateTable_*` наряду с общим
   календарём.
4. PBIT не содержит RLS-ролей; при этом в модели присутствуют ФИО, телефон и
   коды клиентов. Целевой набор по-прежнему исключает PII.

## Подтверждённые дефекты и риски текущей реализации

1. Текущий grouping количества должен быть приведён к подтверждённой
   гибридной единице: один контракт предоплаты или один ежемесячный платёж
   рекарринга.
2. Справочник типа оплаты должен объединить `Кредит` и `Бесплатный` с
   `Предоплата`.
3. Справочник канала должен содержать все шесть значений, включая редко либо
   никогда не встречающиеся `Website` и `App сотрудника`.
4. Текущая `Детские секции` должна быть преобразована в `Дети`, а
   справочник сокращён до `Взрослые/Дети/Юниоры`.
5. Цена и длительность используют club-specific расчёт, а поступления —
   фактические движения; пять карточек нельзя выводить из одного агрегата.
6. `Table.Distinct` применяется после потенциально размножающих joins.
7. Исторические Power Query физически дублируются по годам; в целевой модели
   нужен один параметризованный extract с полуинтервалом BR-003.
8. Excel-планы остаются в Power BI и не должны попасть в PostgreSQL-витрины.
9. Hard-coded GUID, названия клубов и поиски подстрок не имеют справочника
   эффективных дат.
10. Текущая модель импортирует PII без подтверждённого визуального
    потребителя.

### MR-V02: ключи и состояния

```sql
WITH x AS (
  SELECT '7370' AS source_kind, _RecorderRRef AS recorder_id,
         _LineNo AS line_no, _Active AS active, _RecordKind AS record_kind,
         _Period AS event_at, _Fld7377 AS amount
  FROM _AccumRg7370
  UNION ALL
  SELECT '7478', _RecorderRRef, _LineNo, _Active, _RecordKind,
         _Period, _Fld7481
  FROM _AccumRg7478
  UNION ALL
  SELECT '7646', _RecorderRRef, _LineNo, _Active, _RecordKind,
         _Period, _Fld7659
  FROM _AccumRg7646
  UNION ALL
  SELECT '7739', _RecorderRRef, _LineNo, _Active, _RecordKind,
         _Period, _Fld7749
  FROM _AccumRg7739
)
SELECT source_kind, active, record_kind,
       count(*) AS rows_total,
       count(*) FILTER (WHERE recorder_id IS NULL OR line_no IS NULL) AS null_key_rows,
       count(*) - count(DISTINCT (recorder_id, line_no)) AS duplicate_rows,
       count(*) FILTER (WHERE amount IS NULL) AS null_amount_rows,
       count(*) FILTER (WHERE amount < 0) AS negative_amount_rows
FROM x
GROUP BY source_kind, active, record_kind;
```

Ожидание: `null_key_rows=0`, `duplicate_rows=0`; распределение состояний и
знаков фиксируется до выбора production-фильтра.

### MR-V08: ties предыдущего контракта

```sql
WITH ranked AS (
  SELECT _Fld681RRef AS client_id, _IDRRef AS contract_id,
         _Fld671 AS start_date, _Fld672 AS end_date,
         dense_rank() OVER (
           PARTITION BY _Fld681RRef
           ORDER BY _Fld671 DESC
         ) AS start_rank
  FROM _Reference59
)
SELECT client_id, start_date, count(*) AS tied_contracts
FROM ranked
WHERE start_rank = 1
GROUP BY client_id, start_date
HAVING count(*) > 1;
```

Фактический current-PBIT результат SV-116: в scope 2025–2026 есть 508 пар
`клиент × дата активации` с несколькими договорами (518 избыточных договоров,
максимум 4). PBIT не задаёт вторичный порядок и не использует `MIN(contract_id)`;
его результат сохраняется по BR-018 без нового tie-break.
