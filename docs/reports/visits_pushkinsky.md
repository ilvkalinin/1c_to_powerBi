## Показатели из бизнес-описания

### Структура клиентской базы

| Показатель | Описание | Статус |
|---|---|---|
| `Итого КБ` | distinct клиентов с абонементом на снимок 00:00: начало `< D`, окончание `>= D−1` | CONFIRMED — единое целевое правило пользователя |
| `Активная база` | действующие члены, посетившие Пушкинский в `[D-30, D)`, но не посетившие его в D | CONFIRMED — DAX и scope текущего запроса |
| `Неактивная база` | `Всего КБ - Посетили ЧК на дату - Активная база` | CONFIRMED — DAX |
| `ЧК не пришёл в клуб` | члены Пушкинского без посещения в выбранный день | CONFIRMED concept |

Подтверждённое равенство:

> `Итого КБ = Активная база + Неактивная база + Посещения ЧК`.

Например, 01.12.2025: `1 838 + 598 + 736 = 3 172`. Название `Активная база` на странице означает именно активных не-посетителей дня, а не всю активную базу.

### Посещения членов клуба

| Показатель | Описание | Статус |
|---|---|---|
| `Посещения ЧК` / `Посещения всего` | distinct клиентов с основным и фактическим клубом Пушкинский в фильтр-контексте | CONFIRMED — DAX |
| `Посещения ГП` | бесплатные групповые программы | CONFIRMED concept |
| `Посещения по купону` | услуги по купонам | CONFIRMED concept |
| `Посещения ДПФУ` | distinct клиентов из `Посещения проверка ДПФУ` | CONFIRMED — DAX выбирает узкую версию |
| `С тренером` | ГП + купон + ДПФУ | CONFIRMED по итоговой формуле; ИП отдельно не включён |
| `Без тренера` | `Посещения всего - (ГП + ДПФУ + купон)` | CONFIRMED — DAX пользователя |

Отрицательные значения `Без тренера` присутствуют в визуале, поэтому пересечения категорий либо различие denominator уже существуют в текущей модели.

### Посещения не членов клуба

| Показатель | Описание | Статус |
|---|---|---|
| `Посещения Гостевой визит` | посещения по гостевому визиту | CONFIRMED concept |
| `Посещения VIP` | посетители с основным клубом Пушкинский VIP | CONFIRMED concept |
| `Посещения ДРЦ` | посетители с основным клубом ДРЦ, кроме Продлёнки и Умняшек | CONFIRMED — решение пользователя |
| `Посещения Продлёнка` | ДРЦ, услуга содержит `продленка/продлёнка` | CONFIRMED current rule |
| `Посещения Умняшки` | ДРЦ, услуга содержит `умняши` | CONFIRMED current rule |
| `Посещения не ЧК` | гостевой визит + VIP + ДРЦ + Продлёнка + Умняшки | CONFIRMED BY DAX composition |
| `Итого посещения` | `Без тренера + ГП + купон + ДПФУ + ГВ + ДРЦ + VIP + Продлёнка + Умняшки` | CONFIRMED — DAX |

Все client-based категории используют `DISTINCTCOUNT` в текущем фильтр-контексте и несуммируемы по датам. Итог складывает категории без межкатегорийной дедупликации.

## Предварительное повторное использование

`ASSUMPTION`: не создавать отдельную полную копию посещений Пушкинского. Общий обезличенный client-day слой, намеченный для «Посещения Физкульт», можно расширить:

- включить фактический клуб Пушкинский;
- сохранить стабильный обезличенный client key;
- добавить признаки текущего основного клуба/типа доступа;
- добавить флаги гостевого визита, VIP, ДРЦ, Продлёнки и Умняшек;
- использовать общий дневной агрегат ГП.

Дневная структура КБ хранится готовыми количествами когорт в общем объекте `дата × клуб`, где уже находится дневной показатель ГП. Отдельная таблица только для КБ Пушкинского и client-level снимок всей КБ на VM-2 не нужны.

## Единое правило членства

Пользователь подтвердил применение общего снимка на 00:00:

- абонемент с началом в D ещё не входит;
- абонемент с окончанием в D−1 входит;
- условие целевого membership set: `ДатаНачала < D` и `ДатаОкончания >= D−1`.

Это правило намеренно заменяет граничное поведение текущего DAX Пушкинского и совпадает с отчётом «Клиентская база». Расчёт membership interval реализуется один раз для обоих отчётов.

Активность подтверждённо считается только по посещениям Пушкинского действующими членами Пушкинского: мера использует таблицу `Посещения всего`, а её SQL фильтрует и фактический, и основной клуб как Пушкинский.

Детские пакеты в Пушкинском отсутствуют и в расчёт КБ не входят.

`Посетили ЧК на дату` — служебный показатель, на который ссылается формула неактивной базы:

> distinct действующих членов Пушкинского, имеющих посещение Пушкинского в D.

Для одной выбранной даты он совпадает по множеству клиентов с текущей мерой `Посещения всего`. Предоставленная DAX-мера подтверждает это и не требует отдельного источника.

## Полученный DAX

Полная активная версия предоставленных мер сохранена в `docs/source_reports/visits_pushkinsky/DAX основные меры.txt`.

Ключевые свойства:

- `SELECTEDVALUE` требует одну дату для показателей КБ;
- активное окно фактически `[D-30, D)`, потому что посетители D исключаются;
- `Посещения проверка ДПФУ` окончательно выбирает одноимённый узкий запрос, а не `Посещения платно ДПФУ`;
- гостевой визит, VIP, ДРЦ, Продлёнка и Умняшки считаются как distinct клиентов;
- `Итого посещения` намеренно складывает готовые меры.

Полученная мера:

```DAX
Посетили ЧК на дату =
VAR ТекущаяДата =
    SELECTEDVALUE ( 'СпрДата'[Date] )
RETURN
    IF (
        ISBLANK ( ТекущаяДата ),
        BLANK (),
        CALCULATE (
            DISTINCTCOUNT ( 'Посещения всего'[КодКлиента] ),
            REMOVEFILTERS ( 'СпрДата'[Date] ),
            'Посещения всего'[_period] = ТекущаяДата
        )
    )
```

Полученная мера:

```DAX
Без тренера =
[Посещения всего]
    - (
        [Посещения ГП]
            + [Посещения проверка ДПФУ]
            + [Посещения по купону]
    )
```

Исправленное правило ДРЦ: услуга не должна относиться ни к Продлёнке, ни к Умняшкам. Технически все условия исключения должны соединяться через `AND`, а не через текущий `OR`.

Общее архитектурное решение двух посещенческих отчётов: `docs/adr/0003-shared-visits-domain.md`.
