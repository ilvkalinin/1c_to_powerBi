# Требования отчёта: «Выручка ДПФУ»

Статус: `BUSINESS LOGIC COMPLETE / PHYSICAL DESIGN DEFERRED`. Получены бизнес-описание, текущие SQL/M, часть DAX, десять визуалов и ответы пользователя. SQL, физические таблицы и проверки на БД не создаются.

## Назначение

Договорный отчёт № 29 показывает по группе компаний:

- факт выручки ДПФУ;
- количество оказанных платных услуг;
- средний чек;
- сравнение с годовым бюджетом, текущим планом и предыдущим годом;
- структуру показателей;
- факторный анализ отклонения выручки.

## Страницы

### Динамика выручки

Фильтры: период, сеть/клуб, подразделение.

Показатели:

- выручка ДПФУ;
- план С/С и отклонение выручки;
- количество оказанных услуг;
- плановое количество и отклонение;
- средний чек;
- предыдущий год;
- рейтинги клубов и структура по подразделениям.

### Структура выручки

Дополнительный фильтр: возрастная группа.

Разрезы:

- подразделение;
- формат тренировки;
- возрастная группа;
- иерархия `Формат тренировки → Наименование услуги`.

### Факторный анализ

Отклонение факта от среднесрочного плана раскладывается в порядке:

1. УЧК;
2. регулярность;
3. средний чек;
4. ИП;
5. прочее.

Описание подтверждает метод цепных подстановок, но полные прямые DAX-формулы факторов в техническом документе отсутствуют.

### Для правления — Отчет 3

Иерархия: кластер → клуб.

Показатели:

- план С/С за месяц;
- текущий план за весь месяц;
- текущий план за выбранные дни;
- факт за выбранные дни;
- выполнение текущего плана.

Есть переключатель `ИП / Штат`; без выбора показывается общий итог.

### Для правления — Отчет 4

Иерархия: кластер → клуб.

Показатели:

- план С/С;
- факт;
- отклонение факта от плана в рублях и процентах;
- факт аналогичного периода прошлого года;
- отклонение от прошлого года в рублях и процентах.

## Разные базы текущих показателей

Визуалы и DAX подтверждают, что показатели сейчас намеренно или случайно используют разные наборы строк:

- общая карточка выручки: `217,2 млн`, включая `36,6 млн` ИП;
- выручка страницы структуры: `180,6 млн`, без ИП;
- общее количество: `133 379`, без `43 828` услуг ИП;
- строка подразделения ИП отдельно показывает эти `43 828` услуг;
- средний чек `1 352` соответствует `180,6 млн / 133 379`, то есть также исключает ИП.

Это поведение подтверждено пользователем. ИП — тренеры, которые платят аренду по рекуррентным договорам членства. Стоимость их собственных услуг неизвестна, а сами услуги заносятся не всеми ИП и не полностью. Поэтому:

- арендная выручка ИП входит в общую выручку;
- услуги ИП не входят в общее количество услуг;
- ИП не влияют на средний чек;
- при выборе только ИП их неполное количество может показываться отдельно как справочный показатель.

## Подтверждённые правила

- поступления штата — сумма на дату движения в `AccumRg7575` и `AccumRg7646`;
- возвраты/сторно уменьшают сумму и количество;
- строки с нулевой стоимостью исключаются;
- выручка ИП — оплаты по рекуррентным договорам членства ИП;
- выручка ИП учитывается на фактическую дату движения, без `date_trunc('month')`;
- `Ср/мес. УЧК` — среднее месячных distinct клиентов;
- регулярность — среднее месячных отношений `Количество услуг / УЧК`;
- клиент двух клубов считается в каждом клубе и один раз на уровне сети;
- для количества, УЧК, регулярности и среднего чека используется текущий набор мер: штатные `Прочие услуги`, без аренды и ИП; отдельные исключения гостей, сотрудников и купонов текущими мерами не задаются;
- факторный анализ можно пересобрать по подтверждённому порядку цепной подстановки;
- бюджеты, дополнительные планы и классификатор услуг остаются внешними файлами;
- возраст определяется на дату движения: `Дети` — `[0,14)`, `Юниоры` — `[14,18)`, `Взрослые` — `[18,+∞)`;
- Кстово — отдельный новый кластер и не включается в исторические кластеры при сравнении с прошлым годом;
- обновление — один раз в день.

## Предварительная минимальная гранулярность факта

Для штатных ДПФУ кандидат:

> дата оказания × фактический клуб × клиент × услуга × подразделение × формат тренировки × техническая категория расчёта.

В строке суммируются количество и выручка. Клиентский уровень необходим для УЧК и регулярности; услуга, подразделение, формат и возрастная группа необходимы странице структуры. ФИО клиента, дата рождения и ФИО сотрудника показанными страницами не используются.

До архитектурного решения отдельно рассматриваются:

- факт оказанных услуг и выручки;
- уже спроектированный общий факт `Тренировки ИП`;
- плановые показатели с другой гранулярностью.

Их нельзя механически соединять строка-к-строке: фактические услуги, тренировки ИП, месячная выручка ИП и планы имеют разные бизнес-события.

## Кандидаты повторного использования

1. `Тренировки ИП` из отчёта № 8 должны повторно использоваться для количества услуг ИП, без второй выгрузки `InfoRg7006`.
2. Клиентский факт ДПФУ потенциально может заменить отдельную классификацию ДПФУ в посещенческих отчётах, если совпадут фильтры сотрудников, купонов, клубов и дат.
3. Тот же факт почти наверняка потребуется отчётам `KPI Фитнеса`, `Записи администраторов` и `Свод выручка ГК`, но это пока `ASSUMPTION`.
4. Годовой и текущий планы можно объединить в один плановый факт только после получения их схем и подтверждения совместимых измерений.

## Минимальная логическая модель

Новые копии по страницам не создаются.

1. `Оказанные услуги ДПФУ` — один квалифицированный дневной факт:
   - штатные услуги содержат клуб, обезличенного клиента, услугу, количество и выручку;
   - оплаты ИП содержат дату, клуб и выручку, но не участвуют в количестве, УЧК и среднем чеке;
   - тип строки позволяет общей выручке включать ИП, а структурным мерам исключать их.
2. `Текущий план ДПФУ` — компактный дневной план `дата × клуб × подразделение` только с плановой выручкой.
3. `Тренировки ИП` — уже спроектированный общий факт; повторно используется только для справочного количества услуг ИП.
4. Годовой бюджет, бюджет количества, дополнительные планы и классификатор услуг остаются внешними источниками Power BI по решению пользователя.

Физический тип объектов, способ загрузки и полный контракт Power BI не выбираются до технической проверки ключей, связей, типов и объёмов.

## Не переносить без подтверждённого потребителя

- ФИО клиента;
- дату рождения после расчёта возрастной группы;
- ФИО сотрудника;
- код и название контракта;
- основной клуб доступа клиента;
- предыдущие посещения по клиенту, клубу, сети и тренеру;
- разницы между посещениями и флаги прошлого месяца;
- тестовый признак типа клиента по одному жёстко заданному коду;
- дублирующие кластер и сеть внутри факта — они должны определяться справочником клуба.

## Разрешённое расхождение планового количества

Повторная проверка DAX показала:

- количество из `InfoRg6612` не используется показанными мерами;
- план количества берётся из внешних таблиц `Бюджет` и `Бюджет по клубам`;
- из `InfoRg6612` нужен только дневной план выручки `SUM(Fld6620)`.

Поэтому ни `COUNT(Fld6619)`, ни `SUM(Fld6621)` в целевой набор не переносятся.

## Отложенные технические проверки

1. Ключи движений и сохранение сумм после joins.
2. `Active`, проведение, удаление, сторно и допустимые состояния.
3. Связь оплат с рекуррентными договорами ИП.
4. NOT_APPLICABLE для PostgreSQL: внешний классификатор услуг остаётся в Power BI.
5. Фактические типы, объёмы и контрольные значения.
