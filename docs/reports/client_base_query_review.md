и считает строки с ненулевым основанием. Серверная проверка сравнивает это с
прямым `Контрагент` регистра и ресурсом `Количество`; текущая логика не
меняется без доказанного расхождения.

## 4. Стаж клиента

Получен отдельный Power Query `СтажКлиента`.

Metadata подтверждает:

- `РегистрСведений.ВидСтажаКлиентов`;
- `Период (Period)`;
- `Клиент (Fld5655)`;
- `ВидСтажа (Fld5656)`;
- индекс `Клиент + Период`;
- перечисление `ВидыСтажаКлиентов`.

Текущий запрос выбирает последнюю запись стажа без ограничения отчётной датой. Это даёт текущий стаж для всех исторических снимков. Для корректного снимка требуется последняя запись с `Period < report_date` или другой подтверждённой границей момента 00:00.

Текущий join сравнивает ссылки через `encode(..., 'hex')`, хотя обе стороны являются ссылочными полями. Это может мешать индексу; равенство исходных бинарных значений нужно проверить и использовать напрямую.

## Проверки источника до проектирования

1. Получить типы и описания всех перечисленных полей из catalog/XML metadata.
2. Проверить уникальность `_IDRRef` и кодов клиентов/абонементов.
3. Проверить количество активных продуктов на одного клиента и клуб в одну дату.
4. Найти дубли `RANK() = 1` и число кандидатов для каждого `LIMIT 1`.
5. Проверить sentinel/null даты активации.
6. Сверить status/enum UUID с metadata.
7. Измерить строки и объём каждого запроса за проектный период.
8. Проверить максимальную давность изменений.
9. Сравнить клиента/клуб и количество посещений из прямых полей регистра с текущей логикой через документ.
10. Проверить физическое соответствие metadata-имён `Reference141` и фактической таблицы `_Reference141X1` через `pg_catalog`.
11. Посчитать влияние фильтров `Marked/Posted/Active/ЗакрытС/ЗаблокированС/Статус` на клиентскую базу по контрольной дате.
