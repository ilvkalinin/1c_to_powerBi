## Подтверждённая текущая бизнес-логика

### Первое посещение New

`AccumRg7575` соединяется с `Document325` по recorder и с `Reference59` по
`Fld7578`. Отбираются движения с 2025-01-01, New-контракт, GUID вида
документа «посещение». Ранжирование `ROW_NUMBER(PARTITION BY contract ORDER
BY Period)` оставляет первое движение. После SQL исключаются клубы ДРЦ и УК,
абонементы по тексту «ИП»/«сотрудн» и неклиентский тип контрагента.

### Гостевая конверсия

База гостевых визитов — `InfoRg7064`, соединённый с `Document325` (клуб) и
клиентом. Для каждого клиента M выбирает максимум даты истории стажа до
`_Period`; отсутствие истории подменяется датой 1990-01-01 и стажем `New`.

ACCUNIQ определяется по дате движения `AccumRg7575`, клиенту и одному из 12
кодов услуг; после группировки принимаются итоговые количества 1 или 2.
Гость получает ACCUNIQ только при равенстве дат. Покупка — первый по смещению
подходящий абонемент клиента, активированный в `[guest_visit_date,
guest_visit_date + 44 days]`. Финальный `Distinct` оставляет одну строку на
`client code × guest visit date`.

### Туры

`ТурыВсе` оставляет CRM-взаимодействия задач в воронке «Продажа клубной
карты» с GUID события «встреча». `ДатаДляОтчета` равна `_InfoRg7146.Fld7150`,
если она не `NULL`, иначе `_Reference67.Fld820`; подзапрос не агрегирует
телефонию. `Туры` сохраняет только пары «Закрыто/Выполнено» и
«Запланировано/Не выполнено». Успешность покупки и запись на ACCUNIQ затем
определяются двумя M-join; оба признака остаются пустыми вне совпадения.

## DAX: что остаётся в модели

- distinct-счётчики и конверсии должны оставаться DAX-мерами, потому что
  зависят от фильтров периода;
- текущие `_ТуровСостоялось` и `_ТуровЗапланировано` используют `COUNT`, не
  `DISTINCTCOUNT` stable ID — сохранить как текущую семантику до V-08;
- возрастные группы 0–2, 3–5, …, 82–85, 85+ и крупная группа дети `<14` /
  взрослые `14+` считаются в DAX от возраста на дату события;
- `План на день`, `План (НИ)` и `Факт (НИ)` остаются DAX: они используют
  `TODAY()` и контекст календаря.

## Риски реализации

1. `ROW_NUMBER` первого визита не имеет tie-breaker и не проверяет знак/
   `Active` движения.
2. Гостевой запрос не использует `Статус` и `РегистрацияГостевогоВизита`, хотя
   их извлекает. Ни одно поле не доказывает факт проведения.
3. Левый join с историей стажа после фильтра по максимуму может размножить
   гостевые строки при равных периодах.
4. Фильтрация ACCUNIQ по `Количество IN (1,2)` может исключать корректные
   повторные/сторнирующие события; бизнес-смысл `Fld7585` не доказан.
5. Покупка присоединяется по коду клиента, а не по физическому ID; уникальность
   кода и допустимость повторных визитов в одном дне не доказаны.
6. `ЗаписиНаАккуники` выбирает latest record по `ГрупповоеЗанятие`, не по
   клиенту; это противоречит последующему join по клиенту и дате.
7. Состояние тура названо текстом из справочника, а статус — жёсткими GUID:
   пара требует проверки на реальных значениях.
8. Внешний план привязан к имени листа одного месяца и не имеет стабильного
   ключа/схемы.
