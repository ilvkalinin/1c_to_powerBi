## Основной запрос контрактов

Гранулярность-кандидат:

> один исходный контракт `Reference59.ID`.

Текущий запрос:

- выбирает контракты с окончанием после 2024-01-01 и не далее конца
  шестимесячного будущего окна;
- исключает клип-карты, бесплатные, подписку, ИП, сотрудников, переданные
  контракты и срок менее 30 дней;
- исключает договоры, найденные как `Document332.Fld4422
  АбонементЗачета`;
- исключает контракты с любой найденной `Document287` по абонементу;
- через `LATERAL ... ORDER BY inner_a.Fld671 LIMIT 1` выбирает первый следующий
  подходящий контракт того же клиента.

Metadata подтверждает:

- `Document332.Fld4422` — `АбонементЗачета`;
- `Document287.Fld3379` — `Абонемент`;
- `Reference59.Fld670/Fld671/Fld672` — активация, начало, окончание;
- `Reference59.Fld693` — срок действия;
- `Reference59.Fld699` — тип оплаты.

## Риски определения продления

1. Следующий контракт определяется эвристикой по одному клиенту и датам, без
   прямой ссылки старый → новый.
2. Требуется только `next.start > current.start` и
   `next.end > current.end`. Начало следующего может быть раньше окончания
   текущего, поэтому отрицательная задержка допустима.
3. `LIMIT 1` сортирует только по дате начала. При одинаковой дате двух
   контрактов выбор недетерминирован.
4. `Marked`, статусы и закрытие обоих контрактов не проверяются.
5. `Document287` исключает контракт без проверки `Posted/Marked/status`;
   черновик либо отменённая заявка может удалить контракт из когорты.
6. `Document332` проверяет `Posted`, но не `Marked`.
7. `ПереданС = 0001-01-01` сравнивается с sentinel без подтверждённого типа и
   timezone.
8. Бизнес-описание включает любой бесплатный следующий контракт, а DAX
   исключает бесплатное короткое продление.

## Посещения

Запрос почти совпадает с `%Renew`:

- контрактная когорта по `Reference59`;
- `COUNT(AccumRg7575.Fld7578_RRRef)`;
- период жёстко ограничен 2026 годом;
- исключаются ДРЦ и управляющая компания;
- тип события и тип клиента задаются GUID.

Годовой период обрезает посещения контрактов, пересекающих Новый год.
Переиспользуется mapping `renew_contract_usage`; отдельный факт не нужен.

## Последнее взаимодействие

Текущий запрос выбирает последнее взаимодействие по коду клиента:

- только созданные после 2023-11-01;
- воронка `Продажа клубной карты`;
- исключается тип `Оформление`;
- исключаются запланированные и авто-взаимодействия;
- `ROW_NUMBER()` только по коду клиента и дате начала.

Набор является текущим состоянием клиента, а не состоянием конкретного
контракта. При одинаковой дате выбор недетерминирован; требуется ID tie-breaker.

## Рейтинг и стаж

Оба запроса берут максимальный период по клиенту. Это соответствует фильтрам
`Текущий рейтинг` и `Текущий стаж`, но:

- рейтинг не фильтрует `InfoRg6861.Active`;
- несколько строк клиента на одном максимальном периоде могут размножить
  связь;
- tie-breaker отсутствует.

## Цена

`SUM(AccumRg7739.Fld7749)` группируется по контракту при `RecordKind = 0` и
периоде после 2015 года. `Active`, возвраты, состояния регистратора и
кардинальность не проверяются.

## Текущая модель Power BI

Скриншот показывает несколько связей `1:1` с двунаправленной фильтрацией:

- `Посещения ↔ Абонементы`;
- `Цены ↔ Абонементы`;
- `Рейтинг ↔ Стаж ↔ Абонементы`;
- `МаксВзаимодействие ↔ Стаж`.

Это избыточная цепочка для атрибутов одного контракта/клиента и создаёт риск
неоднозначных фильтров. Текущие таблицы должны сначала гарантировать одну
строку на ключ; иначе объявленная `1:1` маскирует потерю или размножение строк.

## Направление улучшения

- одна контрактная строка является центром модели;
- посещения переиспользуются из общего контрактного набора;
- текущий рейтинг, стаж и последнее взаимодействие присоединяются к контракту
  после схлопывания до одной строки клиента;
- все ID остаются стабильными, связи по кодам используются только до миграции
  внешних выгрузок;
- расчёт задержки продления выполняется на контрактной строке;
- Renew-проценты остаются DAX-мерами из готовых флагов.

Оба Renew этого отчёта строятся только по текущим данным базы и одной строке
исходного абонемента:

- первый флаг проверяет дату активации следующего абонемента относительно
  1-го числа после месяца окончания;
- второй — относительно `current_date`;
- снимки и Excel-выгрузки не используются.
