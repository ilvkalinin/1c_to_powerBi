# Требования отчёта: «Карта администратора»

Статус: `BUSINESS LOGIC COMPLETE / PHYSICAL SOURCE AVAILABILITY VALIDATED — SV-002 / STAGE 3 SOURCE CONTROLS DEFERRED`. Получены
бизнес-описание, текущий SQL/M Gymmy, два визуала и пояснение по внешним
Excel-файлам. SQL и физические таблицы не создаются; проверено только
физическое существование `InfoRg5836` в read-only каталоге gymdb.

## Назначение

Договорный отчёт № 25 контролирует использование карт администраторов для входа и выхода из клубов, сравнивая:

- журнал, вручную заполняемый администраторами;
- фактические срабатывания СКУД из Gymmy.

## Фильтры

- клуб;
- период `с ... по ...`.

## Метрики

| Метрика | Правило |
|---|---|
| `Всего входов администратор` | количество итоговых строк Excel с направлением `Вход` |
| `Всего входов Gymmy` | количество итоговых строк Gymmy с направлением `Вход` |
| `Разница входов` | администратор − Gymmy |
| `Всего выходов администратор` | количество итоговых строк Excel с направлением `Выход` |
| `Всего выходов Gymmy` | количество итоговых строк Gymmy с направлением `Выход` |
| `Разница выходов` | администратор − Gymmy |

Пользователь подтвердил общее правило: в текущей модели визуалы считают
количество строк итогового набора по датам и клубам. В сжатой модели этому
эквивалентна сумма поля `Количество использований`; `DISTINCTCOUNT` не нужен.

## Визуализации

- шесть карточек входов/выходов и отклонений;
- причины входов по данным Excel;
- причины выходов по данным Excel;
- подневное сравнение Excel и Gymmy для входов;
- подневное сравнение Excel и Gymmy для выходов;
- красный цвет отклонения при ненулевой разнице, зелёный при нуле.

## Источники

### Gymmy

`InfoRg5836` (`РегистрСведений.ЖР_СКУД`):

- дата и время события;
- терминал;
- клиент/карта;
- идентификатор события;
- вид события;
- успех;
- сообщение.

Текущий запрос:

- оставляет 12 жёстко заданных кодов карт;
- оставляет два GUID событий `Вход` и `Выход`;
- в текущей версии не фильтрует `Успех`; в целевой выборке пользователь
  потребовал исключить `Успех = 0`;
- получает клуб как последнее слово наименования клиента/карты;
- передаёт в Power BI каждое событие.

### Журнал администраторов

Внешние Excel-файлы, заполняемые администраторами. Для отчёта необходимы только:

- дата;
- клуб;
- направление `Вход/Выход`;
- причина;
- количество строк.

Фактические названия и типы колонок не переданы.

## Минимальная логическая гранулярность

Power BI не требует отдельных событий. Достаточен дневной агрегат:

> дата × клуб × направление × источник × причина.

`Причина` заполнена только для журнала администратора; у Gymmy она пустая. В строке хранится `Количество использований`.

Предварительное имя пользовательской таблицы Power BI:

> `Использования карты администратора`.

Пользовательские колонки:

- `Дата`;
- `Клуб`;
- `Вход/Выход`;
- `Источник`;
- `Причина`;
- `Количество использований`.

## Минимальная модель

- PostgreSQL возвращает только агрегат Gymmy `дата × клуб × вход/выход`.
- Power Query приводит небольшой внешний Excel-журнал к той же схеме, агрегирует по причине и выполняет один `Table.Combine`.
- Для шести карточек и диаграмм используется одна итоговая таблица, а не
  отдельные таблицы входов, выходов и источников.
- Источник Gymmy не хранит ФИО, код карты, терминал и идентификатор события на VM-2.

## Сравнение с разобранными отчётами

`InfoRg5836` ранее не использовался. С посещениями клиентов объединять его нельзя:

- СКУД фиксирует срабатывание карты администратора;
- посещенческие факты отражают клиентов и другие бизнес-события;
- совпадение даты и клуба не означает общую строку.

Общий справочник дат и клубов можно переиспользовать. Универсальный факт СКУД пока не создаётся: другие подтверждённые потребители отсутствуют.

## Подтверждённые эксплуатационные правила

- текущие 12 карт соответствуют полному перечню 12 действующих клубов;
- при открытии нового клуба код его карты вручную добавляется в фильтр запроса;
- учитываются только строки Gymmy с `Успех <> 0`;
- обновление выполняется один раз в день.

Для реализации позднее потребуется один пример Excel или полный M-код его
загрузки. Он не запрашивается и не анализируется по границе проекта; это не
блокирует source-side Gymmy контур, но внешняя часть остаётся в Power BI.

## Результат Stage 2

SV-002 подтвердил физическое существование `public._inforg5836`; отсутствующий
источник не выявлен. Ключ события, тип и распределение `Fld5841`, соответствие
12 карт клубам, исключение неуспешных событий и контроль дневной агрегации
остаются `VALIDATION_PENDING` до отдельного разрешения Stage 3. Нельзя
подменять клуб извлечением последнего слова из наименования карты без
доказанного mapping.

## Учёт class-C критичности — 2026-08-13

Новый вопрос пользователю не требуется. Подтверждённые правила Gymmy уже
задают будущий состав агрегата: 12 карт, два GUID направления, дневная
агрегация и `SUM(usage_count)` вместо `DISTINCTCOUNT`.

- исключение `Успех = 0` — уже принятое пользовательское правило; до
  подтверждения физического типа `Fld5841` нельзя менять его на иную
  трактовку успеха или silently оставить неуспешные события;
- технический event key, соответствие карты каноническому клубу и дневной
  `COUNT(*)` должны быть доказаны до сжатия. Извлечение последнего слова из
  наименования карты не становится production mapping;
- только Gymmy находится в границе этого технического контура. Внешний журнал
  администраторов не анализируется и не переносится; его отсутствие не
  оправдывает изменение Gymmy-метрик или создание новой дедупликации.

Это safeguards, а не начало реализации или изменение методики.
