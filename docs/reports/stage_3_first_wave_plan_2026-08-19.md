# План первой Stage-3 волны — 2026-08-19

Статус: `PLANNED ONLY / FIRST CANDIDATE BLOCKED BY S3-RR-ADMISSION-001 / NO DDL OR DML AUTHORIZED`.

## Разрешённая граница

Пользователь подтвердил после полного review только выбор и подготовку первой
волны. Поэтому `.agents/project_stage_gate.tsv` находится в состоянии
`STAGE3_PLANNING_AUTHORIZED`: runnable package selection, DDL, DML, создание
витрин и повторные загрузки намеренно заблокированы.

## Выбор первого кандидата

Первым следующим кандидатом был отдельный пакет
`STAGE_3_PRODUCT_ADMISSION — Выручка рецепции` с единственным объектом
`mart.v_reception_revenue`. Проверка 2026-08-19 установила, что этот объект
нельзя строить над текущим `mart.ancillary_revenue_movement`: его фактический
scope ограничен ДПФУ. До архитектурного решения кандидат не является runnable.

| Критерий | Почему кандидат подходит |
|---|---|
| Приоритет | «Выручка рецепции» — следующий не реализованный отчёт класса A после уже выполненной «Выручки ДПФУ». |
| Повторное использование | Отклонено для текущего состояния: общий факт не содержит рецепционный scope. |
| Зафиксированная логика | Grain подтверждён, но его категории и строки отсутствуют в принятом общем факте; см. S3-RR-ADMISSION-001. |
| Внешняя граница | Excel-план остаётся Power BI-фактом и не переносится. |
| Риск первого релиза | Семантика продавца и текстовая классификация не переписываются: сохраняются current rule и BR-018. |

В каталоге устранено только техническое расхождение имени: прежнее
`mart.v_reception_revenue_daily` приведено к подтверждённому ADR/data-contract
имени `mart.v_reception_revenue`. Это не создаёт view и не меняет его grain.

## Что должен содержать отдельный admission-пакет

1. Один детерминированный SQL-проект view с явными mapped-колонками, без
   обращения к raw-регистрам и без внешнего Excel.
2. Отдельный просмотр SQL, rollback и явное разрешение DDL/DML до запуска.
3. После создания: проверка ключа/grain, строк и знаковых сумм, сохранения
   отрицательных движений, контроль одного клуба и месяца, rerun и SLA до
   08:30 МСК.

До такого отдельного разрешения не выполняется ни один из этих пунктов.

## S3-RR-ADMISSION-001 — scope общего факта не покрывает рецепцию

`mart.ancillary_revenue_movement` построен с фильтром `activity_name IN`
для шести фитнес-направлений. Точный target control на 2026-08-19 подтвердил
только: «Боевые искусства», «Водные программы», «Групповые программы»,
«Детский клуб», «Игровой зал» и «Тренажёрный зал (Штат)».

Подтверждённый current rule «Выручки рецепции», напротив, исключает эти
фитнес-направления и дополнительно требует восемь `reception_category_key`.
В текущем факте такой колонки нет. Обычный view над ним неизбежно дал бы
пустой либо неполный рецепционный отчёт. Это не исправляется новым фильтром
view и не является разрешением менять бизнес-методику.

Для продолжения пользователь должен выбрать архитектуру: расширить общий факт
вторым, отдельно маркированным рецепционным scope с его подтверждённой
категоризацией либо создать отдельный узкий рецепционный факт. До выбора
DDL/DML запрещены.

После фиксации S3-RR-ADMISSION-001 следующим unblocked кандидатом первой
волны назначен отдельный admission-пакет «KPI Фитнеса». Это не снимает блокер
рецепции и не разрешает его DDL/DML.

S3-KF-ADMISSION-001 подтвердил, что «KPI Фитнеса» не создаёт отдельный
PostgreSQL-объект по ADR-0012 и не может быть принят как полный отчёт без
ещё не загруженной `mart.client_base_daily`. Её source formation, SQL-контракт
и пустая схема закрыты ADR-0031/S3-CBD-DDL-001; требуется только отдельный
initial-load пакет. Поэтому на
момент составления первой волны независимым кандидатом была выбрана
`mart.administrator_card_gymmy_daily` («Карта администратора»), для которого
source controls уже закрыты.
