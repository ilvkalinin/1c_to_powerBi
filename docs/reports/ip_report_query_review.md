# Разбор текущих запросов: «Отчет по ИП»

Статус: `BUSINESS LOGIC CONFIRMED / TECHNICAL VALIDATION DEFERRED`.

## Пакетный audit 2026-08-11

Два исходных M-набора, DAX-таблица `Общая` и четыре меры повторно
сопоставлены с requirements, mapping и ADR-0025. Подтверждённый `SV-058`
дополняет source evidence: в ветке ГП 147 900 строк PBIT совпадают с 147 900
исходными событиями, а в ветке ПЗ 49 200 строк PBIT соответствуют 48 973
событиям из-за 227 строк размножения `VT4352`. Это наблюдаемая текущая
кратность, а не основание менять расчёт.

По BR-018 `training_count` первого релиза воспроизводит `COUNT(Контрагент)`
текущих ветвей, включая подтверждённую кратность ПЗ. Переход к уникальным
логическим тренировкам требует отдельного методического решения. Физические
типы, полиморфная ссылка, полнота состояний, объём и контрольные суммы
сохраняются как `VALIDATION_PENDING`; в текущем `STAGE_1_LOCAL_ANALYSIS`
новые подключения и SQL не выполнялись.

Источники:

## Текущие наборы

### `РС_СостояниеПредЗаписи (ДОК_ПЗ)`

Источники:

- `InfoRg7006` — `РегистрСведений.СостояниеПредварительнойЗаписи`;
- `Reference141X1` — клиент;
- `Reference132` — клуб;
- `Document329` — предварительная запись;
- `Reference225` — сотрудник;
- `Enum448` — состояние клиента;
- `Document329.VT4352` — услуги предварительной записи;
- `Reference163` — номенклатура.

Отбор ИП:

- услуга регистра равна `bcd000505688c8b011ee0a8ba155d4a1`; или
- тип взаиморасчётов строки услуги равен `a0f1524d502e0d5d4c1dfeb9d5bbb3fe` («с сотрудником»).

### `РС_СостояниеПредЗаписи (ДОК_ГП)`

Использует тот же регистр состояния, но присоединяет `Document279` (`ГрупповоеЗанятие`). Ветка оставляет только специальную услугу ИП `bcd000505688c8b011ee0a8ba155d4a1`.

### `Общая`

Вычисляемая DAX-таблица:

```DAX
Общая =
UNION (
    'РС_СостояниеПредЗаписи (ДОК_ГП)',
    'РС_СостояниеПредЗаписи (ДОК_ПЗ)'
)
```

В обеих ветвях Power Query оставляет строки, где `Состояние <> 2` и `Состояние <> 3`.

## Текущие меры

```DAX
Count =
COUNT ( 'Общая'[Контрагент] )

dCount =
DISTINCTCOUNT ( 'Общая'[Контрагент] )

RegC =
DIVIDE ( 'Меры'[Count], 'Меры'[dCount] )

_УслугНа1тренера =
DIVIDE (
    'Меры'[Count],
    DISTINCTCOUNT ( 'Общая'[Сотрудник] )
)
```

## Подтверждённое пересечение

Обе ветви и мера `COUNT(Контрагент)` совпадают с источником показателя `Посещения ИП` отчёта «Посещения Физкульт». Это доказанное повторное использование, а не предположение по названию.

## Критические наблюдения

1. Нижняя граница `_Period >= '01.01.2024'` захардкожена и не соответствует скользящей политике истории проекта.
2. Фильтр состояний выполняется в Power Query после `Odbc.Query`. Пользователь подтвердил текущее правило `<> 2 AND <> 3`; в целевом варианте его следует применять сразу в source-side SQL.
3. `InfoRg7006.Active` выбирается, но не фильтруется.
4. `Document279.Posted`, `Document279.Marked`, `Document329.Posted` и `Document329.Marked` не проверяются.
5. В ветке ПЗ табличная часть услуг присоединяется только по ссылке документа. Один документ с несколькими строками услуг может размножить строку регистра.
6. Условия по услуге регистра и типу взаиморасчётов относятся к разным строковым уровням. Без ключа строки нельзя доказать соответствие выбранной услуги конкретной строке записи.
7. Физическое поле связи имеет вид `_Fld7007_RRRef`; текущие ветви не показывают проверку типа составной ссылки. До проверки нельзя исключить ошибочное присоединение одного `RRef` к обеим таблицам документов или дубли между ветвями.
8. Текущий `COUNT(Контрагент)` считает непустые строки результата join, а не поле `Количество` регистра и не доказанный ключ тренировки.
9. `DISTINCTCOUNT(Контрагент)` и `DISTINCTCOUNT(Сотрудник)` выполняются по отображаемому имени. Однофамильцы могут объединиться; переименование может разорвать историю.
10. Для фильтра источника используется технический период регистра, а визуал анализирует тренировки по месяцу и дням. Пользователь подтвердил: отчётная дата берётся из `Document329.Fld4306` / `Document279.Fld3218`; дата внесения строки в регистр не определяет период тренировки.
11. `encode(..., 'hex')` применяется в каждом join. В целевом SQL сравнение следует выполнять в исходном бинарном типе, а кодировать только при необходимости выдачи.
12. DAX `UNION` объединяет две импортированные таблицы внутри модели, хотя одинаковую нормализацию можно выполнить один раз на PostgreSQL.
13. Код клиента нужен в детальном визуале. Это исключение из общего правила обезличенных посещений и требует ограничить выдачу этой таблицы кругом пользователей отчёта.

## Направление оптимизации

- объединить две ветви на стороне PostgreSQL;
- выбрать только записи целевого периода и нужные поля;
- воспроизвести подтверждённую текущую кратность ветки ПЗ; нормализацию до
  уникальных событий вынести в отдельное методическое улучшение;
- считать `УЧК` по стабильному client key, тренеров — по employee key;
- после установления логических тренировок агрегировать их до `дата × клуб × сотрудник × клиент × услуга` с количеством;
- использовать этот же факт для показателя ИП в «Посещениях Физкульт»;
- оставить в DAX интерактивные `COUNT`, `DISTINCTCOUNT`, отношения и проценты.
