Статус: `BUSINESS LOGIC COMPLETE / TECHNICAL VALIDATION PARTIALLY VALIDATED — SV-072`.
Production SQL и физические объекты не создаются; выполнены только read-only
проверки источника.

PBIT `Контроль_предварительной_записи.pbit` получен 2026-07-31
(SHA-256 `bfa912276c0b49730e2ade1c3004b51eef8857cc207a662bfee78a350dcf1132`).

## Назначение

Отчёт контролирует, насколько своевременно в Gymmy внесены предварительные
записи на платные тренировки, их соответствие текущему плану ДПФУ и
наполняемость групповых программ. Пользователь и владелец отчёта: `UNKNOWN`.

Текущая логика использует три разных набора с несовместимой гранулярностью:

1. события состояния предварительной записи — для структуры по времени,
   отмен и детализации отмен;
2. дневной план по сотрудникам — для сравнения плана с количеством записей;
3. групповое занятие — для вместимости, активных записей и фактических
   пришедших.

Их нельзя склеивать в одну строку или один факт без потери семантики.

## Подтверждённая текущая логика

- Источником статусов записи является `InfoRg7006`; текущий M различает
  персональную ветку `Document329` и групповую `Document279`.
- Для платных персональных записей исключаются купоны, специальная услуга ИП
  и строки взаиморасчётов «с сотрудником». Для групповых в основной структуре
  остаются только предварительно оплаченные записи; состояние `1` считается
  ожидаемым, `2` и `3` — отменами, `4` — прибытием. Названия и полнота этих
  состояний требуют технической проверки.
- Временная структура считается относительно начала/окончания занятия:
  до начала календарного дня занятия, до окончания занятия, после окончания;
  «в следующие дни» — после полуночи следующего дня. Визуальная подпись
  «до 9:00» исторически неточна: M использует `Period < Date(lesson_start)`,
  то есть до `00:00` даты занятия, что соответствует формулировке «до 23:59
  предыдущего дня» в описании.
- Отмены уменьшают количество записей: до начала дня — из категории «до
  9:00», после — из отдельной категории отмен. Поэтому текущая мера
  `ВсегоЗаписей` является нетто-количеством, а мера «Отмены» возвращает
  отрицательное значение. Это сохранено как `CONFIRMED` текущая реализация,
  а не исправлено без контрольных значений.
- Текущий план — `COUNT(InfoRg6612.Fld6619)` с разрезами даты, клуба,
  подразделения и тренера. Другая колонка регистра (`Fld6620`) используется
  для плановой выручки, но не для числа услуг этого отчёта.
- На странице «Записи на групповые» число неотменённых записей — сумма
  `+1` для состояния `1` и `−1` для `2/3`; число пришедших берётся отдельно
  из статуса `4`, а для бесплатных программ — из `InfoRg8675.Fld8677`.

## Страницы и показатели

| Страница | Фильтры | Подтверждённые показатели |
|---|---|---|

| «Графики» | год, месяц, клуб, вид деятельности, тренер | дневная/месячная/годовая доля каждой временной категории |
| «ПЗ и план», «ПЗ и план-факт» и рейтинги | дата, клуб, вид деятельности, тренер (с исключениями на рейтинговых страницах) | план услуг, записи до предыдущего дня, отношение к плану, а также факт оказанных услуг на варианте plan-fact |
| «Отмены» | дата, клуб, вид деятельности, тренер, время отмены, факт визита | детальная строка отмены: клуб, начало урока, отмена, сотрудник, услуга, код/ФИО клиента, отменено до/после, был в клубе |
| «Записи на групповые» | дата, клуб, вид деятельности, услуга, тренер, тип оплаты | время занятия, вместимость, неотменённые записи, свободные места, заполненность по записи и факту, пришедшие |

Плановая страница использует именно количество услуг, а не плановую выручку.
Визит клиента на странице отмен проверяется по совпадению кода клиента,
календарной даты и клуба фактического посещения.

## Модель Power BI и границы миграции

Текущая модель считает доли и рейтинг сотрудников в DAX. Эти меры остаются
filter-dependent и не переносятся в будущий SQL как готовые проценты.
Для детализации отмен в текущей модели передаются код и ФИО клиента; это PII,
доступные всем пользователям с доступом к отчёту (решение пользователя
2026-07-31, BR-017). PBIT не содержит роли RLS; техническая настройка прав
проверяется перед реализацией.

PBIT подтверждает текущую модель из 20 содержательных таблиц и 19 активных
однонаправленных связей: общие дата, клуб, вид деятельности и тренер фильтруют
план, уроки, записи и отмены. Это не доказывает уникальность отображаемых
текстовых ключей и не заменяет PC-V01…PC-V13.

Готовые агрегаты `mart.visit_client_day`, факт тренировок ИП и агрегированный
дневной план ДПФУ не заменяют текущие наборы: им не хватает соответственно
времени изменения статуса, категории отмены либо разреза тренер × клиент.
