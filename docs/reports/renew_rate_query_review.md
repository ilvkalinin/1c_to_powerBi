## Текущие правила

- `Document325.Fld4164` равен переданному GUID вида операции `посещение`;
- исключаются клубы по названиям `Детский развивающий центр` и
  `Управляющая компания`;
- период жёстко ограничен `[2026-01-01, 2027-01-01)`;
- тип клиента равен переданному GUID `Клиент`;
- строки без кода контракта исключаются;
- результат группируется по строковому коду контракта.

## Наблюдения

1. `COUNT(*)` считает движения регистра, а не доказанные уникальные документы
   посещения и не ресурс `Fld7585`. До проверки нельзя незаметно заменить
   текущую формулу.
2. Годовой фильтр не соответствует жизненному циклу контракта. Например,
   контракт 2025–2026 потеряет посещения 2025 года.
3. `Reference59` присоединяется через полиморфное поле основания без проверки
   типа ссылки. Совпадение бинарных ID разных типов нужно исключить.
4. `Active`, `Document325.Posted` и `Document325.Marked` не фильтруются.
5. Клубы исключаются по изменяемому тексту; после проверки использовать ID.
6. `Reference59.Code` удобен для связи с выгрузкой 1С, но уникальным
   техническим ключом PostgreSQL должен быть `Reference59.ID`.
7. Полное имя, телефон и другие данные клиента не нужны и не переносятся.

## Целевое направление

На VM-1 отбираются только посещения контрактов нужного отчётного горизонта и
только внутри интервала каждого контракта. На VM-2 передаётся компактный набор
на уровне контракта, а не сырые строки `AccumRg7575`.

Набор обновляется ежедневно для контрактов текущих и будущих месяцев
окончания. Закрытые месяцы не пересчитываются: их состояние сохраняется
отдельными Excel-выгрузками 1С.

Окончательное правило подсчёта посещений остаётся текущим `COUNT(*)` до
read-only проверки:

- число движений по `(Recorder, LineNo)`;
- число уникальных `Document325.ID`;
- сумма `Fld7585`;
- расхождения между тремя вариантами на контрольных контрактах.
