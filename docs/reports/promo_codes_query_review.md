Связь по дате применения неактивна, а дата создания промокода активна.

## Подтверждённые расчёты DAX

- количество применений: строки без серии + distinct серийные номера;
- УЧК: `DISTINCTCOUNT(КодКлиента)`;
- приложения на клиента: применения / УЧК;
- выпуск: distinct ключ `Промокод + Серия`, с корректировкой до не меньшего
  числа применений;
- конверсии: distinct УЧК с соответствующим флагом / УЧК категории;
- подарки: текстовая классификация и извлечение числовой части после `+ `;
- скидочные категории: `SWITCH(TRUE())` по сумме, цене, направлению и тексту.

## Наблюдения и риски

1. Текущий SQL не отдаёт `Recorder` и `LineNo`, поэтому факт нельзя
   доказательно дедуплицировать и связать с источником на уровне движения.
2. `AccumRg7606` и `AccumRg7615` перед объединением агрегируются по текстам и
   дате. Несколько исходных строк с одинаковыми атрибутами могут быть
   схлопнуты; обратное размножение возможно через joins `Document332`/
   `Document346` и их табличные части.
3. Для абонемента, ДПФУ и справочника промокодов зашиты диапазоны 2025–2026.
   Они соответствуют текущему окну BR-003, но не являются динамической
   календарной политикой.
4. Дата создания промокода не хранится отдельно: M извлекает строку вида
   `YYYY-MM` из одного из четырёх уровней и подставляет `2024-01`, если не
   нашёл. Это подтверждённая текущая эвристика, а не доказанная дата создания.
5. Текущая DAX-мера выпуска способна заменить фактическое число выпущенных
   промокодов числом применений. Это текущая отчётная корректировка, её нельзя
   неявно перенести как физический факт.
6. Цена до скидки для `Document332` соединяется без номера строки; текущий
   SQL сам содержит закомментированную проверку `LineNo`. Сумма может
   размножиться при нескольких строках одного абонемента.
7. Текстовые `SEARCH` в DAX зависят от регистра, орфографии и переименования
   номенклатуры/подарка. Категории должны оставаться отчётными правилами до
   появления управляемого справочника.
8. `Подарок (ед.)` забирает ровно два символа после `+ `. Значения дня с тремя
   и более цифрами будут искажены; наличие таких значений —
   `VALIDATION_PENDING`.
9. SQL не проверяет `Active`, проведение, пометку удаления, сторно и возвраты
   ни у движений, ни у регистраторов.
10. Клиентское ФИО и код извлекаются, но подтверждённый визуал использует
    только агрегаты. В будущий факт без отдельного потребителя они не входят.
11. Правило «Друг купил абонемент» отсчитывает 45 дней от активации
    подаренного другу абонемента. Это решение пользователя от 2026-07-31;
    расхождение с кратким описанием страницы устранено в пользу текущего SQL.
