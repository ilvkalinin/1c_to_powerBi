# Readiness matrix: incremental refresh design

Пакет: `project_refresh_incremental_design_2026-08-31`. Статусы ниже относятся
только к возможности automatic incremental refresh; они не меняют acceptance
существующих физических витрин.

| DAG job | Physical targets | Status | Evidence / decision |
|---|---|---|---|
| `administrator_bookings_daily` | `mart.administrator_bookings_daily` | `BLOCKED` | Runner существует только как незакоммиченный файл и отсутствует в `HEAD`/GitHub release. Нельзя анализировать или автоматизировать unversioned implementation. |
| `administrator_card_gymmy_daily` | `mart.administrator_card_gymmy_daily` | `FULL_REBUILD_ONLY` | `public._inforg5836`: 54,730,751 rows; columns only `_period` plus event payload, no active/deletion marker, update/version timestamp or change feed. `_period` is event time. Late changes/deletions cannot be reconciled by a watermark; current atomic BR-003 rebuild remains the only evidence-based mode. |
| `children_package_sale` | `mart.children_package_sale` | `FULL_REBUILD_ONLY` | BR-039 output depends on `AccumRg7646`, `Document346`, `VT4913` and `VT4924`, including return report-groups. Only `Document346` exposes `_version`; movement and both tabular parts have no change field, and `AccumRg7646` has 4,923,880 rows with `_active=false` = 0. A document-only watermark misses late mutation/deletion of the remaining inputs, so no separate incremental runner is safe. |
| `client_base_daily` | `mart.client_base_daily` | `INCREMENTAL_CANDIDATE` | A source watermark is unavailable (`VT4913`, `VT4924` and `AccumRg7646` lack it), so the separate runner detects late changes and deletions by a double deterministic fingerprint of every day’s exact reviewed source aggregate versus the persisted target. It replaces only the contiguous span covering differing dates and validates stage/persisted totals plus BR-038 controls before commit. Candidate plan: 31 days = 17.882 s; 608 days = 30.850 s, no source reads from disk. `--check-only` found a real current mismatch on all 608 dates; no DML was run in this package. |
| `client_base_snapshot_retention` | `mart.client_base_snapshot`, `mart.client_base_retention` | `INCREMENTAL_CANDIDATE` | The confirmed contract requires a minimum two-month late-change window. `AccumRg7575`, `InfoRg5654`, `AccumRg7646` and the child tabular parts have no change watermark, so the new composite runner atomically replaces that fixed window for both facts from one exported source snapshot. Fresh August exact plans: snapshot 99,515 rows / 20.770 s; retention 64,905 rows / 32.956 s. This is a correct bounded incremental strategy but no one-minute SLA is claimed; DML remains unexecuted. |
| `club_attendance_hourly` | `mart.club_attendance_hourly` | `INCREMENTAL_CANDIDATE` | No source watermark is available, so the separate runner compares daily double fingerprints of the exact current source aggregate and persisted target; it detects old corrections/deletions without a business lookback rule, then atomically replaces only the span of differing visit dates. The 413.220 s full source baseline means this is correct but explicitly not a one-minute daily SLA. DML remains unexecuted. |
| `contract_usage` | `mart.contract_usage` | `INCREMENTAL_CANDIDATE` | The user-approved remediation removed `finalized_month` and mutable cutoff. The separate runner instead fingerprints each exact current BR-003 contract row, deletes source-absent contract keys, and stages only changed source keys. Exact extract baseline is 31,788 rows / 1.514 s in the technical review; no DML has run in this design package. |
| `crm_br032` | `mart.crm_interaction`, `mart.crm_interaction_phone`, `mart.feedback_interaction`, `mart.club_day_metrics` | `BLOCKED` | Core/phone and club-day have physical keys, but `feedback_interaction` is the final PBIT business grouping with no stable target key and with mutable comment/follow-up fields. A changed group cannot be identified for atomic row replacement; replacing its complete fact would be a full rebuild, not incremental. The four facts must commit coherently, so no separate composite incremental runner is safe without an approved stable feedback key or an explicit full-feedback policy. |
