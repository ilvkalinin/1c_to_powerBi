# Узкий статический аудит оркестрации Codex

Дата: 2026-07-28. Аудит выполнен только по локальным текстовым инструкциям;
skills, субагенты, MCP, SQL и серверные подключения не запускались.

## 1. Итоговый вердикт

Текущая конфигурация сама по себе не запускает PostgreSQL, SQL или агентов:
в [.codex/config.toml](../.codex/config.toml) есть только включение агентов и
лимит параллельности `3`; MCP, hooks, модель, reasoning и сетевые правила не
объявлены. Главный риск создаёт не конфигурация, а обязательная цепочка в
[AGENTS.md](../AGENTS.md): для каждого нового отчёта она требует fan-out двух
субагентов, затем архитектора и SQL-инженера. Это противоречит текущему этапу
локального анализа и может привести к лишнему контексту, делегированию и
преждевременной реализации.

На текущем этапе безопасен основной агент с ограниченным контекстом и skill
`source-to-target-mapping` при необходимости. Валидация и реализация должны
оставаться явными пользовательскими переходами. Все подготовленные проверки
нужно фиксировать как `VALIDATION_PENDING`; их текст не должен выполняться.

## 2. Критические проблемы

| Критичность | Файл | Наблюдение | Риск | Минимальное исправление |
|---|---|---|---|---|
| Высокая | [AGENTS.md](../AGENTS.md) | Строки 22–30 описывают непрерывную последовательность до SQL и проверок, но не содержат отдельного gate: локальный анализ → серверная валидация → реализация. | Архитектурное решение или mapping могут ошибочно трактоваться как разрешение на SQL-реализацию. | Ввести три именованных этапа, статус `VALIDATION_PENDING` и прямой запрет на подключение/SQL до явного разрешения пользователя. |
| Высокая | [AGENTS.md](../AGENTS.md) | Строка 143 предписывает для каждого нового отчёта параллельно запускать `source_mapper` и `powerbi_reviewer`, затем `data_architect` и `postgres_engineer`. | Лишние вызовы агентов и передача контекста; возможен преждевременный переход к реализации. | Заменить обязательную цепочку правилом: на этапе локального анализа работает основной агент; субагент — только для крупной независимой задачи и по явному решению основного агента. |
| Средняя | [.agents/skills/postgres-performance-review/SKILL.md](../.agents/skills/postgres-performance-review/SKILL.md) и [.codex/agents/performance_reviewer.toml](../.codex/agents/performance_reviewer.toml) | Описаны `EXPLAIN` и сбор фактов каталога, но нет явного запрета на выполнение до серверного этапа. | При ручном вызове может быть предпринята преждевременная серверная операция. | Добавить entry gate: до явного разрешения серверной валидации — только план измерений, без подключения и выполнения. |
| Средняя | [.codex/config.toml](../.codex/config.toml) | `agents.enabled = true`, `max_concurrent_threads_per_session = 3`; этап проекта не задан. Конфигурация не запускает агентов автоматически. | При следовании строке 143 `AGENTS.md` становится доступен ненужный параллельный fan-out. | Не считать это самостоятельной ошибкой; после исправления `AGENTS.md` оставить лимит, а фактический запуск ограничить явным stage gate. |

Нет статических признаков постоянно подключённого PostgreSQL MCP, hooks,
автоматического schema discovery, автоматических терминальных команд или
автоматического выполнения SQL. Их параметры — `NOT_DEFINED`.

## 3. Решения по skills

| Skill | Решение | Допустимость и причина |
|---|---|---|
| `source-to-target-mapping` | `KEEP` | Единственная чёткая задача этапа локального анализа. Инструкция ограничивает доказательства переданными материалами и запрещает mart SQL. Использовать по необходимости, не для повторного mapping уже зафиксированного отчёта. |
| `powerbi-data-contract` | `ON_DEMAND_ONLY` | Полезен только после достаточного mapping и архитектурного решения; его pre-design режим может дать findings, но не нужен каждому новому отчёту. |
| `postgres-mart-design` | `DISABLE_UNTIL_IMPLEMENTATION` | Выбор view/materialized view/table и refresh должен следовать за подтверждённой серверной валидацией и отдельным разрешением на реализацию. |
| `data-quality-reconciliation` | `DISABLE_UNTIL_IMPLEMENTATION` | Инструкция требует существующую реализацию и готовит тесты в `sql/tests/`; сейчас допустим только краткий план будущих проверок в mapping, без запуска skill. |
| `postgres-performance-review` | `DISABLE_UNTIL_IMPLEMENTATION` | Требует размеры, индексы и планы. До появления SQL-объекта и разрешённой серверной валидации должен быть недоступен. |

`source-to-target-mapping` не требует подключения автоматически: формулировка
«only supplied evidence» в его инструкции это ограничивает. Однако проверки
ключей и joins должны на текущем этапе оформляться только как
`NOT_EXECUTED`/`VALIDATION_PENDING`, а не исполняться.

## 4. Решения по субагентам

| Субагент | Решение | Причина |
|---|---|---|
| `source_mapper` | `ON_DEMAND_ONLY` | Дублирует обычную работу основного агента над одним отчётом; оправдан только для изолированного крупного исследования источников. |
| `powerbi_reviewer` | `ON_DEMAND_ONLY` | Полезен для большой или неоднозначной модели, но не должен автоматически сопровождать каждый отчёт. |
| `data_architect` | `DISABLE_UNTIL_IMPLEMENTATION` | Его prompt выбирает физический объект, слои и refresh; это преждевременно до серверной валидации. |
| `postgres_engineer` | `DISABLE_UNTIL_IMPLEMENTATION` | Это write-агент реализации; его вызов на этапе анализа недопустим. |
| `data_quality_reviewer` | `DISABLE_UNTIL_IMPLEMENTATION` | Сопоставляет готовую витрину с mapping и готовит reconciliation tests. |
| `performance_reviewer` | `DISABLE_UNTIL_IMPLEMENTATION` | Работает с фактическими планами и измерениями, которых на текущем этапе нет. |

В prompts субагентов не задано право вызывать других субагентов. Рекурсивное
делегирование статически не обнаружено. Обязательный fan-out возникает только
из [AGENTS.md](../AGENTS.md), а не из `.codex/config.toml`.

## 5. Вывод по `.codex/config.toml`

Конфигурация минимальна: агенты включены, одновременно допустимы до трёх
потоков. Правила модели и reasoning — `NOT_DEFINED`; дорогая модель или высокий
reasoning рутинным задачам не назначены. MCP-серверы, hooks, разрешения сети,
терминала и SQL — `NOT_DEFINED`; PostgreSQL не подключён постоянно.

Файл не содержит автоматических правил активации субагентов. Значит, снижение
расхода токенов следует начинать с исправления маршрутизации в `AGENTS.md`, а
не с отключения всей агентной подсистемы. Файлы
[`config/project.example.yml`](../config/project.example.yml),
[`config/reports.example.yml`](../config/reports.example.yml) и
[`config/sources.example.yml`](../config/sources.example.yml) не имеют
обнаруженных ссылок из проверенных инструкций или `.codex/config.toml` и
выглядят только bootstrap-примерами: `NOT_USED`. Они не содержат заполненных
параметров подключения и сами по себе не инициируют соединение.

## 6. Текущий и оптимальный маршрут нового отчёта

Сценарий: пользователь передал Power Query, DAX, SQL отчёта и пояснения;
сервер недоступен.

| Шаг | Текущий маршрут по инструкциям | Оптимальный минимальный маршрут |
|---|---|---|
| Старт | Основной агент читает проектные инструкции, каталоги и материалы отчёта. | Основной агент читает `AGENTS.md`, контекст, три каталога, шаблон mapping и только материалы текущего отчёта. |
| Анализ | По строке 143 `AGENTS.md` запускаются `source_mapper` и при известной структуре `powerbi_reviewer`. | Основной агент восстанавливает логику, фиксирует несостыковки и документирует отчёт. Субагенты не вызываются. |
| Mapping | `source_mapper` применяет свой skill; основной агент затем обязан вызвать `data_architect`. | Основной агент создаёт mapping и reuse review; skill `source-to-target-mapping` применяется только если задача действительно требует отдельного методического прохода. |
| Серверная часть | После «согласования» инструкция ведёт к `postgres_engineer`, хотя в project context серверная валидация отложена. | Сформировать конкретный read-only план, пометить каждый запрос `NOT_EXECUTED`, статус — `VALIDATION_PENDING`; ни подключения, ни SQL-выполнения. |
| Завершение | Риск лишнего делегирования и неявного перехода к реализации. | Обновить только документацию текущего отчёта и накопить очередь будущей валидации. |

Текущий статический риск подключения низкий: ни skill, ни config не выполняют
соединение автоматически. Он становится средним при ручном запуске
`performance_reviewer`, поскольку его prompt допускает `EXPLAIN`; stage gate
в `AGENTS.md` должен это исключить.

## 7. Три наиболее затратных элемента

1. Обязательный многоагентный конвейер в [AGENTS.md](../AGENTS.md): дублирует
   анализ текущего отчёта, передаёт контекст двум агентам и может продолжить
   цепочку до write-агента.
2. Неявный переход от архитектурного решения к реализации в
   [AGENTS.md](../AGENTS.md): вынуждает преждевременно читать и обсуждать SQL,
   тесты и rollback вместо накопления `VALIDATION_PENDING`.
3. Отсутствие явного stage gate в performance skill и его prompt:
   создаёт риск ненужной попытки получить каталог/план, хотя реальные размеры
   и планы пока недоступны.
