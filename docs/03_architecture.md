# Архитектура

## Подтверждённая граница

```text
VM-1: PostgreSQL / сырые регистры 1С (read-only)
             |
             | фильтрация периода + выбор колонок + доступный pushdown/aggregation
             v
VM-2: PostgreSQL / компактные аналитические витрины
             |
             v
           Power BI
```

## Подтверждённые ограничения

- Не хранить на VM-2 полную копию сырых таблиц.
- Ограничивать факты требуемым горизонтом последних 2–3 лет после уточнения точной границы.
- Передавать между ВМ только нужные строки и колонки, предпочтительно после source-side фильтрации/агрегации.
- Хранить на VM-2 итоговые витрины и только фактически переиспользуемые небольшие измерения/промежуточные результаты.
- Не считать «один отчёт = одна таблица» архитектурным правилом.

## Предлагаемый минимальный поток

1. Первичная загрузка только согласованного периода.
2. Регулярное обновление через надёжный инкремент либо пересчёт ограниченного изменяемого окна.
3. Для изменений задним числом — повторный расчёт подтверждённого окна; глубина окна определяется данными.
4. Power BI читает локальные объекты VM-2 и не выполняет тяжёлые операции над источником.

Из-за разницы ресурсов тяжёлые фильтры, `JOIN` и допустимые агрегации предпочтительно выполнять на мощной VM-1 одним read-only `SELECT`. На VM-2 выполнять загрузку компактного результата, проверку и выдачу Power BI. Это направление `PROPOSED`, пока не измерены запрос и передаваемый объём.

Windows Task Scheduler достаточен как текущий оркестратор. Задачи одного объекта не должны запускаться параллельно; необходимы ненулевой exit code, лог без секретов, timeout и защита от повторного запуска.

Решение пользователя 2026-08-31 распространяет automation scope на все 40
физических витрин. Используется один dependency-aware orchestrator на VM-2 и
on-demand jobs без собственных daily-trigger. Глобальная последовательность по
одинаковым timeout и одновременный старт всех jobs запрещены; concurrency
выбирается по измеренным heavy/light профилям и критическому пути до 08:30.
Требование: [project-wide refresh orchestration](reports/project_wide_refresh_orchestration_requirement_2026-08-31.md).

VM-2 имеет 8 vCPU, 8 ГБ RAM и 172 ГБ свободного диска на момент измерения. До фактических тестов считать память главным ограничением конкурентных загрузок: не запускать тяжёлые refresh параллельно и не создавать крупные временные копии. Дисковое пространство выглядит достаточным только как рабочая гипотеза; подтвердить её после оценки объёма первой витрины и старых выгрузок.

## Отложенные решения

Транспорт между ВМ (`postgres_fdw`, потоковая задача чтения/записи или другой механизм), целевые схемы, тип объекта (`view`, `materialized view`, таблица) и режим обновления остаются `DECISION_REQUIRED`. Их нельзя выбирать до проверки сети, прав, source mapping, объёмов, поведения исправлений/удалений и SLA.

Версии PostgreSQL 19 → 18.3 требуется подтвердить командами `SHOW server_version;`. До проверки совместимости не предполагать, что сложный FDW-запрос будет полностью pushdown на более новую удалённую версию.

Существующие самостоятельные выгрузки на VM-2 не являются частью рабочей архитектуры: это изолированный личный тестовый полигон без потребителей и подключений. Перед очисткой всё равно провести read-only инвентаризацию файлов, таблиц и размеров; удаление остаётся отдельным явным действием пользователя.

Для каждой витрины сравниваются прямой `mart`, минимальный технический buffer + `mart` и общий слой только при доказанном повторном использовании. Решение фиксируется отдельным ADR.

Повторное использование посещений доказано двумя отчётами. `ADR-0003` предлагает обезличенный client-day и дневные показатели `дата × клуб`, объединяющие ГП и состояние КБ. Отдельные таблицы посещений Физкульт и Пушкинского не создаются.

«Отчет по ИП» доказал, что его строки переиспользуются показателем ИП в «Посещениях Физкульт», но требуют иной гранулярности: `дата тренировки × клуб × сотрудник × клиент × услуга` с количеством. Кандидат на общий компактный факт описан в `docs/mappings/ip_training.md`. Бизнес-правила подтверждены; объект не утверждён физически до технической проверки временного ключа и кардинальностей. Дублирующее количество ИП не следует добавлять в client-day.

«Загрузка ОП» использует один CRM-домен для основной и плановой страниц. Вместо двух почти одинаковых импортов предложен один interaction-level набор с фактической и плановой датами; исторические snapshots backlog не нужны. Кандидат описан в `docs/mappings/sales_interactions.md` и остаётся без физического DDL до проверки кардинальности телефонии.
